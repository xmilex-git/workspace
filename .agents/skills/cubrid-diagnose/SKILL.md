# cubrid-diagnose

The generic loop (build a red loop, reproduce, minimise, hypothesise, instrument, fix) is the
`diagnosing-bugs` skill. This skill is what that loop needs to know about CUBRID and this host.
Read-only inspection and probes are the lead's; builds, CTP and anything over ~10 min go to the
designated worker (`cubrid-build`, `ctp-run`).

## Terms

- **SA / CS**: `csql -S` runs the engine inside the client (stand-alone); `csql -C` or JDBC talks to a `cub_server` through the master/broker (client-server). Only CS packs values over the network, traces (`show trace`), tracks resource leaks per request and runs SERVER_MODE-only paths (parallel scans).
- **namespace job**: a probe under `unshare -Urmipnf` with volatile overlays over the install and a fresh DB — `tools/fast-gate/fast-sa.sh` (SA), `fast-cs-csql.sh` / `fast-cs-jdbc.sh` (CS); no fsync, private ports and shm, nothing written to the install. Inside, the user is `root` (`$(id -un)`, not `$USER`); job DB names are `cas0`, `cas1`, … (normalize `:cas[0-9]+:` before diffing).
- **archive build**: a gha-ci develop build at `http://192.168.1.48:30080/builds/develop/<40-char sha>/{debug,release}/CUBRID.tar.gz` (`debug` = optdebug); the window moves (about a month), so `curl -sfI` before planning on one.
- **release-line install**: an official release extracted under `~/release/CUBRID-<stamp>` (from `https://ftp.cubrid.org/CUBRID_Engine/<line>/`), used to say "since which version".
- **discriminating row**: a row in the probe's data that matches only if the claimed mechanism is true.
- **driver row**: a one-row outer table (`/*+ ordered use_nl */`) that keeps every inner emission inside one root row.
- **core store**: host cores land at `/data/core/core.%e.%p.%h.%t` (`/data/core` → `/bench/ssd/core`; `find /data/core/` with the trailing slash); container cores under `/bench/hdd/core/ctp/<run>/shard_N/`.

The incidents behind every `(P<n>)` are in `PITFALLS.md`; a new lesson goes there as a case under its rule, or as a new rule added to both files in one commit.

## Preconditions (checkable)

- `ls tools/fast-gate/fast-sa.sh tools/fast-gate/fast-cs-csql.sh` exist (this repo).
- `sysctl kernel.core_pattern` prints `/data/core/core.%e.%p.%h.%t`; `ls -ld /data/core` is a symlink to `/bench/ssd/core`.
- `curl -sfI http://192.168.1.48:30080/builds/develop/ | head -1` answers (archive server reachable; use `--noproxy '*'` for LAN hosts).
- `ls ~/release/ | grep -c CUBRID-1` ≥ 1 (release-line installs present) or fetch per P2.

## Where to run the probe (Phase 1: the loop)

- A probe runs in CS mode on an optdebug build unless the question is SA-only: `csql -S` shows `show trace` as NULL for every statement, tracks no resource leaks, does not pack values over the network and never runs SERVER_MODE-only paths, so a defect in re-execution, value transfer, tracing or parallel scans is invisible there — use a `fast-cs` job (or JDBC) and read the trace right after the query. (P1)
- A repro on a develop commit uses the archive build for that sha when the archive still has it, else a local `INSTALL_PREFIX=… just build` (release ≈ 3 min; it then overwrites the conf with the campaign conf — copy the worktree's `conf/cubrid.conf` back and set the port); an archive's binaries carry `RPATH=/home/CUBRID/lib`, so run them with `LD_LIBRARY_PATH=<inst>/lib` and confirm with `ldd`; `CUBRID_TMP` stays short (the socket path must fit 107 bytes); the install's master is stopped by the pid whose `/proc/<pid>/exe` is under it (no `cubrid master stop` in archives, never `cubrid service stop` or `pkill`); after a crash run, wait ~10 s before starting the next version so the respawned orphan does not register with the new master. (P2)
- "Since which version" is answered on release-line installs: `~/release/CUBRID-11.4.6.1963`, `-11.3.6.1321`, `-11.2.9.0866`, `-11.0.16.0419`, `-10.2.18.9024` (no public 11.1); 11.2/11.0/10.2 need `libncurses.so.5` from `nix-build tools/legacy-libs/ncurses5-el8.nix -o .git_ignored_dir/legacy-libs/ncurses5` on `LD_LIBRARY_PATH`; each install's conf is stock except `cubrid_port_id` — claim a port first, and when the port is taken make a shadow install (symlinks except `conf`, `log`, `var`, `tmp`) with the claimed port. (P3)
- A/B over two installs starts with their confs: hardlinked variants (`cp -l`, `-pc0`) share one `conf/cubrid.conf` (`ls -i`), so `rg -n '^(max_plan_cache_entries|plus_as_concat|return_null_on_function_errors)' <install>/conf/cubrid.conf` on both before reading any result, and break the link (`cp -p` to a temp name, `mv` back) before editing one. (P4)
- A database loaded for a probe is generated by seed table × cross join × `ROWNUM <= N` (`CREATE TABLE t1 (n INT PRIMARY KEY)` with 10 rows, then `INSERT INTO t SELECT ROWNUM, … FROM t1 a, t1 b, t1 c … WHERE ROWNUM <= N`), never `CONNECT BY LEVEL <= N` beyond a few thousand rows; a recursive CTE stops at `cte_max_recursions` (2000). (P5)
- A copied database is opened by the engine only after its `_vinf` names the copy: a reflink or `cp` copy keeps the original's absolute paths in `_vinf` and in every volume header, the engine reads `_vinf` first (a header path that differs only gives a -114 notification), so a server or SA utility on an unfixed copy opens the original's volumes and `cubrid deletedb` deletes them; rewrite every `_vinf` line to the copy's directory (cubrid-fastmig baseline DBs: `basedb/safe_copy.sh`), print it before the first start, check `ls -l /proc/<cub_server pid>/fd` holds no path outside the copy, and remove a copy by its literal path with `rm -rf`, never `deletedb`. (P18)

## Designing the probe (Phase 2–3)

- A claim about develop is made only after running it on a develop build with a discriminating row; a statement that fails on develop is run three ways on the candidate — with keys reached, on an empty table, and with a bound that skips every key — and the server log's error count is read beside the client message, because a check that moved from scan-open into the key compare fails only when a key is met. (P6)
- A "subquery result reused across inner rows" or stale-dptr question is probed behind a driver row: `qexec_clear_all_lists` runs once per root row, so a 2-table join hides a missing per-row dptr reset; `xasl_debug_dump=yes` (optdebug, client parameter) prints which node owns the dptr list. (P7)
- csql and CQT grammar that wastes a probe: `select @v := s a` is ambiguous — write `(@v := s) a`; no quoted values inside probe labels; `… group by g using index a, b order by 1` (not `using index … group by`); ROWNUM / ORDERBY_NUM() cannot share an expression with a column or correlated subquery (only CASE/IF/DECODE conditions escape); `count(*)` over a CONNECT BY subquery returns 1 per start row (CBRD-27461) — use `count(col)` or `max(level)`; CQT answers print only `Error:<code>`, so message-text changes are invisible to CTP; JDBC cannot prepare a CTE whose select list holds an untyped `?` (-494); `cast(? as int)` is coerced on the client, so the server's path never runs — hand it a string with `concat(?, '')`; literal-only expressions fold at compile; an indexed column's comparison fails at scan open on develop too (probe an unindexed column); a PL/CSQL function declared PARALLEL_ENABLE that uses SQL is refused at CREATE, so the runtime refusal text is reachable only by a Java SP or an undeclared SP in a worker, and PL/CSQL in a worker shows the client only -889 (the text is in `log/pl/*_pl.log`). (P8)
- A statement that runs on develop keeps running unless the break is justified at spec level: SERIAL (`s.next_value`, `s.current_value` in comparisons, arithmetic, aggregates), host variables, PL/CSQL and JDBC binds are written by real applications, so turning their develop result into an error means the engine is wrong, not the test; session variables as typed operands are the only accepted exception, and the exception list is recorded in the ticket. (P9)
- When the same item fails twice, or a fix for symptom A surfaces symptom B of the same kind, stop patching consumers: write the shared-cause hypothesis in one line (a producer decision vs its consumers), measure develop per consumer kind in separate statements (output, aggregate, comparison, arithmetic, CAST, WHERE/IN/BETWEEN, ORDER BY, CASE) across releases, fix at the decision site, delete the consumer patches, add a generation-time assert comparing the decision with the declaration, and only then rerun the gate; a type the compiler can know from the schema, spec or plan is a generation defect, never an exception. (P10)

## Instrumenting (Phase 4)

- For "where does the server raise error -NNN", add `call_stack_dump_activation_list=-NNN` to the smoke conf: `er_set` writes the symbolized stack into `$CUBRID/log/server/<db>_<date>.err` with no debugger; client-side parser errors do not pass `er_set` — run SA `csql -S` under `timeout N gdb -batch -x <script> --args …` (gdb owns the process and ends with it); SERVER_MODE-only paths show in `xasl_debug_dump=yes` (access-spec flags such as `no_parallel_scan`); never `pgrep -f` with a string that appears in your own command line, never an unbounded `wait`, every csql/gdb under `timeout`, and a smoke that rewrote the install conf copies the claimed-port conf back at the end. (P11)
- gdb is a diagnosis tool, not verification evidence, and it never attaches to a live `cub_server` (a 2026-08-06 attach produced a server core during QA): it reads cores offline and runs SA `csql -S` inside a namespace job (`gdb -batch -x cmds.gdb --args csql -S … -i <sql>` with a pending breakpoint whose `commands` print `bt` and `continue`; `info breakpoints` at the end gives the hit count; a runner waits for a `printf "=== GDB READY\n"` the commands file emits before its first `continue`, since `-p` attach does not echo "Continuing."); break on a source line, not an extern function (the `@plt` stub stops first with no arguments and aborts the `commands` block), read `info breakpoints` sub-locations before comparing hit counts, and expect an optdebug frame line to sit at a loop head near the real call. (P12)
- A core is matched by the pid you own, never by time and name: start csql with `&` and keep `$!`, take a `cub_server` pid from `/proc/<pid>/exe` before the probe, then `find /data/core/ -name "core.*.<pid>.*"` — `%e` is the crashing thread's comm, so a server assert is `core.transaction.<pid>…` or `core.vacuum.<pid>…`, never `core.cub_server.*` — and run gdb with that process's binary; a core from a `just ctp` container unwinds to `?? ()` without the image's glibc: extract the cubridci image rootfs once (`podman create --name x docker.io/cubridci/cubridci@sha256:<digest>`, `podman export x -o rootfs.tar`, `tar -xf … -C <scratch>/rootfs`, `podman rm x`) and read it with `gdb -batch -ex "set sysroot <rootfs>" -ex "set solib-search-path <run>/shard_0/CUBRID/lib" -ex "file <run>/shard_0/CUBRID/bin/cub_server" -ex "core-file <core>" -ex "bt 40"` (the crashing thread is current; an assert shows as `abort_handler → __assert_fail → <CUBRID frame>` with file:line; the assertion text is not in the core); cores are sparse — `du`, not `stat`. (P13)
- A CTP run prunes its shard copies, so a container core's binary is the run's install (`install=` in `provenance.txt`) — usable only if its `lib/libcubrid.so.11.5` sha256 still matches what the run used (the gate report's fingerprint); otherwise rerun the case with `CTP_KEEP_COPIES=1`. The image digest is in `provenance.txt` too.
- An `mspace_free` / `db_private_free` abort on a `parallel-query` thread is a cross-thread free until proven otherwise: `cub_server` private heaps are per-thread dlmalloc mspaces (`FOOTERS=0`), so a buffer freed by a thread that did not allocate it aborts only when the address check catches it and silently corrupts both heaps otherwise, which makes a bisect non-monotonic; in gdb, `thrd->private_heap_id` is the `HL_MSPACE*` — print `((mstate) msp)->seg` base/size for the crashing thread and for the connection thread with the same tran_index (the one in `qexec_execute_query` / `run_jobs`) and see which range holds the freed pointer, then look for a main-thread producer (gate, pin, recipe) of the freed value. (P14)
- `cubrid checkdb` is not a test: "정합성 체크" in this workspace means comparing query results (variants against a serial no-hash reference), checkdb runs only for work that changes index structure (page split/merge, overflow keys, prefix separators) on a small DB and is named in the report, and worker prompts carry "no checkdb". (P15)

## Reporting a triage (Phase 5)

- A defect-triage report says, per issue, whether it occurs on a develop **release** build with the engine-default conf (only the port set) in CS mode, a 0–10 severity (integrity breaks high, shapes nobody writes low; an optdebug-only assert scores 0) and the reason, with repro steps that read "start the server, run this SQL"; no release outcome is stated from source reading (a release PREPARE once failed with "Internal error- reporting semantic error" where the source read as "passes silently"), issue-body claims are re-probed before they are repeated, fix directions and internal tool names stay out (stack frames as evidence are fine), and it is delivered as a Korean `.md` via SendUserFile plus a short summary table. (P16)
- Evidence that will go to JIRA comes from develop builds only (`cubrid-jira-issue-write` P2); a branch-install repro stays in the workspace issue.

## Cleanup (Phase 6)

- A core whose cause is recorded (assert text + case, or a backtrace in `cores-analyzed.txt` under the effort's scratch) is deleted at once by literal path, as are the smoke DB dirs of each batch after their logs are read and every CTP run dir whose evidence has been copied out (keep only the latest passing baseline); other sessions' cores are listed for the user, never touched; a "how much disk" question is answered with a per-location `du` table (scratch, run dirs, cores, worktree). (P17)
- Servers and masters the probe started are stopped by pid and their ports released (`cubrid-server-control` P4, P8); a conf the smoke rewrote is restored (P11).
