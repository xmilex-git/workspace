# PR Body Tone Guide

PR 본문을 작성할 때 반드시 따르는 문체 기준. 기준점은 **PR #8096**(CBRD-24029) — 아래 예제 3이 이 문체의 정수다.
`pr-corpus/`(#4432–#6911)는 변경 규모별 분량 감각을 잡는 참고용이며, 문장과 구성은 이 문서를 따른다.

## 독자와 목적

리뷰어는 이 코드를 처음 본다고 가정한다. 코드를 열지 않고 본문만 읽어도
**원래 어떻게 돌아가야 하는지 → 무엇이 잘못됐는지 → 그래서 사용자에게 무슨 일이 생기는지 → 어떻게 고쳤는지**를
순서대로 따라갈 수 있어야 한다. 결함을 바로 들이밀지 않고, 먼저 그 자리의 정상 동작을 한 문단으로 설명한다.

## 골격

```markdown
http://jira.cubrid.org/browse/CBRD-XXXXX

<무엇을 고치는/바꾸는 PR인지 한 문장. "~하는 PR입니다.">

### Purpose

<1. 정상 동작: 이 자리가 원래 어떻게 돌아가는지, 누가 무슨 역할인지>
<2. 결함: 어디가 어떻게 어긋났는지. 코드 발췌 + ← → 주석이 있으면 그림으로>
<3. 결과: 사용자가 보는 현상. debug 빌드 / release 빌드로 나눠서>

### Implementation

**1. <바꾼 것 한 문장>**

<무엇을 왜 바꿨는지. 단계·순서가 있으면 텍스트 트리>

**2. ...**

### Remarks

* 동작 변화: <보이는 변화와, 바뀌지 않은 것>
* <남긴 TODO와 별도 이슈>
* <리뷰 보조 커밋 등 머지 전에 정리할 것>
```

- 첫 줄 한 문장 요약 — Purpose가 두 문단 이상일 때 쓴다. Purpose가 한두 문장이면 그 자체가 요약이므로 생략한다.
- `### Purpose` — **항상 필수**.
- `### Implementation` — 변경이 여러 관심사에 걸칠 때. 한두 함수 수정은 생략한다. 항목은 **파일이 아니라 관심사(무엇을 해결했나)별** 번호 매김이고, 제목은 볼드 한 문장이다.
- `### Remarks` — 해당 불릿이 하나라도 있으면 쓴다. 없으면 생략한다.
- **길이는 변경 크기에 비례한다.** Purpose 한 문장짜리 6줄 PR이 정상이다(예제 1, 2). 그림·Implementation·Remarks는 설명할 메커니즘이 있을 때만 붙인다.

## 규칙

1. **짧은 문장, 한 문장에 사실 하나.** 절이 셋 이상 이어지면 자른다.
2. **합니다체.** 그림과 라벨 안에서는 명사형으로 끝낸다(잠듦, 넘겨줌, 종료, 대기).
3. **쉬운 우리말 동사.** 넘겨주다, 잠들다, 깨우다, 챙기다, 바닥나다, 손대다, 쥐다, 놓다, 떼어 내다, 한 바퀴 돌다.
   "수행", "처리", "로직", "구조를 개선", "최적화" 같은 말은 무엇을 하는지 보이는 동사로 바꾼다.
4. **용어는 처음 나올 때 한 구절로 풀이한다.** 그 다음부터는 그대로 쓴다.
   예: "버퍼 풀에서 victim을 찾지 못한 스레드는 대기 큐에 들어가 잠들고, 누군가 victim을 넘겨줘야 깨어납니다."
   역할이 나뉘어 있으면 누가 무엇을 맡는지 나열한다: "그 역할은 flush 데몬, post-flush 데몬, ... 등이 나눠 맡습니다."
5. **숫자는 출처와 함께.** 주기·상한·기본값은 괄호에: `(100ms 주기)`, `(기본 300초)`, `(`page_flush_interval_in_msecs`, 기본 1초, 0이면 무한 대기)`.
   측정한 값은 "실측"이라고 밝힌다: `(실측 리스트당 최대 9개)`. 측정하지 않은 효과는 쓰지 않는다.
6. **결과는 빌드별로.** 사용자가 보는 현상을 `debug 빌드 : ...` / `release 빌드: ...`로 나눠 적는다.
7. **그림.** 루프, 호출 순서, 단계, 서로 기다리는 관계가 있으면 fenced block(언어 표기 없음)에 텍스트 트리로 그린다.
   - 결함 코드는 원문을 발췌하고 `←`에 왜 틀렸는지, `→`에 그 결과를 단다.
   - 트리 기호는 `└ ├ │`. 한 줄에 한 단계. 조건·수치는 괄호로.
   - 그림은 글로 설명한 것을 한눈에 보여 주는 용도다. 그림만 두고 글을 빼지 않는다.
8. **코드 식별자는 백틱, 영어 그대로.** 함수는 `name()`. 파일명은 함수가 어디 있는지 알려야 할 때만 괄호로 덧붙인다.
9. **Implementation 항목은 "무엇을 + 왜".** 바꾸지 않은 기존 경로가 어떻게 되는지도 한 문장 둔다
   ("같은 함수를 부르는 기존 경로는 상한 없이 그대로 동작합니다"). 두 곳의 기준을 하나로 묶었으면 그 이유를 쓴다.
10. **Remarks의 "동작 변화"는 바뀐 것과 바뀌지 않은 것을 같이 쓴다.** 통계·오류 메시지·로그처럼 보이는 변화를 먼저,
    그리고 "디스크 포맷, 로그, 프로토콜, 시스템 파라미터는 바뀌지 않습니다"처럼 호환성 범위를 한 줄로.
11. **diff에 없는 내용을 쓰지 않는다.** 추측, 과장, 필러("본 PR은", "전반적으로", "안정성 개선") 금지.

## 사람처럼 읽히는 이유 — 단어와 논리

#8096이 기계 번역문처럼 읽히지 않는 이유를 규칙으로 옮긴 것이다. 위 규칙과 겹치는 부분은 더 구체적인 쪽이 이긴다.

### 단어

1. **행위자가 있는 문장.** 주어는 스레드, 데몬, vacuum, 워커처럼 실제로 움직이는 것이다. "동기화 호출이 잦아집니다"가 아니라
   "스레드가 서로 기다립니다". "~되었습니다"처럼 누가 했는지 없는 피동문은 쓰지 않는다.
2. **몸으로 그려지는 동사.** 넘겨주다, 잠들다, 깨우다, 챙기다, 손대다, 바닥나다, 훑다, 쥐다, 놓다, 몰리다, 떨어지다("zone 3로 떨어지는 BCB").
   추상 동사(수행, 처리, 관리, 보장, 개선, 최적화)가 나오면 그 자리에서 무엇을 하는지 보이는 동사로 바꾼다.
3. **영어 용어는 영어 그대로, 그 주변은 우리말.** `victim`, `flush`, `quota`, `zone 3`를 희생자·할당량으로 옮기지 않는다.
   "quota를 넘긴 private 리스트", "LRU mutex를 쥔 채"처럼 용어만 남기고 조사와 동사는 우리말이다.
4. **비유는 하나를 골라 끝까지 쓴다.** "안전망"이 도입(이때를 대비한 안전망), 결함(안전망이 없는 상태), 수정 전반을 꿰고 있다.
   매 문단 다른 비유를 꺼내지 않는다.
5. **헤지는 사실이 확률적인 자리에만.** "다른 공급 경로가 **우연히** victim을 주지 않으면", "아무도 챙기지 **않을 수 있습니다**",
   "사용자 트랜잭션을 먼저 살리는 편이 **나을 수 있어**". 확실한 사실에 "~로 보입니다", "~일 수 있습니다"를 붙이지 않고,
   확률적인 사실을 단정하지도 않는다.
6. **날짜·횟수·실측치로 말한다.** "오래된 결함"이 아니라 "2017년 도입된 이후 한 번도 실행되지 않았습니다".
   "많이 배정"이 아니라 "실측 리스트당 최대 9개".
7. **평가어와 꾸밈말 금지.** 효과적으로, 안정적으로, 명확하게, 일관되게, 적절히, 다양한, 핵심, 주요, 전반적으로, 보장합니다,
   이를 통해, ~함으로써, 중요한. 자기 변경을 칭찬하는 말은 한 단어도 쓰지 않는다.
8. **접속은 말하듯이.** 그런데, 그래서, 그 결과, 그 사이, 그래도, 하더라도. "따라서", "또한", "이에 따라", "뿐만 아니라",
   "결론적으로"는 쓰지 않는다.
9. **라벨 금지.** "문제:", "원인:", "해결:", "배경:" 같은 머리표를 문장 앞에 붙이지 않는다. 문장이 흐름으로 그 역할을 한다.

### 논리

1. **인과 사슬.** 각 문장은 앞 문장이 만든 질문에 답한다.
   정상 동작 → 누가 맡는가 → 그들의 한계("그런데 이들은 모두 사건이 있어야 동작하므로") → 그래서 안전망이 있다 → 안전망이 깨져 있다 → 결과.
   한 문단은 인과 한 걸음이고, 문단의 마지막 문장은 그 걸음의 결과다.
2. **독자의 다음 질문을 먼저 막는다.** "그럼 첫 조건만 고치면?" → "첫 조건을 고치더라도 `!restarted` 때문에 ...".
   "panic 경로도 바꿨나?" → "같은 함수를 부르는 기존 경로는 상한 없이 그대로 동작합니다".
   "왜 그 순서인가?" → "quota 안쪽 페이지는 그 스레드가 쓰는 중이라 최후에만 사용합니다".
3. **이전 동작을 수치와 함께 인정한 뒤 고친다.** "한 리스트에서 대기 스레드가 바닥날 때까지 ... 계속했습니다(실측 리스트당 최대 9개)"
   다음에 "상한 인자를 추가해". 고친 것만 쓰면 무엇이 달라졌는지 독자가 알 수 없다.
4. **왜 지금까지 몰랐는지 말한다.** "호출처가 위 루프뿐이라 함께 실행된 적이 없던", "깨워 줄 주체가 없습니다".
   결함이 숨어 있던 이유는 결함 자체만큼 중요하다.
5. **설계 선택은 기존 코드와의 일관성으로 정당화한다.** "일반 victim 탐색인 `pgbuf_get_victim()`과 같은 정책을 따릅니다",
   "flush 데몬과 같은 매크로를 쓰도록 묶어, 두 곳의 기준이 어긋나지 않게". 새로움이나 우수함으로 정당화하지 않는다.
6. **같은 숫자를 다시 써서 섹션을 잇는다.** 그림의 "최대 5개"가 항목 2의 "배정 상한(5개)"로, "100ms 주기"가 그림의 "(100ms 마다)"로.
   반복은 연결 용도일 때만.
7. **안 한 일은 이유와 처리 계획을 같이.** "panic 상황에서는 ... 나을 수 있어 TODO로 남겼고, 별도 이슈로 검토합니다".
8. **메타 서술과 마무리 요약 금지.** "이 PR에서는", "아래에서 설명합니다", "정리하면", "결론적으로"를 쓰지 않는다. 마지막 문장은
   사실로 끝난다.

## 셀프 체크 (제출 전)

- 피동문, 추상 동사, 평가어, 라벨을 찾아 바꾼다. 문장마다 주어가 실제로 움직이는 것인지 본다.
- 문단마다 "앞 문단이 던진 질문에 답하는가"를 본다. 답하지 않으면 순서를 바꾸거나 지운다.
- 고친 것 앞에 이전 동작이 수치와 함께 있는가. 안 한 일에 이유와 계획이 있는가.

- 코드를 모르는 사람이 Purpose만 읽고 "원래 동작 → 결함 → 사용자 현상"을 말할 수 있는가.
- 처음 쓰는 용어마다 풀이가 붙어 있는가. 숫자마다 단위·기본값·출처가 있는가.
- 절이 셋 이상인 문장이 남아 있으면 자른다.
- Implementation 항목이 파일 나열이 되어 있으면 관심사별로 다시 묶는다.
- diff에 없는 내용이 한 줄이라도 있으면 지운다.
- 소형 수정에 요약 줄·그림·Remarks를 붙였으면 뺀다. crash fix 한 줄 수정인데 본문이 10줄이면 잘못 쓴 것이다.


```markdown

### Purpose
```

### 예제 3 — 대형 bug fix: 이 톤이 기준이다 (#8096, CBRD-24029)

```markdown
http://jira.cubrid.org/browse/CBRD-24029

page maintenance 데몬이 victim을 기다리는 스레드에게 victim을 넘겨주지 못하던 버그를 고치는 PR입니다.

### Purpose

버퍼 풀에서 victim을 찾지 못한 스레드는 대기 큐에 들어가 잠들고, 누군가 victim을 넘겨줘야 깨어납니다.
그 역할은 flush 데몬, post-flush 데몬, zone 3로 떨어지는 BCB 처리 등이 나눠 맡습니다. 그런데 이들은 모두
flush나 페이지 접근 같은 사건이 있어야 동작하므로, 활동이 적은 시점에는 아무도 대기 스레드를 챙기지
않을 수 있습니다. 이때를 대비한 안전망이 page maintenance 데몬(100ms 주기)이 호출하는
`pgbuf_direct_victims_maintenance()`입니다.

이 함수의 루프는 시작 조건과 계속 조건이 서로 모순이라, 2017년 도입된 이후 한 번도 실행되지 않았습니다.

```
for (index = prv_index, restarted = false;
     ... && index != prv_index && !restarted;      ← 시작하자마자 index == prv_index 이므로 거짓
     ...)                                          → 본문 0회 (shared 리스트 루프도 같은 구조)
```

첫 조건을 고치더라도 `!restarted` 때문에 마지막 리스트에서 0번으로 넘어가는 순간 멈춰, 리스트를 한 바퀴
돌지 못합니다. 그 결과 안전망이 없는 상태가 됩니다.

```
pgbuf_allocate_bcb
 └ victim 탐색 실패 → 대기 큐 등록 → 잠듦
     다른 공급 경로가 우연히 victim을 주지 않으면
     page_latch_timeout_in_msecs (기본 300초) 까지 대기
       debug 빌드  : assert (r != ER_CSS_PTHREAD_COND_TIMEDOUT) 로 abort
       release 빌드: 쿼리 에러
```

### Implementation

**1. LRU 리스트를 round-robin으로 한 바퀴 돌며 victim을 넘겨줌**

`pgbuf_assign_direct_victims_round_robin()`이 지난번에 멈춘 다음 리스트부터 한 바퀴를 돕니다. 방문 순서는
일반 victim 탐색인 `pgbuf_get_victim()`과 같은 정책을 따릅니다. 다른 스레드의 private 리스트는 quota를 넘긴
경우에만 먼저 손대고, quota 안쪽 페이지는 그 스레드가 쓰는 중이라 최후에만 사용합니다.

```
pgbuf_direct_victims_maintenance        (100ms 마다, 최대 5개)
 ├ 1단계 quota를 넘긴 private 리스트
 ├ 2단계 shared 리스트
 ├ 3단계 quota 이하 private 리스트 (최후 수단)
 │    대기 스레드가 없거나 5개를 다 넘겨주면 그 자리에서 종료
 └ 그래도 대기 스레드가 남고, flush하면 victim이 생길 리스트가 있으면 flush 데몬을 깨움
```

**2. 주기당 배정 상한(5개)이 실제로 지켜지게 함**

`pgbuf_panic_assign_direct_victims_from_lru()`는 한 리스트에서 대기 스레드가 바닥날 때까지 LRU mutex를 쥔 채
배정을 계속했습니다(실측 리스트당 최대 9개). 배정 상한 인자를 추가해 page maintenance 데몬은 남은 몫까지만
넘겨주게 했습니다. 탐색 중 대기 스레드가 몰렸을 때 같은 함수를 부르는 기존 경로는 상한 없이 그대로 동작합니다.

**3. 처음으로 실행되는 코드의 결함 정리**

호출처가 위 루프뿐이라 함께 실행된 적이 없던 `pgbuf_lfcq_assign_direct_victims()`에서, 리스트의 bottom이
NULL일 때 역참조하던 부분을 막았습니다. hint와 bottom이 같으면 같은 구간을 다시 훑지 않게 했습니다.

**4. flush 데몬 조건부 기상**

flush 데몬은 flush할 후보를 찾지 못하면 다음 주기(`page_flush_interval_in_msecs`, 기본 1초, 0이면 무한
대기)까지 잠듭니다. 그 사이 `pgbuf_adjust_quotas()`가 quota와 zone을 조정해 flush 대상이 새로 생겨도 깨워 줄
주체가 없습니다. 그래서 대기 스레드가 남아 있고, flush가 진행 중이 아니며, flush 대상 리스트의 zone 3에
아직 victim 후보가 아닌 BCB가 있을 때만 flush 데몬을 깨웁니다. flush 대상을 정하는 식은 flush 데몬과 같은
매크로(`PGBUF_PRIVATE_LRU_VICTIM_FLUSH_TARGET`)를 쓰도록 묶어, 두 곳의 기준이 어긋나지 않게 했습니다.
```

```markdown
### Purpose

병렬 힙 스캔과 통계 샘플링(`UPDATE STATISTICS ... WITH FULLSCAN`)은 스캔 시작 때 찍어 둔 파일 페이지
```

```markdown
vacuum은 빈 페이지를 체인에서 떼어 낼 때 이웃 페이지를 쥔 채, 떼어 낸 페이지를 할당 해제하려고 다시
fix 합니다. 그 페이지를 비트맵 순서로 먼저 잡은 워커가 이웃 페이지를 기다리면 둘은 서로를 기다립니다.

```
워커   : 페이지 P를 쥔 채 → 이웃 페이지 Q를 fix 대기
vacuum : Q를 쥔 채        → P를 fix 대기
  page_latch_timeout_in_msecs (기본 300초) 까지 양쪽 다 멈춤
    debug 빌드  : assert
    release 빌드: 300초 뒤 질의 실패
```

**1. 다음 페이지를 fix 하기 전에 지금 페이지를 놓음**

비트맵 순서에서는 지금 페이지를 쥐고 있어도 다음 페이지가 보호되지 않습니다(해제된 페이지는 이미
건너뜁니다). 그래서 `get_next_vpid_with_fix()`(`px_scan_input_handler_heap.cpp`)와
`scan_ftab_partition()`, `scan_ftab_partition_multi()`(`histogram_sampler_sr.cpp`)가 다음 페이지를 fix 하기
전에 지금 페이지를 unfix 합니다. 이전 페이지를 들고 있던 `m_tl_old_page_watcher`와 `old_pw`는 제거했습니다.

**2. vacuum이 대기자를 만나면 제거를 포기**

그 빈 페이지를 bestspace에 등록합니다.
```
