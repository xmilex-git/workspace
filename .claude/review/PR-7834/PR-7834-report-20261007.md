- **주요 이슈**: 생성기 fast-path의 비결정 항 판정이 좁음. 작은 상한에서 스필이 메모리를 늘림. 해시 리다이렉트가 PK 순서 루트 출력을 바꿈.

## Findings

### Blocking (must fix)

- **생성기 fast-path가 세션 변수와 저장 함수를 한 번만 평가** (`src/query/query_executor.c:18713`)
  - 결함: `qexec_opcode_is_prior_or_volatile`은 RAND, DRAND, RANDOM, DRANDOM, SYS_GUID만 비결정으로 봅니다.
  - 원인: fast-path(`qexec_execute_connect_by_generator`)는 자식 스캔을 사전 스캔에서 한 번만 돌리고 그 결과를 모든 레벨에 재사용합니다. 그래서 스캔 술어에 들어간 `@v :=` 대입이나 저장 함수 호출이 레벨마다 다시 평가되지 않습니다.
  - 결과: develop과 다른 행을 냅니다. 같은 집합(서브쿼리, 메서드, 시리얼, 세션 변수)은 기존 `qo_or_extract_check_ref_pre`(`query_rewrite_term.c:4516`)가 이미 "두 번 평가하면 안 되는 항목"으로 분류합니다.

```sql
CREATE TABLE one_row (c INT); INSERT INTO one_row VALUES (1);
SET @w = 0;
SELECT LEVEL FROM one_row CONNECT BY LEVEL <= 10 AND c + (@w := @w + 1) <= 4;
-- develop(30043f492): 4행, @w=4 / PR head: 10행, @w=1 (optdebug, 3회 반복 동일)
-- c + f_seq (c) <= 4 (시리얼 NEXT_VALUE를 반환하는 PL/CSQL 함수): develop 4행, 시리얼 4 / head 10행, 시리얼 1
```

- **작은 상한에서 스필이 메모리를 늘림** (`src/query/query_executor.c:20052`)
  - 결함: 청크 크기 `chunk_bytes = MAX (limit / 4, 1)`가 청크 하나에 붙는 고정 버퍼보다 작아질 수 있습니다.
  - 원인: 청크마다 `qfile_open_list`(20121, 20621)로 리스트를 하나씩 엽니다. `qmgr_create_new_temp_file`은 리스트마다 `temp_mem_buffer_pages`(기본 4) x 16KB = 64KB 메모리 버퍼(membuf)를 미리 할당합니다.
  - 결과: 상한이 256KB보다 작으면 내린 바이트보다 버퍼가 더 큽니다. 상한 0("노드마다 스필")에서는 노드당 64KB를 씁니다. 상한을 줄이는 목적(메모리 절약)과 반대로 동작하고, 자식이 많으면 OOM이 날 수 있습니다. 1차 이후 추가된 자식 스필뿐 아니라 stack/path 스필도 같은 경로입니다.
  - 측정(release SA, star 10만 자식, 튜플 합 약 13MB, SA 기본 RSS 약 520MB):

| `max_connect_by_dfs_size` | 128M | 8M(기본) | 1M | 64K | 0 |
|---|---|---|---|---|---|
| 피크 RSS (MB) | 566 | 575 | 554 | 869 | 6843 |
| 시간 (s, 중앙값) | 0.224 | 0.272 | 0.256 | 0.266 | 1.290 |

  체인 깊이 5만도 128M에서 463MB, 상한 0에서 3592MB였습니다.

- **PK만 있는 테이블에서 START WITH 루트 순서가 바뀜** (`src/optimizer/rewriter/query_rewrite_select.c:4049`)
  - 결함: `531b2583` 이후 게이트는 자식 컬럼(`PRIOR id = pid`의 `pid`)으로 시작하는 인덱스가 있을 때만 `single_table_opt`(단일 테이블 계층 질의 플랜)를 유지합니다.
  - 원인: `id` PK만 있는 테이블도 해시 경로로 갑니다. 해시 경로는 입력 전체를 재료화한 뒤 START WITH를 적용합니다. 그래서 PK 인덱스로 START WITH를 풀던 develop과 달리 루트가 heap 순서로 나옵니다.
  - 결과: ORDER BY 없는 계층 질의의 출력 순서가 develop과 달라집니다. PR 본문과 JIRA는 아직 "인덱스가 하나라도 있으면 기존 플랜 유지, 결과 불변"이라고 적고 있습니다.

```sql
CREATE TABLE foo (a INT PRIMARY KEY, b INT);
INSERT INTO foo VALUES (4, 5), (3, 4), (2, 3), (1, 2);
SELECT a, b FROM foo START WITH a < 4 CONNECT BY PRIOR a = b;
-- develop: 루트 1, 2, 3 순 (iscan pk_foo_a) / head: 루트 3, 2, 1 순 (sscan) (CTP bug_bts_9613)
```

### Non-blocking (should consider)

- **ORDER SIBLINGS BY 동순위 형제 순서가 상한에 따라 달라짐** (`src/query/query_executor.c:20523`)
  - 원인: 스필된 자식은 키를 뒤집어 정렬한 뒤 정방향으로 읽고, 꺼낼 때 다시 역순이 됩니다. 이 경로는 해시 경로에서는 메모리 경로와 순서가 같습니다. 그러나 인덱스, heap 경로에서는 같은 키를 가진 형제의 순서가 반대로 나옵니다.
  - 증거: 인덱스 경로 star 2000 자식(`ORDER SIBLINGS BY k`, k에 동순위)에서 develop과 head 기본값은 같습니다. head 상한 65536과 0에서는 순서가 다릅니다(행 집합은 같음). `ORDER SIBLINGS BY k, id`와 해시 경로는 모든 설정에서 같습니다.
  - 제안: 비해시 경로는 원래 키로 정렬하고 역방향으로 읽는 방식이 메모리 경로(`qexec_connect_by_sort_siblings`의 안정 정렬)와 맞습니다.
- **사이클 필터가 깊이에 선형** (`src/query/query_executor.c:18326`)
  - 원인: 자식 후보마다 경로 배열 전체(16B 노드)를 훑어 해시를 비교합니다. 전체 비용이 O(깊이^2)입니다.
  - 측정(release, 128M): 체인 깊이 25k/50k/100k/200k = 0.54/1.25/4.20/15.3 s입니다. 같은 20만 행을 fan-out 10 트리로 만들면 0.57 s입니다. 200k 프로파일에서 전체의 92%가 `qexec_execute_connect_by`이고, 그중 98.8%가 18328행 `if (path[i].hash == child_hash)`입니다.
  - 제안: develop보다는 빠르므로 회귀는 아닙니다. 경로 해시를 개수 세는 해시 집합으로 유지하면 O(1)이 됩니다(cpp-perf-rules PRIORITY 1단계, 차선책은 해시만 따로 둔 배열 MEM-04).
- `src/query/query_executor.c:20541`: "the file is already gone" 주석이 틀립니다. `qfile_sort_list_with_func`는 사전 실패 경로(정렬 결과 리스트 열기, 스캔 열기, 정렬 정보 초기화 실패)에서 입력 리스트를 지우지 않고 NULL을 반환합니다. 그래서 `QFILE_FREE_AND_INIT_LIST_ID`는 list_id만 풀고 temp 파일은 질의가 끝날 때까지 남습니다. 오류 경로에서만 생깁니다.
