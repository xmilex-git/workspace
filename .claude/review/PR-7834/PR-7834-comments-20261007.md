### 인라인 1 - src/query/query_executor.c:18713

`DRANDOM` 계열은 빠졌지만, 사전 스캔 결과를 모든 레벨에 재사용하는 구조라서 세션 변수 대입이나 저장 함수 호출이 스캔 술어에 있어도 같은 문제가 생기는 것 같습니다. 아래 쿼리가 develop은 4행(`@w`=4), PR은 10행(`@w`=1)이 나옵니다.

```sql
SET @w = 0;
SELECT LEVEL FROM one_row CONNECT BY LEVEL <= 10 AND c + (@w := @w + 1) <= 4;
```

시리얼을 반환하는 PL/CSQL 함수(`c + f_seq (c) <= 4`)도 develop 4행, PR 10행이었습니다. `qo_or_extract_check_ref_pre` 에서 두 번 평가하면 안 되는 항목(서브쿼리, 메서드, 시리얼, 세션 변수)을 이미 분류하고 있어서, 같은 기준을 쓰는 것은 어떨까요?

### 인라인 2 - src/query/query_executor.c:20052

청크마다 `qfile_open_list` 로 리스트를 새로 여는데, `qmgr_create_new_temp_file` 이 리스트마다 `temp_mem_buffer_pages`(기본 4페이지, 64KB) membuf를 미리 잡는 것으로 알고 있습니다. 그래서 `chunk_bytes` 가 64KB보다 작아지면 내린 튜플보다 버퍼가 더 커지는 것 같습니다. release에서 자식 10만 개 star(튜플 약 13MB)의 피크 RSS가 상한 128M에서 566MB, 64K에서 869MB, 0에서 6843MB였습니다. 상한을 낮출수록 오히려 OOM에 가까워지므로, 청크 크기 하한을 membuf 크기 이상으로 두거나 파라미터 하한을 올려야 할 것 같습니다.

### 인라인 3 - src/optimizer/rewriter/query_rewrite_select.c:4049

`id` PK만 있는 테이블도 이제 해시 경로로 가면서, START WITH 루트가 PK 순서가 아니라 heap 순서로 나오는 것 같습니다. CTP `bug_bts_9613` 에서 아래 쿼리의 루트 순서가 1, 2, 3 에서 3, 2, 1 로 바뀌었습니다.

```sql
CREATE TABLE foo (a INT PRIMARY KEY, b INT);
INSERT INTO foo VALUES (4, 5), (3, 4), (2, 3), (1, 2);
SELECT a, b FROM foo START WITH a < 4 CONNECT BY PRIOR a = b;
```

develop에서 나오던 출력 순서가 바뀌는 것이라 유지되어야 할 것 같습니다. START WITH 쪽은 기존처럼 인덱스를 쓰고 자식 탐색만 해시로 하는 방법은 어떨까요?

### 인라인 4 - src/query/query_executor.c:20523

스필된 자식은 키를 뒤집어 정렬한 뒤 정방향으로 읽어서, 해시 경로가 아닌 경우(인덱스, heap)에는 키가 같은 형제의 순서가 메모리 경로와 반대로 나오는 것 같습니다. `pid` 인덱스가 있는 star 2000건에서 `ORDER SIBLINGS BY k`(k 동순위) 결과가 기본값에서는 develop과 같고, 상한 65536, 0 에서만 순서가 달랐습니다. 비해시 경로는 원래 키로 정렬한 뒤 역방향으로 읽으면 `qexec_connect_by_sort_siblings` 와 같은 순서가 될 것 같은데 어떨까요?

### 인라인 5 - src/query/query_executor.c:18326
