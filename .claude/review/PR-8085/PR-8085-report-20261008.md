## Findings

### Blocking (must fix)

- `src/optimizer/query_planner.c:3937` -- `qo_seg_has_unique_index ()`가 참이면 NDV를 행 수로 덮어쓴다. unique 인덱스는 NULL을 여러 개 허용한다(PK 컬럼만 NOT NULL). memoize는 NULL 키의 "결과 없음"도 저장해 재사용하므로(`storage::put_nullptr ()`), NULL이 많은 키에서 memoize를 생략하면 NULL 행마다 inner를 다시 읽는다 -> develop보다 느려짐.
  ```c
  if (qo_seg_has_unique_index (seg))
    {
      /* one value per row, whatever the sampled NDV says */
      seg_ndv = (double) QO_NODE_NCARD (node);
  ```
  재현 (Runtime Verification B1): `bx (id int primary key, u int unique)` 20000행 중 u의 90%가 NULL, inner `bi (k, v)` 500행에 인덱스 없음, `select /*+ ordered use_nl(i) */ count(*), sum(i.v) from bx x, bi i where i.k = x.u`.
  - develop (merge-base / 최신 `1386afc02`): MEMOIZE hit 17999 / miss 2001, bi readrows 1,000,500, 447 / 525 ms
  - PR head: MEMOIZE 없음, readrows 10,000,000, 4050 ms (memoize를 끈 3.89 s와 같음)

  `380d10ad9` 이전에는 표본 NDV(약 2000)가 행 수의 90%에 못 미쳐 판단하지 않았다. inner가 인덱스 scan이면 NULL 키 probe가 싸서 차이가 없다(B2 34 ms vs 37 ms). 수정 방향: `QO_SEG_IS_NOT_NULL (seg)`일 때만 행 수로 덮어쓴다(`qo_is_pk_fk_full_join ()`이 FK 컬럼에 NOT NULL을 요구하는 것과 같은 방식). NULL을 허용하면 기존 95% 규칙으로 판단하는 대안도 있다. 이 형태를 TC에 넣으면 수정이 고정된다.
