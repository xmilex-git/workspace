# CUBRIDSUS-9961 조사 — 클라이언트 캐스트 제거 시도와 PR #8022 비교

작성 2026-09-29. 대상 PR: CUBRID/cubrid#8022(CBRD-27510, draft). 머리는 `4abc28ea1`, develop 기준은 `e1c3db198`, 커밋 58개다.

## 0. 요약

- **9961 이 무엇이었나.** 클라이언트 파서는 대입·함수 인자·비교 자리의 식을 `CAST(식 AS 목표 타입)` 로 다시 써서 타입을 맞췄다. 9961(2012-12-10, 서경식)은 이 방식을 걷어내고 타입 변환을 서버가 실행 중에 하도록 바꾸려던 코드 개선 과제다. 이유는 셋이었다.
  - 유지보수가 어렵다.
  - 자잘한 오류가 계속 난다.
  - CAST 때문에 인덱스 스캔을 못 하는 등 성능 문제가 생긴다.
- **끝난 것은 대입 경로 둘이다.** INSERT … SELECT(11608, `d79e94fe2`)와 UPDATE … SET(11648, `926b67b90`)이다.
  - 두 경로의 변환은 서버로 옮겨갔다. 하나는 저장 시점(`heap_attrinfo_set`)이다. 다른 하나는 출력 튜플을 만들 때(`qdata_get_dbval_from_constant_regu_variable`)로, 행마다 값 타입을 보고 변환한다.
  - 의미 오류(-494)가 실행 오류(-181·-427 등)로 바뀌었다.
  - R9.3 에도 이식했다(12960·12961).
- **멈춘 것.** INSERT … VALUES(11749)는 2013-08-19 "영향 평가 이후"로 보류됐다. 계획의 2·3단계(함수 인자, 비교)는 시작하지 않았다. 9961 에 연결된 버그 34건 중 21건이 미해결로 남았다. 멈춘 이유는 셋이다.
  - 스펙(엄격/비엄격, MySQL 호환)은 "한 번에 정리"하기로 미뤘다.
  - 단계마다 기대 답이 30~45개씩 바뀌었다.
  - 회귀가 뒤따랐다(13817 등).
- **PR 8022 와의 관계.** 둘 다 "서버의 실행 쪽에서 정한다"는 방향이지만 옮기는 대상이 다르다.
  - 9961 은 목표 타입을 이미 아는 대입의 *변환*을 클라이언트 컴파일에서 서버의 행 처리로 옮겼다.
  - PR 은 컴파일 때 값이 없는 자리(호스트 변수·auto-param·세션변수)의 *도메인·collation 결정*을 옮긴다. 행·첫 값에서 정하던 것을 로드 도출과 실행당 1회 게이트로 옮긴다.
  - 곧 9961 은 "어디서(클라이언트 → 서버)"를, PR 은 "언제(행마다 → 실행당 한 번)"를 바꿨다.
- **당위성 근거.** 9961 기록 안에 PR 을 받치는 근거가 네 가지 있다.
  - 9961 조사 결론(2012-12-24)은 "당분간 스펙은 유지하고 구현을 정리한다"였다. PR 의 원칙("답은 develop 과 같다")과 같은 태도다. 9961 은 스펙 논쟁과 답 변경량에서 멈췄는데, PR 은 그 두 지점을 피했다.
  - 11848(2013)은 "값을 보는 시점에 판단하되, SELECT 는 목표 타입이 없어 어렵다"는 숙제를 남겼다. 게이트 슬롯이 이 숙제를 푼다.
  - 9961 은 행마다 타입 검사를 남겼고, 2014년 9490 은 그 비용을 줄이려고 제자리 1회 변환과 실행 중 상수 표시를 더했다. PR 은 이 둘을 로드 도출과 실행 소유 값으로 바꿨다.
  - 9490 은 "한 호스트 변수는 한 자리"라고 가정했다. PR 은 그 가정의 반례를 찾아 참조별 자리로 풀었다.
- **PR 이 하지 않는 것.** 9961 의 본래 목표인 클라이언트 CAST 재작성 제거는 이어가지 않는다.
  - INSERT … VALUES 의 CAST 감싸기, 바인드 값의 클라이언트 캐스트(ADR 0021 정정, D-335-08), 비교에서 컬럼을 감싸는 CAST(인덱스 문제)는 그대로다.
  - 오류 시점은 둘로 갈린다. DML 대입은 develop 처럼 행 시점이다(11686 과 같은 원칙). 반면 상수 실패와 타입 조합 거부는 행이 없어도 실행 전 오류로 당긴다. 이것은 9961 시절 MySQL 식 관대함과 반대 방향이다.

## 2. 9961 은 왜 시작됐나

### 2.1 이슈 본문 (2012-12-10)

동기:
- client-side explicit casting 이 너무 많다.
- 코드 유지 보수가 어렵다.
- 자잘한 오류가 계속 발생한다.
- 성능 이슈가 생기는 경우가 있다(cast 때문에 index scan 안 됨 등).

목표는 client-side explicit casting 을 최대한 제거하고, 가급적 run-time 에 server-side casting 으로 처리할 수 있는지 검증하는 것이다. 조건이 둘 붙었다.
- 성능 저하가 없어야 한다.
- 타입 변환 설계 사상을 단순하고 직관적으로 만든다.

### 2.2 근거가 된 버그

2012-12 에 서경식이 check-in 테스트 답안을 MySQL 5.5 와 대조하면서 "[MySQL 호환성]" 버그를 한꺼번에 등록했다. 이동현이 선별(2012-12-17)에서 이들을 "casting 이슈들을 같이 확인해서 진행할 것 (CUBRIDSUS-9961)"로 묶었다. 성격별로 넷으로 나뉜다.

**(가) 클라이언트가 씌운 CAST 가 답을 바꾼 것 — 9961 의 직접 근거**

```sql
-- 10036: 선택 목록이 cast(concat(x, 'b') as char(2)) 로 바뀌어 오류 없이 잘린다
create table bar (x char(2));
insert into bar values ('aa');
insert into bar select concat(x, 'b') from bar;

-- 10060: values 가 cast(b'11111' as bit(4)) 로 바뀌어 잘린다
create table t (b bit(4));
insert into t values (b'11111');

-- 11510: 시스템이 씌운 CAST 때문에 orderby_num() 이 계산되지 않아 rank 가 0
insert into tt (rank, id, score)
  select orderby_num() as rank, id, score from (...) a order by score desc;
```

- 10036·10060 의 원인 분석(서경식): "client-side에서 강제로 query rewrite 하는 방식은 이와 같이 risk 있기 때문에 다른 방식이 필요하다."
- 12031: INSERT/UPDATE 의 정렬 열을 CAST 로 감싼 탓에 정렬 비교가 경계 밖을 읽었다(valgrind). 9.2·R4.x 는 패치했다. trunk 는 "이미 casting 하지 않도록 변경했으므로" 적용하지 않았다(오이석 2013-08-13).
- 10171: 같은 17자리 수가 클라이언트 INSERT(`cast(… as numeric)`)에서는 오류이고, 서버 INSERT … SELECT 에서는 성공했다.
- 11724: `sum(?) over (partition by i1)` 에 문자 바인드를 주면 -181 이 났다. 서경식은 "Please do not use client-side CAST rewrite method"라고 적었다.

**(나) 행이 없어도 컴파일에서 나는 오류 — 오류 시점 문제**

```sql
-- 11686: 빈 테이블인데 9.x 부터 오류. R4.x 와 MySQL 은 0행 성공
create table foo (i int, dt datetime);
update foo set i = dt;
```

- 11686 의 기대 결과는 "update 문이 갱신할 때에만 type 변환 오류가 발생하도록"이었다.
- 10042·11754: 트리거를 생성할 때 타입 검사를 해서 생성이 실패했다. 서경식은 "trigger 수행시에 실제로 insert를 수행할 때 value를 casting 하면서 에러 검사해야 겠다"고 적었다.
- 9972·10010: `where a = 'aaa'`(a 는 int), `where datetime_col = 'nhn cubrid db'` 가 컴파일에서 오류(-494)였다. MySQL 은 0행이다.

**(다) 인덱스**

- 10272: `char_col = id` 가 `cast(char_col as double)` 로 바뀌어 인덱스를 못 쓰고 오류까지 났다. 서경식은 "type casting 때문에 index scan이 불가해지는 경우가 발생하는데, 이는 장애 risk가 될 수 있다"고 적었다.

**(라) 스펙**

- 숫자↔날짜 변환: 10006·10042·10065·10068·10337.
- BIT 변환: 10061~10064.
- 엄격/비엄격: 9493·10036·10915·11757·11763·11896.

### 2.3 조사 결론 메일 (2012-12-24, 파트장 대상)

스펙 관점에서 문제는 둘이었다.
- CUBRID 는 number↔date 변환을 어떤 방식으로도 지원하지 않는다. MySQL·ORACLE·SQL Server 는 각자의 규칙으로 지원한다.
- INSERT/UPDATE 는 옛 MySQL 호환 때문에 no_strict 가 기본이다. 그런데 MySQL 은 strict 로 바꿀 것 같다. 두 모드를 다 지원하는 것에는 반대한다(현재 코드 구조와 QA 비용 때문).

구현 관점에서도 문제는 둘이었다.
- type conversion 루틴이 client·server 모두에 흩어져 있어 유지 보수가 어렵다.
- client 에서 cast 로 rewrite 하는 방식은 index scan 을 무효화할 위험이 있어, 성능 관점에서도 가장 buggy 한 부분이다. parse tree rewrite 는 모두 제거하는 것이 좋다.

그래서 기본적으로 type conversion 은 server 에서 run-time 에 수행하도록 정리하는 것이 좋다고 보았다. semantic error 가 run-time error 로 바뀌는 경우가 많을 것이라는 점도 적었다.

결론(원문 요지):
> 벤더마다 고유 철학이 있어 특정 제품의 spec 만 따라갈 필요도 없고 그럴 수도 없다. **당분간은 현재 제품에 들어있는 spec 을 유지하면서 구현을 안정화, 코드 정리하는 방향**이 좋아 보인다. 단 (cast rewrite 제거 포함) 코드 정리는 매우 시급하다. banana 를 시작하면서 작은 업무 단위로 꾸준히 반영한다. spec 을 다시 검토한다면 ORACLE 방식(implicit 은 보수적으로, explicit 은 강력하게)이 가장 직관적이다.

### 2.4 단계 계획 (2012-12-21)

- 대입(INSERT/UPDATE)
  - rvalue 가 literal — 1단계
  - rvalue 가 non-literal — 2단계
  - strict/no_strict 지원 여부 — 4단계(??)
- 함수 인자·반환 값
  - 인자가 literal — 1단계
  - 인자가 non-literal, 반환 타입 결정 — 2단계
- 관계 연산
  - literal vs literal — 1단계
  - non-literal vs literal, non-literal vs non-literal — 3단계

실제로 들어간 것은 대입의 non-literal 중 두 경로(INSERT … SELECT, UPDATE … SET)뿐이다.

## 3. 무엇을 했나

### 3.1 INSERT … SELECT — 11608 (`d79e94fe2`, 2013-07-01, trunk r31608)

변경:
- `pt_coerce_insert_values` 에서 `pt_cast_select_list_to_arg_list` 호출을 뺐다. 이 호출이 SELECT 선택 목록에 CAST 를 씌우던 곳이다.
- dev_fbo(rev 7132) 때 들어온 strict_cast 개념을 지웠다. `TP_STRICT_COERCION`, `tp_value_strict_cast`, 그리고 LOB 변환만 막던 조건이다. 지운 이유는 "현재의 type 시스템 철학과 배치"였다.
- 11510 의 임시 수정(`f4744f092`, `CAST(orderby_num())` 특수 처리)을 되돌렸다. 오이석의 지시는 "cast를 씌우지 않는다면 그 수정은 더 이상 의미가 없다"였다.
- 서버 `heap_attrinfo_set` 이 속성 도메인과 다른 값을 `tp_value_auto_cast` 로 바꾸고, 실패는 `tp_domain_status_er_set` 으로 알린다.
  - 이전 주석은 "we really shouldn't get here on the server, the coercion rules should have been checked by now"였다. 서버는 클라이언트가 이미 맞췄다고 가정하고 있었다.

부작용: check-in 에서 33건이 실패했다.
- 29건은 오류 코드 변화다(-454→-181, -494→-181, -454→-427). 서경식은 "semantic 오류가 run-time 오류로 … (제가 보기에는 바람직한 방향으로)"라고 적었다.
- 4건은 오류가 나던 것이 성공으로 바뀌었다(11622, `ifnull(int, clob)`).

### 3.2 UPDATE … SET — 11648 (`926b67b90`, 2013-07-11, trunk r32285)

변경:
- `pt_cast_select_list_to_arg_list` 를 지웠다. `pt_check_assignments` 는 이제 CAST 를 씌우지 않고 객체 클래스 호환만 본다(`pt_assignment_class_compatible`).
- `pt_eval_expr_type` 의 PT_ASSIGN 에서 우변을 좌변 타입으로 `pt_coerce_value` 하던 검사를 뺐다.
- 서버 `qdata_get_dbval_from_constant_regu_variable`(출력 튜플 값을 만드는 곳)에 코드를 넣었다. **행마다** 값 타입과 regu 도메인을 비교하고, 다르면 `tp_value_auto_cast` 한다.
  - 분석 창 중간 목록은 `REGU_VARIABLE_ANALYTIC_WINDOW` 로 제외했다.
  - 이유는 기존 AVG 답을 보존하기 위해서다. 원 도메인으로 합산한 뒤 DOUBLE 로 바꾸는 방식과 먼저 바꿔 합산하는 방식은 소수점 아래 10자리 이하에서 값이 다르다.
- `fetch_peek_arith`·`qdata_*_dbval` 의 변환 호출을 `tp_value_auto_cast` + `tp_domain_status_er_set` 으로 바꿨다. UPDATE 상수 대입(`pt_to_update_xasl`)도 같은 변환을 쓴다.
- 새 코드가 파서 밖에서 식을 만들 수 있도록 `parser_make_expression` 에 parser 인자를 추가했다. 문법 파일의 변경은 이 기계적 변경이다.

결과: 11686 이 해결됐다(빈 테이블 UPDATE 가 0행 성공).

부작용: medium 4건과 sql 29건이 추가로 실패했고, 거의 전부 오류 코드 변화였다.
- -494 가 -181·-553·-458·-552·-214·-427 로 바뀌었고, 한 건은 0행 성공이 됐다.
- serial.next_value 가 한 번 더 증가하는 답 변화가 1건 있었다(의미 오류가 실행 오류로 바뀌어서).

### 5.3 9961 기록이 PR 의 당위성을 받치는 지점

1. **태도가 같다.**
   - 2012-12-24 결론은 "당분간 현재 spec 을 유지하면서 구현을 안정화, 코드 정리"였다. PR 의 P0 도 "전부 develop 과 동일 작동, domain 만 gate 에서"(D-336-A)다.
   - 9961 은 실행 단계에서 MySQL 호환·엄격 모드 같은 스펙 질문으로 번졌고, 거기서 멈췄다(§4).
   - PR 은 스펙 변경을 표 하나로 가두고 항목마다 승인을 받았다.
2. **흩어진 결정을 모은다.** 9961 이 적은 "루틴이 흩어져 유지보수가 어렵다"를, PR 은 서버 쪽에서 세 가지로 줄인다.
   - 결정 지점 2곳(컴파일·게이트).
   - 서버 격자 한 모듈(`domain_resolver`).
   - 변환 의미 한 벌. `tp_value_cast_internal`·`tp_value_coerce_strict` 와 같은 셀 함수를 쓴다(ADR 0022). 셀 함수는 변환 상태만 돌려주고 오류는 실패 정책을 아는 호출자가 낸다. 10024 가 `tp_domain_status_er_set` 으로 변환 상태와 오류 코드를 나눈 것과 같은 분리다.
3. **"성능 저하 없도록"을 채운다.**
   - 9961 은 변환을 행으로 옮기면서 행마다 타입 검사를 남겼다(`qdata_get_dbval_from_constant_regu_variable`).
   - 9490 은 비교 자리의 호스트 값을 첫 행에서 제자리 변환하는 것으로 이를 덜었다.
   - PR 은 결정을 실행당 1회로 모으고, 행에서는 고정된 변환기만 부른다(PR 본문의 벤치 표).
4. **11848 의 숙제를 푼다.**
   - 숙제는 "값을 보는 시점에 판단하라, 그런데 SELECT 는 목표 타입이 없어 어렵다"였다.
   - 형제가 타입을 못 정하는 `SELECT ?`, `? + ?`, `sum(?)` 같은 자리를, PR 의 게이트 슬롯이 바인드 값의 타입으로 실행당 1회 정한다(ADR 0019).
   - 기본형(DOUBLE/VARCHAR)을 강제하는 안은 답을 바꾸므로 기각했다.
5. **9490 의 가정과 그 결함을 정리한다.**
   - "한 호스트 변수는 평가 트리 한 자리"라는 가정은 성립하지 않는다. 등식 축약(`a = ? AND a = b` → `b = ?`)과 UNION 가지 푸시다운이 같은 바인드를 서로 다른 형제 옆에 복사한다(#323 탐침).
   - PR 은 바인드 값을 실행당 1회 두고, 참조마다 자리와 변환기를 따로 둔다(ADR 0021).
   - 제자리 변환이 만들던 결함 둘도 없어진다.
     - `cbrd_24598`: 앞 실행의 INT 바인드가 캐시된 XASL 리터럴을 바꿔, 다음 실행이 실패했다. TC 가 "known bug"로 적어 둔 자리다(스펙 변경 §3).
     - L-46: 연결 스레드가 만든 값을 PX 워커가 해제해 교차 mspace free 가 났다.
   - 실행 중 플랜에 쓰던 `REGU_VARIABLE_FETCH_ALL_CONST`/`NOT_CONST` 는 로드 때 정하는 피연산자 부류(상수·행·상관·휘발)로 바뀌었다(`e2b57afe0`, #352). 9490 이 휘발 함수를 상수로 잘못 봐서 뒤따라 고친 일(sleep, serial, sys_guid)을 로드 도출이 구조로 막는다.
6. **static 과 dynamic 을 맞춘다(상수 실패의 시점에 한해).**
   - 352(2009)·11757·11763 은 "같은 질의면 리터럴이든 바인드든 같은 동작"을 요구했다.
   - PR 은 상수(리터럴·바인드·상수 부분트리)의 계산·변환 실패를 모두 실행 전 오류로 맞춘다(스펙 변경 §10). 2012 기록(9972·10010)을 보면 리터럴은 원래 컴파일에서 오류였다.
   - 다만 11757·11763 의 대입 절단 차이는 DML 대입이라 PR 이 다루는 모양이 아니다(실측 없음).
7. **결정 위반을 숨기지 않는다.**
   - 9961 의 회귀(11685 assert, 13817 원자성)는 결정 위치가 바뀌면서 생긴 틈이었다.
   - PR 은 세 가지로 틈을 드러낸다. 플랜 불변(결정은 `XASL_STATE` 에만), 로드·실행 경계 오류 -1383, optdebug assert 다.

  - 지금 남는 이유는 이 객체 바인드와, 클라이언트 캐스트가 develop 규칙(반올림 등) 그대로의 답을 내는 자리라는 점이다.

  - 상수 계산·변환 실패(§10).
  - 연산자가 받지 않는 타입 조합(§1).
  - 집합 연산 가지 타입 불일치(§5).

```sql
-- 스펙 변경 §10 의 예. ce_e 는 빈 테이블
prepare q from 'select a, a + concat(?, '''') from ce_e';
execute q using 'abc';
-- develop: 0행 / PR: -181
```

- 상수 조건이 막는 가지는 develop 답을 유지한다(D-367-07).
- 이 방향은 사용자 결정이다(D-335-02, #367 (가), D-341-14).
- 리뷰에서 "9961·11686 과 반대 아니냐"는 질문이 나오면 이렇게 답할 수 있다.
  - 대입은 같고 상수만 당겼다.
  - 이유는 결정성이다. 행 수, 힙 순서, 첫 값에 따라 오류가 났다 안 났다 하지 않는다.

**MySQL 호환 버그 21건은 PR 로 풀리지 않는다.**
- PR 은 답을 지키므로 이 이슈들을 고친다고 볼 근거가 없다.
- 스펙 변경 표에 해당하는 모양이 아니면 develop 답 그대로다.

### 5.5 9961 에서 가져올 확인 항목

- **오류 위치 이동과 원자성.**
  - 13817 은 오류가 나는 함수가 바뀌면서 savepoint 조건을 빠져나간 경우다.
  - PR 은 오류를 실행 전(게이트)으로 당기는 쪽이라 부수효과 전에 멈춘다.
  - 그래도 트리거·serial·다중 테이블 UPDATE·MERGE 에서 게이트 오류가 원자성 경로를 거치는지는 볼 만하다.
- **드라이버 메타.**
  - 8182 처럼 호스트 변수 노드에 타입 정보가 없으면 드라이버의 파라미터 타입이 0 으로 보고된다.
  - ADR 0021 에 따르면 `host_var_expected_domains[]` 는 prepare 응답 메타로 남고, 게이트가 정한 `SELECT ?` 열 메타는 실행 응답의 컬럼 정보로 갱신된다. 드라이버 쪽 동작은 이 조사에서 따로 확인하지 않았다.
- **브랜치 사이 차이.**
  - 13005 처럼 한 브랜치만 받으면 오류 코드가 갈린다.
  - PR 에는 새 오류 코드(-1383·-1384)와 실행 전 오류로의 시점 변화가 있다. 백포트 여부를 따로 정해야 한다.
- **답안 관리.**
  - 9961 은 단계마다 답을 수십 개씩 갱신했다.
  - PR 은 CTP 전수 통과, 스펙 변경 문서, TC 변경 설명으로 관리했다.

## 6. PR·JIRA 배경 문단 초안

> 2012년 CUBRIDSUS-9961 은 클라이언트가 CAST 로 질의를 다시 써서 타입을 맞추는 방식이 조용한 오답, 행이 없어도 나는 오류, 인덱스 손실을 낳는다고 보고, 타입 변환을 서버 실행 시점으로 옮기기 시작했다(INSERT … SELECT, UPDATE … SET). 그 결과 서버 실행 경로에는 값 타입을 보고 행마다 도메인을 정하고 변환하는 코드가 늘었다. 2014년 CUBRIDSUS-9490 은 그 비용을 줄이려고, 호스트 변수 값을 첫 비교에서 제자리 변환하고 실행 중 플랜에 상수 표시를 남겼다(한 호스트 변수는 한 자리에서만 쓰인다는 가정). 이 PR 은 서버 실행 쪽에서 정한다는 방향을 유지하되, 결정을 행이 아니라 실행 전 한 번으로 모으고 플랜은 바꾸지 않는다. 9961 의 조사 결론처럼 답(스펙)은 develop 과 같게 두고 구현 구조만 정리한다.

## 7. 확인하지 않은 것

- 2012~2013 재현 SQL 을 현재 develop 과 PR 머리에서 돌리지 않았다. 대상은 9972, 10010, 10036, 10060, 10171, 10272, 11686, 11697·11699, 11724, 11757, 11763, 11848, 13411 등이다. 로컬에는 PR 머리의 설치본이 없다. 확인하려면 두 빌드를 만들어 SA 로 한 번에 돌린다.
- R9.3·R9.2·R4.x 이식 커밋의 내용은 git 에 없어 JIRA 기록으로만 보았다.
- 2015년 이후 CBRD 에서 클라이언트 CAST 재작성이 원인인 버그를 따로 모으지 않았다.
