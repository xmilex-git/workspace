## 4. SET TRACE — 플랜·병렬도·임시 페이지 동일성 (Q01/02/04/06, A vs B)

`trace-A.out` / `trace-B.out`(문장1 웜업 → `SET TRACE ON` → 문장2 트레이스). 4종 전부:

- **플랜 구조 동일**(조인 방법·스캔 순서·집계 방식 변화 없음).
- **병렬 워커 수 완전 동일** — grep `parallel workers: N` 결과 A/B diff 없음(전부 workers=2, threshold=0 강제 병렬이므로 당연).
- **임시 리스트 페이지 수(`page:`) 완전 동일** — Q01/Q04 GROUPBY `page: 1`, Q02 ORDERBY `page: 0`, 5개 지점 전부 A=B.
- `heap time`/`fetch` 등 카운터는 `fetch`(페이지 접근 횟수)가 A/B 완전 동일(예: Q01 lineitem 스캔 `fetch: 682950` 양쪽 동일)한 반면 `heap time`(ns)만 수백~수천 단위로 흔들려 — 이는 호스트 스케줄링 잡음이며 페이지 접근 패턴 자체는 무관함을 보여준다.

D-193-5 유형의 "페이지 수 기반 병렬도 차이"는 이 8종에서 **재현되지 않았다**(parallelism=2 + 임계값 4종 모두 0 으로 강제 병렬이라, 병렬도 자체가 페이지 수 판정에 좌우되지 않는 conf 이기 때문 — #193 은 parallelism=6·기본 임계값 2048 조건이었다).

## 5. 결론

8종(Q01,02,03,04,06,07,11,15) **전부 NOISE** 로 판정한다. 근거:

1. 4문장 세션 median 재측정에서 Q03/Q15 는 방향이 역전(B 가 더 빠름), Q07/Q11 은 동률, Q01 은 사전측정 108%→100.5%로 소멸.
2. 남은 경계값 3종(Q02/Q04/Q06, 105~120%)도 **완전히 독립적인 3번째 단발 재측정**(perf 캡처와 동시 수행)에서 전부 ±2% 안으로 수렴했고 Q06 은 오히려 B 가 8.7% 빠르게 나왔다 — 즉 §2 의 경계값 자체가 단일 표본의 흔들림이었다.
3. Q01/02/04/06 perf 프로파일 상위 10개 자기시간 심볼에 PR 심볼이 **전혀 없다**. `qfile_` 계열 심볼은 percent-limit 없이 찾아도 4종 전부 0~0.5%. 지배 비용은 heap 스캔/`eval_pred`/집계로 PR 과 무관한 develop 공통 코드다.
4. SET TRACE 로 확인한 플랜·병렬 워커 수·임시 리스트 페이지 수가 4종 전부 A=B — 페이지 수 기반 병렬도 차이(#193 의 원인)도 이 conf(강제 병렬, threshold=0)에서는 발생하지 않는다.
5. 8종 전부 결과 바이트 완전 동치.

**코드 레벨 원인 가설 없음** — 8종 모두 애초에 PR 이 재설계한 임시 리스트 튜플 조립/비교 경로를 거의 실행하지 않거나(Q01/06: 0%), 실행량이 노이즈 이하(Q02/04: <0.5%)이므로 `qfile_tuple_layout.c`/`list_file.c`/`external_sort.c`/`query_executor.c` 어느 쪽에서도 회귀를 지목할 근거가 없다. 사전 단발 측정에서 관측된 106~137% 편차는 이 공유 호스트의 I/O·스케줄링 잡음(±30% 폭, #193 §3 각주와 동일 현상)으로 귀속한다.

**후속 제안**: 이 8종의 판정은 확정하되, PR 의 튜플 포맷이 실제로 지배적 비용이 되는 질의(대형 정렬/DISTINCT/analytic sort — #193 M1~M4, S1~S3 계열)에 대한 회귀는 이미 #193/#200 에서 별도로 측정·수정(D-193-4 비교자 fast path, D-200-10 조립기 정정)되어 있으므로 이 티켓 범위에서는 추가 조치가 필요 없다고 판단한다.
