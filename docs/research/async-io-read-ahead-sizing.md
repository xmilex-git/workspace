# 비동기 읽기의 앞서 읽기 크기와 io_uring 사용 지침 (2026-11-10 조사)

async-io 설계(`docs/tla/CBRD-28005/`) 그릴링 중 "한 번에 200MB쯤 요청해야 효과가 있지 않나, PostgreSQL은 어떻게 돼 있나, 다룬 논문이나 조사가 있나"에 답하려고 모았다. 각 항목 끝이 출처다.

## PostgreSQL의 앞서 읽기 크기 (`~/dev/postgres` b0392c26bd3)

- 한 스트림이 붙잡는 버퍼 상한: `max_pinned_buffers = (max_ios + 1) * io_combine_limit` (`src/backend/storage/aio/read_stream.c`, `read_stream_begin_impl`).
- 기본값: `effective_io_concurrency = 16`, `io_combine_limit = 128KB`(8KB 블록 16개) (`src/include/storage/bufmgr.h:170,176`). 그래서 기본 상한은 17 × 16 = 272블록 ≈ **2.1MB**다.
- 최댓값: `effective_io_concurrency` 1000, `io_combine_limit` 1MB(`io_max_combine_limit`, `PG_IOV_MAX`). 이론상 약 1GB지만 backend당 pin 한도(`GetPinLimit`, shared_buffers의 몫)와 접근 전략의 한도(`GetAccessStrategyPinLimit`)로 잘린다 (같은 함수).
- 거리(앞서 읽는 깊이)는 1에서 시작해 I/O를 기다렸을 때만 늘리고 적중이 이어지면 줄인다 (`read_stream.c`, 커밋 f63ca337902 "Only increase read-ahead distance when waiting for IO").
- 큰 테이블 순차 스캔은 버퍼 풀을 채우지 않는다: 테이블이 `NBuffers / 4`보다 크면 `BAS_BULKREAD` 전략(작은 ring의 버퍼를 스캔이 재사용)을 쓴다 (`src/backend/access/heap/heapam.c:398-410`). ring은 256KB에서 시작해 I/O 동시성만큼 키운다 (`src/backend/storage/buffer/freelist.c:444-480`).
- buffered I/O에서 io_uring은 페이지 캐시에 있는 데이터를 submit한 프로세스가 직접 복사한다. 그래서 큰 읽기(4블록 이상)나 진행 중 I/O가 4개를 넘으면 `IOSQE_ASYNC`로 커널 워커에 넘겨 복사를 병렬화한다 (`src/backend/storage/aio/method_io_uring.c` `pgaio_uring_should_use_async`, 커밋 a9ee6688174).

## 이 개발 호스트의 장치 (2026-11-10)

- `/home`: Samsung SSD 990 PRO 4TB, xfs. `max_sectors_kb = 1280`(요청 하나가 1.28MB를 넘으면 블록 계층이 쪼갠다), `nr_requests = 1023`, `read_ahead_kb = 4096`(OS readahead가 순차 buffered 읽기를 4MB 앞서 읽는다).

## 조사와 논문

- Jasny, El-Hindi, Ziegler, Leis, Binnig, "High-Performance DBMSs with io_uring: When and How to use it", PVLDB 19(9), VLDB 2026. https://arxiv.org/abs/2512.04859
  - io_uring을 그대로 끼워 넣으면 이득이 작다(버퍼 매니저에서 libaio 대비 1.06배). 구조를 맞추면(비동기 실행, 배치, 등록 버퍼) 2.05배다.
  - 지침 네 가지: (1) I/O가 병목인지 먼저 확인한다. (2) 구조를 io_uring에 맞춘다(I/O와 계산 겹치기, 배치, 스레드당 ring). (3) 실행 모드를 고른다: `DEFER_TASKRUN` + single issuer를 권장하고, io 워커로 떨어지는 것을 피한다. (4) 등록 FD, 고정 버퍼 같은 최적화를 쓴다.
  - 배치 16개만 돼도 연산당 CPU 사이클이 5~6배 줄지만, 지나친 배치는 대기 지연을 만든다. 그래서 진행 중 I/O 수에 맞춰 배치 크기를 조절한다(adaptive batching).
  - PostgreSQL 18 사례: ring을 다른 프로세스가 대신 처리하는 구조라 `DEFER_TASKRUN`을 못 쓰고 차선인 `COOP_TASKRUN`을 쓴다. 지침을 적용해 14% 개선. 측정은 32GiB 콜드 테이블을 **direct I/O**로 스캔한 것이다.
- Tomas Vondra, "Tuning AIO in PostgreSQL 18". https://vondra.me/posts/tuning-aio-in-postgresql-18/
  - 순차 스캔은 `worker`가 가장 빠르고(sync와 PG17의 약 2배) `io_uring`은 그 사이다. 차이 약 20%는 체크섬 검증과 shared buffers로의 복사를 io_uring에서는 backend 혼자 하고 worker에서는 워커들이 나눠 하기 때문이라고 설명한다.
  - 인덱스 스캔은 아직 AIO를 쓰지 않아 차이가 없다.
- PGConf.EU 2025 발표 자료는 순차 스캔 15~25% 개선을 보고한다(2차 자료, 방법 미확인). https://www.postgresql.eu/events/pgconfeu2025/sessions/session/7008/slides/754/pg18-performance-talk-present.pdf

## 설계에 주는 뜻

- "한 번에 200MB"는 요청 하나로는 의미가 없다(장치가 1.28MB로 쪼갠다). 의미 있는 양은 **진행 중인 바이트 = 동시 I/O 수 × 요청 크기**이고, 필요한 양은 대략 (스캔의 소비 속도) × (I/O 지연)이다. 지연이 큰 저장소(네트워크 디스크, RAID)일수록 커진다.
- 진행 중인 프레임은 victim이 될 수 없다(C1). 200MB는 16KB 프레임 12,800개이고 병렬 워커 수만큼 곱해진다. 그래서 상한은 버퍼 크기의 몫으로도 잘라야 한다(PostgreSQL의 pin 한도).
- buffered I/O(D2)에서는 페이지 캐시 → 버퍼 복사를 누가 하느냐가 순차 스캔 속도를 가른다. `IOSQE_ASYNC`를 쓸지는 측정 항목이다.
- 논문이 권하는 `DEFER_TASKRUN`은 D3(기다리는 스레드가 대신 완료 처리)와 함께 쓸 수 없다. 발행자만 완료 처리하는 구조는 TLC 반례로 기각했다(`AsyncRead.mutant-owner-only`). PostgreSQL처럼 `COOP_TASKRUN`이 차선이다.

## I/O 상한 측정 (2026-11-10, 이 개발 호스트)

도구: `.git_ignored_dir/scratch/aio-bench/ioceil_mt.c`(8GB 파일을 16KB 페이지로 읽고 페이지마다 합을 구한다. 스레드는 한 fd를 같이 쓰고 각자 자기 구간을 읽는다. 매 실행 전에 그 파일의 페이지 캐시만 `POSIX_FADV_DONTNEED`로 비운다). 호스트: 커널 6.9.4, Samsung 990 PRO, xfs, `read_ahead_kb = 4096`, 32코어, 측정 중 load average 13~65(다른 세션과 TLC가 같이 돌았다). 수치는 한두 번 잰 값이고 편차가 크다.

| 방식 | 스레드 | 깊이 / 요청 크기 | 처리량 | 프로세스 CPU |
|---|---|---|---|---|
| 동기 pread, 파일 순서 (OS readahead) | 1 | - | 2.3~2.8 GB/s | 2.8~3.4 s |
| 동기 pread, OS readahead 끔 (`FADV_RANDOM`) | 1 | - | 0.45 GB/s | 8.8 s |
| 동기 pread, OS readahead 끔 | 4 | - | 0.88 GB/s | 8.6 s |
| io_uring | 1 | 2.1MB / 128KB | 0.9~1.9 GB/s | 3.8~9.3 s |
| io_uring + `IOSQE_ASYNC` | 1 | 2.1MB / 128KB | 2.6~2.9 GB/s | 3.3~4.2 s |
| io_uring + `IOSQE_ASYNC` | 1 | 200MB / 128KB~1MB | 2.9~3.1 GB/s | 8.8~11.9 s |
| 동기 pread | 4, 8 | - | 2.9~3.0 GB/s | 3.8~4.1 s |
| io_uring (+`IOSQE_ASYNC`) | 4, 8 | 2.1MB / 128KB | 2.9~3.0 GB/s | 2.9~3.8 s |
| io_uring + `IOSQE_ASYNC` | 4, 8 | 200MB / 128KB | 3.1 GB/s | 11.6~15.3 s |

페이지당 계산을 8배로 늘려 스캔이 CPU에 묶이게 하면(동기 745 MB/s): 동기 11.5 s, io_uring+`IOSQE_ASYNC` 2.1MB 9.95 s(-14%), 200MB 10.1 s(CPU 19.2 s).

읽을 수 있는 것:

- 이 호스트에서 콜드 buffered 읽기는 방식과 스레드 수에 상관없이 약 3 GB/s에서 멈춘다. 파일 순서로 읽는 동기 스캔은 OS readahead(4MB) 덕에 이미 그 80~90%다.
- `IOSQE_ASYNC` 없는 io_uring은 스레드 하나일 때 동기보다 느리다. 페이지 캐시에서 버퍼로의 복사를 submit한 스레드가 하고, 커널의 순차 감지 이득도 줄어든다. Vondra의 관찰과 같다.
- 깊이 200MB는 2.1MB보다 5~15% 빠르지만 CPU를 3~4배 쓴다(커널 워커의 복사). 스캔이 CPU에 묶이면 차이가 없다.
- 차이가 크게 나는 경우는 OS readahead가 듣지 않을 때다: 같은 장치에서 0.45 GB/s(1스레드) 대 2.5~3 GB/s. 힙 페이지가 파일 순서로 놓이지 않은 테이블의 체인 순서 스캔, readahead가 작은(기본 128KB) 장치, 지연이 큰 저장소가 여기에 든다.
- 아직 재지 않은 것: CUBRID 자체의 콜드 풀 스캔이 지금 몇 MB/s로 읽는지. 이 값이 상한(약 3 GB/s)보다 훨씬 낮으면 병목은 I/O가 아니라 페이지당 계산이다.

## PostgreSQL에서 인덱스가 이끄는 힙 읽기 (`~/dev/postgres` b0392c26bd3)

- 일반 index scan은 read stream을 쓰지 않는다. `read_stream_begin_relation` 호출은 `heapam.c`(순차 스캔, bitmap heap scan)와 `nbtree.c`(VACUUM)뿐이다. 인덱스 순서로 한 행씩 힙을 동기로 읽는다.
- bitmap heap scan은 힙을 읽기 전에 TID 비트맵을 통째로 만든다(`nodeBitmapHeapscan.c:108` `MultiExecProcNode`). 그 뒤 `heapam.c` `bitmapheap_stream_read_next`가 비트맵에서 블록 번호를 순서대로 꺼내 read stream에 준다.
- 병렬 bitmap heap scan은 한 프로세스만 비트맵을 만들고(`BM_INITIAL -> BM_INPROGRESS -> BM_FINISHED`), 나머지는 `ConditionVariableSleep`으로 기다린 뒤 공유 비트맵을 나눠 순회한다. Gather는 결과 행을 모을 뿐이다.

작업 트리 `CBRD-28005`를 origin/develop `e30370dc0` 위로 올린 release 빌드. 앞 절 뒤에 바뀐 것: 상한이 `index_scan_oid_bitmap_size`(기본 16MB, lineitem의 폭 186비트)가 됐고, 힙 단계가 표시된 페이지를 행을 읽기 전에 한 번 fix해 마지막 행까지 잡으며(`fix_bitmap_page`), 행 조회가 그 페이지를 다시 fix하지 않는다(`process_bitmap_row`). 질의와 조건은 앞 절과 같고 `read_ahead_hint=yes`, `bitmap_heap_scan=yes`, 파라미터는 기본값이다. 경우마다 콜드 1회와 핫 2회, 단위는 초, 콜드 / 핫. 스크립트와 출력: `.git_ignored_dir/scratch/aio-bench/tpch/ab-post.sh`, `ab-p2.log`, `ab-p2-*/`, `ssd-ab-p2-*/`.

| 장치 | 버퍼 | 1% (60만 행) | 10% (600만 행) |
|---|---|---|---|
| NVMe | 16GB | 3.49 / 0.46~0.53 | 4.42 / 2.01~2.02 |
| NVMe | 1GB | 3.36 / 2.06~2.55 | 4.31 / 2.81~3.09 |
| SSD | 16GB | 12.58 / 0.47~0.51 | 22.32 / 1.83~2.04 |
| SSD | 1GB | 12.47 / 2.37~2.56 | 22.28 / 2.40~2.71 |

- 질의 결과는 기존 경로의 실행과 같다(결과 줄의 md5: 1% `784a62d7`, 10% `a59b6637`, 0.1% `11579075`).
- 페이지 fetch 수가 행 수에서 페이지 수로 줄었다: 1%는 600,743에서 408,377, 10%는 6,000,257에서 720,232. 표시된 페이지를 한 번 fix하고 그 페이지의 행을 모두 읽기 때문이다.
- 읽은 페이지 수(ioread)는 앞 절과 같다(1% 408,372~408,373, 10% 720,225).
- 0.1%(6만 행)는 직렬 인덱스 스캔이라 비트맵이 쓰이지 않고 힌트만 든다: NVMe 0.73 / 0.11, SSD 1.85 / 0.12.
- SSD 1%가 앞 절의 27.4초(16GB), 24.2초(1GB)에서 12.6초, 12.5초가 된 것은 힙 단계의 힌트 규칙을 바꾼 결과다(전부 표시된 섹터만 뺌).
- 페이지 단위로만 표시하는 경로(`heap_next_1page`)는 행마다 페이지를 fix한다(같은 스레드가 이미 잡은 페이지). 이 경로는 손대지 않았다.

## 배치 조인 (2026-11-11, `nl_join_batch`)

작업 트리 `CBRD-28005`(push한 `4c4e04f7b` 위의 미커밋 배치 조인)의 release 빌드(`libcubrid.so.11.5` sha256 `f2f33a5a…`), TPC-H SF10, 버퍼 16GB, 병렬도 기본값. 각 칸은 콜드 1회 / 핫 2회(초)이고, 왼쪽은 `read_ahead_hint=yes`만, 오른쪽은 `nl_join_batch=yes`를 더한 것이다. 측정 중 호스트 부하(load average)는 15~18이었다. 출력: `.git_ignored_dir/scratch/aio-bench/tpch/ab-n3.log`.

| 질의 | 장치 | 힌트만 | 힌트 + 배치 조인 |
|---|---|---|---|
| Q7 | NVMe | 70.3 / 15.7~16.9 | 44.1 / 15.8~17.4 |
| Q7 | SSD | 116.0 / 15.9~17.5 | 63.1 / 16.5~17.1 |
| Q9 | NVMe | 22.3 / 8.4~8.7 | 22.4 / 8.2~9.3 |
| Q9 | SSD | 46.6 / 9.1~9.9 | 45.6 / 10.2 |
| Q20 | NVMe | 17.9 / 2.2~2.8 | 16.3 / 2.3~3.1 |

- 질의 결과는 두 설정에서 같다(결과 줄의 md5가 같고, 읽은 페이지 수도 같다: Q7 828,823, Q9 1,022,771, Q20 495,839).
- Q7(직렬 중첩 루프 6단계)이 대상이다. 콜드에서 lineitem 단계(`fk_lineitem_orders`, 읽기 636,925장)의 시간이 NVMe 54.9초에서 26.3초, SSD 96.4초에서 39.0초가 됐고, orders 단계(`fk_orders_customer`)는 NVMe 8.1초에서 6.1초, SSD 11.6초에서 6.3초가 됐다. 트레이스의 `nlbatch`: orders 120,405행, lineitem 1,083,879행, supplier 259행.
- lineitem 단계의 배치는 고객 한 명의 주문(약 10행, OID 약 40개) 단위로 닫힌다. 한 단계의 배치는 윗단계의 현재 행에 대한 바깥 행이 끝나면 닫히기 때문이다(단계 사이 연결 없음). 인덱스 리프 읽기는 그대로 한 번에 하나다.
- Q9와 Q20은 그대로다. Q9에서 읽기가 가장 많은 lineitem 조회(747,060장)는 병렬 리스트 스캔의 워커 안에서 첫 조인 단계로 돌고, 워커의 첫 조인 단계는 묶지 않는다(묶는 결정이 첫 스캔의 행 루프에 있고 워커는 그 루프를 돌지 않는다). Q20에서 읽기가 가장 많은 lineitem 조회(443,630장)는 조인이 아니라 상관 부질의다.
- 핫에서는 차이가 없다. 힌트할 페이지가 없던 배치 뒤에는 행 단위로 돌아가기 때문이다(Q7 핫의 `nlbatch`: orders 1,535행, lineitem 229행, supplier 91행). 이 back-off를 넣기 전 빌드의 Q7 핫은 20.3~20.9초였다(힌트만 14.6~15.6초, 같은 날 `ab-n1.log`).
- 서버 CPU 시간으로 본 Q7 핫(back-off 뒤, `ab-cpu.sh`): 힌트만 17.8~18.7초(부하 45~54), 배치 조인 14.7~16.5초(부하 23~26). 두 실행의 호스트 부하가 달라 차이로 읽지 않는다.
