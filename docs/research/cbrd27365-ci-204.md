## 2. 근본 원인

- `pt_eval_expr_type` 는 NULL 리터럴 인자를 받은 식의 타입을 `PT_TYPE_NULL` 로 둔다 → 출력 컬럼 도메인 `tp_Null`.
  `tp_Null` 은 `disksize 0`, 길이 함수 없음 → 새 레이아웃에서 **FIXED size 0** 컬럼.
- 서버 평가기 `T_DISK_SIZE` (fetch.c) 는 NULL 인자에 **bound INT 0** 을 만든다(4B).
- 라이터 size 패스가 FIXED 폭 불일치(4 != 0) 가드(`a2456c390`, #191 D-191-3 릴리스 폭 가드) 에 걸려 assert(디버그) /
  `ER_QPROC_INVALID_DATATYPE`(릴리스).
- develop 은 4B 본문을 그대로 쓰고 리더가 `tp_Null.data_readval`(아무것도 읽지 않고 NULL) 로 디코드 → 관찰 결과 NULL.
  즉 "NULL 도메인 컬럼의 저장 바이트는 결과에 영향이 없다" 가 기존 계약이다.

## 3. 수정 (D-204-1)

`src/query/qfile_tuple_layout.h`:
- `qfile_col_stores_null(c, v)` = `DB_IS_NULL(v) || c->type_id == DB_TYPE_NULL` 신설. NULL 도메인 컬럼은 평가기가 무엇을
  만들었든 NULL 로 저장(널비트) — develop 의 관찰 결과와 동일, 레이아웃이 기술할 수 없는 본문은 만들지 않는다.
- 적용 지점: `qfile_tuple_size`(src 배열 경로: `is_null` 을 true 로 승격 → fill 이 같은 플래그를 읽음),
  `qfile_tuple_size_from_values` / `qfile_tuple_fill_from_values`(f_valp 경로).
- 대안 기각: 타입체커에서 `disk_size(NULL)` 을 INTEGER 로 확정 — 답안(NULL) 이 바뀌고 다른 NULL 타입 식에는 무효.
