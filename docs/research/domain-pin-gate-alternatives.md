## 0. 한 장 요약

| 물음 | 답 |
|---|---|
| 어디가 느린가 | 게이트(G1)가 **실행마다** 하는 일 중 결정 자체가 아닌 것들: 임시 도메인 객체 생성·해제, 값 복사·해제, 목록 재검사. 그리고 B-tree 키 비교·행 비교의 **행마다 남은 타입·collation 검사**(develop 도 하던 것) |
| 왜 develop 보다 느린가 | 행이 하나인 문장에서는 develop 도 자리 수만큼 결정했다. 결정 횟수는 같고 **결정 한 번의 값**이 다르다: develop 은 타입 태그 비교 몇 번(수십 ns), 게이트는 도메인 객체·값 복사·기록 채우기(0.5~0.7µs) |
| 가장 직관적이고 빠른 구조는 | **"타입은 준비(첫 실행) 때 한 번, 값만 실행마다"** — 같은 바인드 타입 서명으로 다시 실행되면 앞 실행의 결정을 그대로 쓴다(§3 대안 A). PostgreSQL 이 이 모형이고 MySQL 은 서명이 바뀌면 재준비한다(#315). 게이트는 "서명 비교 + 값 변환"이 된다 |
| 그 전에 할 것 | 결정을 바꾸지 않고 하는 일만 줄이는 항목(§3 대안 C·D, #371 워커 A~C·D1·D3): 임시 객체 0, 복사 0, 행마다 검사 0 |
| 바인드 30개 기준 | 자리당 비용은 1/30 이 되고 **실행마다 한 번 드는 고정 비용**(상태 블록 할당·초기화·해제, 스코프 epoch, 키 결정 블록)의 몫이 커진다 — §2.3, 측정은 #371 진행 코멘트 |

## 2. 왜 "앞으로 끌어왔는데" 느린가 — 비용 모형

행 N, 자리 S(바인드가 낀 비교·산술·키), 실행당 develop 의 자리 결정 비용 d ≈ 30ns(타입 태그 비교·`tp_value_compare_with_error` 분기), 게이트의 자리 결정 비용 g.

- develop: 자리마다 행마다 → **N × S × d**. 행이 하나면 S × d.
- dpin(지금): 게이트 S × g + 행 N × S × r (r = 기록으로 비교, `cmpval` 직접, ≈ d/2 이하).
- g 는 측정으로 0.5~0.7µs = 20 × d. 그래서 N = 1 이면 **S × 20d** 대 S × d, N 이 커야 이긴다: 손익 분기 N ≈ g / (d − r) ≈ 40 행.

### 2.1 g 의 구성 (같은 프로파일에서)
| 몫 | 비율 | 없앨 수 있나 |
|---|---|---|
| 임시 도메인 객체 생성·해제 | ~24% | 있다 — `tp_domain_find_charbit`·`tp_domain_find_numeric` 은 임시 객체 없이 찾는다(§3 C) |
| 값 깊은 복사·해제 | ~22% | 있다 — 바인드는 소유권 없는 사본으로, 변환 없는 상수 쪽은 복사 안 함(§3 C) |
| 목록 순회·재검사·기록 채우기 | ~22% | 반은 있다(자리마다 1회로) — 나머지 반이 **결정 자체** |
| 결정 자체(격자 조회 `domain_resolve_comparison`, 콜레이션 병합 `domain_resolve_character`) | ~15% | 결정을 다시 쓰면 0(§3 A) |
| 나머지 | — | 잡음 |

g 를 위 셋으로 줄이면 g' ≈ 100~200ns ≈ 3~6d: 손익 분기 N ≈ 5~10 행. **N = 1 이면 여전히 develop 보다 느리다.** 여기서 구조가 필요하다.

### 2.2 develop 이 이기는 자리의 정체
develop 의 "결정"은 값 두 개의 타입 태그를 보고 분기하는 것이라 캐시 미스가 없고(값은 이미 레지스터·L1 에), 할당이 없다. 게이트의 결정은 (1) 값 → 도메인 객체(캐시 목록), (2) 도메인 → 격자 → 기록(80B 쓰기), (3) 기록 → 실행 상태 배열. 세 단계가 각각 메모리를 건드린다. 결정을 **값에서 도메인 객체를 거치지 않고** 하거나(§3 F), **다시 하지 않거나**(§3 A) 해야 d 에 닿는다.

### 2.3 바인드 30개 기준에서 달라지는 것
S = 30 이면 S × g ≈ 15~20µs. 대신 실행마다 **자리 수와 무관하게** 드는 것이 보인다: `qexec_alloc_resolved_domains`(한 블록, 값 배열 64B × n_refs + 표 + 기록 + 칸 배열; 초기화 memset), `qexec_alloc_held_values`(두 블록), 7단계의 `decided` 배열, 인덱스 스캔의 `qexec_resolve_index_keys` 블록 셋 + `scan_open_index_key_plan` 블록, 끝의 해제 루프. 할당·해제 6~8회 + memset ≈ 1~2µs, 그리고 이 블록들이 실행마다 새 메모리라 캐시가 차갑다. PK 조회(0.1ms 급) 한 번에 1~2% 다. §3 C 의 "스레드별 재사용 버퍼"가 이 몫이다. 실측(release, develop 과 같은 런, 실행당 중앙값 200회, 두 번; `312-371/small/timing{,2}`):

| 셀 | 문장 | dpin | develop | 비(1차 / 2차) | 차이 |
|---|---|---|---|---|---|
| pk-1 | `select c1, c2 from t30 where id = ?` | 0.107 / 0.108 ms | 0.104 / 0.106 | 1.03 / 1.02 | +2~3µs |
| sel-1 | `select ? from db_root` | 0.011 | 0.010 | 1.10 / 1.10 | +1µs |
| nobind | `select c1, c2 from t30 where id = 5` | 0.018 | 0.016 / 0.015 | 1.13 / 1.20 | +2~3µs, 바인드 0개 |
| in-30 | `… where id in (?×30)` | 0.233 / 0.232 | 0.220 / 0.220 | 1.06 / 1.06 | +13µs |
| pkand-30 | `… where id = ? and c1 = ? … c29 = ?` | 0.692 | 0.688 / 0.695 | 1.01 / 1.00 | 0 |
| and-30 | `… where c1 = ? … c30 = ?` 10,000행 스캔 | 4.23 / 4.26 | 4.17 / 4.16 | 1.02 / 1.02 | +60~100µs |
| case-30 | `case when concat(?, '') = ? …` ×30, 한 행 | 0.110 / 0.107 | 0.088 / 0.085 | 1.24 / 1.26 | +21µs |
| upd-31 | `update t30 set c1 = ? … c30 = ? where id = ?` | 0.443 | 0.443 | 1.00 / 1.00 | 0 |

읽기: 바인드 30개짜리 OLTP 문장은 0~6%, 쓰기는 0 이다. 바인드 수와 무관한 **고정 비용 2~3µs**(nobind·pk-1·sel-1)가 있고, 문자 함수 노드가 자리마다 있는 모양(case-30: `concat` 30개의 collation 게이트 노드 + 상수 평가 30회)만 20% 대다. in-30 의 13µs 는 30 range 의 8단계·스캔 열기·B-tree 비교(약 6,000회)다.

## 3. 대안

각 대안: 무엇 / 왜 빠른가(정량) / 더 직관적인가 / 잠긴 결정과의 관계 / 위험 / 비용.

### A. 결정을 실행 간에 다시 쓴다 — "타입은 준비 때, 값은 실행 때"

**무엇.** 게이트가 만드는 결정(GATE 슬롯 도메인, 게이트 의존 노드의 `RESOLVED_DOMAIN`, 비교·원소 기록, 키 규칙, 세션변수의 문장 타입, 가드 판정에 필요한 상수의 *타입*)은 (플랜, 바인드 타입 서명, 세션변수 시작 타입, 결정이 읽는 파라미터) 의 순수 함수다. 이를 **결정 집합** `DOMAIN_DECISIONS` 하나로 묶어 XASL 캐시 항목(`XASL_CACHE_ENTRY`)에 서명별로 보관한다(작은 LRU, 예: 4개). 실행은 (1) 서명을 만들고(바인드마다 타입·precision·scale·codeset·collation·NULL 여부 = 16B), (2) 항목의 결정 집합 목록에서 같은 서명을 찾아(memcmp) 있으면 그것을 `XASL_STATE` 가 가리키고, (3) 없으면 지금의 G1 을 돌려 새 결정 집합을 만들고 등록한다. **값**(상수 부분트리의 값, 변환된 상수 쪽, 스코프 붙잡음 값)은 지금처럼 실행 상태에 실행마다 둔다 — 결정 집합은 값을 갖지 않는다.

**왜 빠른가.** 같은 서명의 재실행에서 자리 수에 비례하는 게이트 일이 서명 생성(바인드 수 × ~5ns)과 memcmp 로 준다. `case … ×512` 셀: 게이트 ≈ 360µs → ≈ 5µs + 상수 평가 512회(develop 도 행에서 하던 일). 바인드 30개 셀: ≈ 15µs → ≈ 0.2µs. 모든 행 수에서 develop 보다 앉는다(행은 이미 `cmpval` 직접). PX 워커는 결정 집합을 **읽기 전용으로 공유**할 수 있어(불변 객체) 지금의 `qexec_deep_copy_xasl_state` 가 하는 표·기록 복사도 없어진다.

**더 직관적인가.** 그렇다. "prepare 로 타입이 정해지고 execute 는 값만 준다"는 사용자 모형(PG 의 `param_types`, MySQL 의 첫 실행 타입 확정 + 재준비, #315 §2.3·§5)과 같다. G1 은 "서명이 다르면 다시 결정" 한 줄로 설명된다. 지금의 8단계는 "서명이 처음일 때의 계산"으로 자리가 정해진다.

**잠긴 결정과의 관계.** ADR 0020 "결정 지점은 컴파일과 게이트 둘" — 결정은 여전히 게이트 코드가 만든다(첫 서명에서). P5 "플랜 불변, 상태는 XASL_STATE" — 결정 집합은 플랜 노드도 클론도 건드리지 않는다. 캐시 항목에 붙는 **불변 객체**고, XASL_STATE 는 포인터로 가리킨다. 지도 Out of scope 의 "바인드 타입 서명 변형 플랜(D)"은 XASL 을 서명별로 여러 벌 만드는 것이라 다르다 — 여기서 XASL 은 하나다. 그래도 **클론 풀에 실행 간 상태가 생기는 것**이므로 사용자 결정(D-1)과 ADR 0020 의 구현 주석이 필요하다.

**위험과 그 대답.**
- 서명이 결정의 입력을 다 담아야 한다. 입력을 열거해야 한다: GATE 바인드의 값 도메인(타입·precision·scale·codeset·collation)과 NULL 여부, 세션변수 읽기의 시작 타입(7b), `domain_resolve*` 가 읽는 시스템 파라미터(`plus_as_concat`·`oracle_style_empty_string`·`compat_mode`·`return_null_on_function_errors` 류 — 세션이 바꿀 수 있는 것은 서명에 넣거나 항목의 결정 집합을 비운다), collation 설정(문장 재컴파일로 항목이 갈리므로 자연히 분리). **이 열거를 정적 감사 + optdebug 그림자 검사(캐시 히트 때 지금의 G1 을 돌려 결정 집합이 같은지 assert)로 증명한다.** 그림자 검사는 지금의 `qdata_assert_precast_*` 와 같은 방식이다.
- 다른 세션의 PX 워커가 같은 클론 풀을 쓴다(CBRD-27484): 결정 집합은 세션 상태가 아니라 서명의 함수이므로 공유해도 답이 같다. 세션변수 타입은 서명에 있다.
- 메모리: 항목마다 서명당 결정 집합 1개(기록 80B × 자리 + 표 56B × 슬롯 + 키 결정). 상한(LRU 4)과 `xcache_Memory_usage` 계정에 넣는다.
- 결정 집합의 도메인 포인터는 `tp_domain_cache` 의 캐시 도메인이라 프로세스 수명(안전).

**비용.** 게이트 진입 `qexec_resolve_domains` 앞의 서명 계산·조회, 결정 집합의 분리(지금 `RESOLVED_DOMAIN_TABLE` 의 결정 필드와 값 필드를 두 구조로 나눔), 캐시 항목의 목록·잠금(`cache_clones_mutex` 옆), PX 상속의 단순화. 리뷰 ②의 R2-08 (a)·R2-13 도 함께 풀린다. 규모는 #368 C5 정도(한 티켓). **답 불변**이어야 하고(P0), CTP 전수와 "서명 교대 셀"(같은 문장에 다른 타입을 번갈아 바인드)로 검증한다.

### B. 프로토콜에서 타입을 선언한다 (PostgreSQL 모형)
클라이언트가 prepare 때 파라미터 타입을 보내면 결정은 전부 컴파일에서 끝난다. **지도 밖**: CAS 프로토콜·JDBC 드라이버 변경, 그리고 develop 답(값 타입이 정하는 답)을 바꾼다(P0 위반). A 는 프로토콜을 두고 같은 효과를 얻는다.

### C. 결정을 바꾸지 않고 하는 일만 줄인다 (#371 워커 A·B·C — 진행 중)
- 도메인 조회에 임시 객체를 만들지 않는다(`tp_domain_find_charbit`·`tp_domain_find_numeric`·`tp_domain_resolve_default` 로 바로 찾기): ALLOC-01. 프로파일 몫 ~24%.
- 값을 복사하지 않고 소유권 없는 사본으로 나눠 쓴다, 변환 없는 상수 쪽은 복사하지 않는다, 비교 자리의 키는 값에서 읽는다: ALLOC-01·PRIORITY 2. ~22%.
- 7단계 준비 검사는 자리마다 1회, 8단계는 상수 키가 컬럼과 같으면 배열·중복 제거·비교표를 건너뜀: BR-04 확장·PRIORITY 1. ~10%.
- 실행 상태 블록의 **스레드별 재사용**(ALLOC-04: 연결 스레드가 최대 크기로 키워 두고 실행마다 재사용, 해제 없음): §2.3 의 고정 비용과 커널 몫(페이지 폴트). 다음 물결 후보.
직관성은 그대로다(구조 불변). 한 행 문장에서 develop 과 같아지지는 않는다(§2.1).

### D. 행 경로를 "결정된 커널 하나"로 (#371 워커 D1·D3 — 진행 중, D2·D4·D5 다음 물결)
- **D1 B-tree 검색 키 비교**: 스캔을 열 때 키 계획으로 비교 종류(DIRECT / MIDXKEY_PLAIN / PLANNED)를 정해 `BTID_INT` 에 두고, 비교마다 NULL 검사 뒤 `cmpval` 만 부른다. 비교당 약 10 분기·1 호출이 준다. `id in (?×1,024)` 실행당 217,074 비교 × ~3ns ≈ 0.6ms(develop 시간 4.1ms 의 15%). 바인드 30개면 6,000 비교 ≈ 20µs. **develop 보다 빨라지는 자리**다(develop 도 비교마다 검사한다).
- **D3 비교 항 leaf**: 기록이 정해질 때 (커널 × 연산자) 함수 포인터를 두고 행은 그것 하나를 부른다(A61·BR-06). 행 비교당 ~10 분기·2 호출 단 감소. 10,000행 × 30항 셀에서 300,000회.
- **D2 칸 접근**: 게이트 끝에 칸을 컴파일 도메인으로 미리 채워 행은 적재 1회(R2-03 (b)); 접근자 항상 인라인(CC-05).
- **D4 스코프 붙잡음 값의 미리 변환**: 스코프 진입 때 변환해 두고 행은 포인터 하나(지금은 행마다 epoch·변환기·목표 비교 8 분기).
- **D5 누적기의 행마다 `is_held` 판정**을 설정으로.
직관성: "행은 결정된 함수를 부른다"가 코드 모양이 된다. 잠긴 결정과 무관(구현 변형, D-323-16 이 열어 둔 것).

### E. 게이트를 의존 그래프 한 번 훑기로
지금 G1 은 8단계에 `after_constants`·`constant_sites_first`·준비 상태·세션변수 고정점·가드 실패 목록이 얽혀 있다. 로드가 항목·자리·상수·세션변수를 노드로, "이 결정이 저 결정을 읽는다"를 간선으로 둔 DAG 를 만들고, 게이트는 진입 차수 0 인 것부터 한 번씩 처리하는 워크리스트 하나로 바꿀 수 있다. 재검사가 구조적으로 없고(각 노드 1회), 단계 번호 대신 "준비되면 처리" 한 문장으로 설명된다. 속도 이득은 §2.1 의 순회 몫(~10%)이라 작고, 검증된 1,500줄을 다시 짜는 비용이 크다. **A 를 하면 이 코드는 첫 서명에서만 돌아 중요도가 내려간다** — A 뒤에 정리 티켓으로.

### F. 도메인 객체를 결정의 통화로 쓰지 않는다
결정의 입력을 `TP_DOMAIN *` 대신 16B 키(타입·precision·scale·codeset·collation)로 두면 `tp_domain_cache` 의 연결 리스트·뮤텍스와 만나지 않는다. `domain_compare_key_of_value` 가 이미 그 방향이다. 그러나 소비자(리스트 파일 type_list, midxkey setdomain, 누산기)가 `TP_DOMAIN *` 를 요구해 경계에서 다시 도메인을 만들어야 하고, 엔진 전체의 어휘가 도메인 객체다. 직관성을 해친다. C 의 "임시 객체 없는 조회"로 같은 이득의 대부분을 얻는다 — **채택하지 않음**.

### G. 산술의 타입별 연산 leaf
`qdata_add_dbval` 류의 (타입1 × 타입2) 2단 switch 는 감사표 S-08 이 "연산 구현"으로 남겼다. 사전 캐스트가 계획에 있으므로 노드마다 (타입1 × 타입2) leaf 를 로드·게이트가 고를 수 있다(A61). 큰 개편(`qdata_*_dbval` 네 함수의 수백 case)이라 #345 의 P1 셀 측정이 산술 몫을 보일 때만. 후보로만 적는다.

## 5. 권고 순서
1. **C + D1 + D3**(진행 중): 결정 불변, 답 불변. 합쳐서 CTP 전수 게이트. 여기까지로 바인드 30개·1행 셀이 어디까지 오는지 잰다(#371 진행 코멘트의 8셀).
2. **A** 를 사용자 결정(D-1)으로 잠그고 다음 티켓(dpin-18e)으로: 서명 입력 열거 → 결정 집합 분리 → 캐시 → 그림자 검사 → 서명 교대 셀. #345(최종 측정) 앞에 둔다. 이것이 "develop 과 같거나 빠르게"를 모든 모양에서 만드는 구조다.
3. D2·D4·D5 는 1 의 측정에서 행 경로가 보이면. E 는 A 뒤 정리로. G 는 #345 뒤 후보.

## 6. 측정 계약 (MEAS)
- MEAS-01/04: 모든 판정은 release, develop 과 같은 런, 실행당 중앙값(200회 이상), 두 번 반복. 셀은 #371 의 8셀(바인드 0·1·30, 읽기·쓰기, 1행·10,000행) + 리뷰의 8셀(원인 추적용).
- MEAS-06: 시간과 함께 호출 횟수(gdb R=1/R=2 차, `312-371/parse_counts.py`)와 함수별 자기 시간(`symbolize.py`)을 같이 적는다 — 카운터 0 은 결정이 없다는 뜻이지 비용이 없다는 뜻이 아니다.
- MEAS-08: 두 빌드는 두 ELF 다. 1% 안의 차이는 심볼 배치 게이트 뒤에 귀속한다.
- A 를 위한 새 셀: 같은 문장에 (INT, VARCHAR) 바인드를 교대해 서명 미스를 강제하는 셀, 서명 히트 셀. 히트에서 게이트 시간 ≤ 1µs 를 목표로 적는다.
