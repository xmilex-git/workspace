# BIGINT/NUMERIC 과 DOUBLE 의 비교는 DOUBLE 의 가장 짧은 왕복 십진수로 정확히 판정한다

develop 은 BIGINT/NUMERIC × DOUBLE 비교의 공통 타입이 DOUBLE 이라 2^53 이상 정수·17자리 초과 NUMERIC 에서 서로 다른 값이 같다고 답하고, 인덱스·파티션 경로는 키 값으로 판정해 순차 스캔과 어긋난다(CBRD-27797/27799/27703). PostgreSQL 18.6 실측(2026-10-30, `.git_ignored_dir/scratch/cbrd27819/grill/pg18-probe2.out`)은 develop 과 같은 DOUBLE 비교이고, 불일치는 혼합 비교에 인덱스 키·파티션 가지치기를 아예 쓰지 않는 것으로 피한다; Oracle 도 NUMBER × BINARY_DOUBLE 은 BINARY_DOUBLE 로 비교한다. 사용자는 2026-10-30 사양 유지(P)와 바로잡기(C) 가운데 (C)를 택했다: DOUBLE 쪽의 비교값을 **가장 짧은 왕복 십진수**(최대 17자리)로 두고 NUMERIC 으로 정확히 비교한다. 바뀌는 답은 서로 다른 두 값이 DOUBLE 로 같아지던 경우뿐이며(아래 표) 전부 현행이 틀린 답이다. 대소도 같은 비교값으로 정해 동등과 대소가 한 값에서 일관된다. CAST·대입(16자리 절단), 산술·집계·함수의 결과 타입, SHORT/INTEGER × DOUBLE 의 답은 바뀌지 않는다.

| 질의 (develop 5b1867174 실측) | develop | 이 결정 |
|---|---|---|
| `9007199254740993 = 9007199254740992e0` (BIGINT 2^53+1) | 참 | 거짓 |
| `n(0.1) = 0.1e0`, `12345678901234568 = 12345678901234568e0` | 참 | 참 |
| `0.10000000000000001 = 0.1e0` / `>` | 참 / 거짓 | 거짓 / 참 |
| `0.3 = 0.1e0 + 0.2e0` | 거짓 | 거짓 |

## Considered Options

- **(P) PG 방식 — DOUBLE 비교 유지, 인덱스·파티션을 "DOUBLE 로 같은 키 전부" 로 맞춤**: 기각. 사양은 지켜지나 틀린 답이 영원히 남고, CBRD-27819 의 전제(공통 타입 NUMERIC)와 어긋난다.
- **(A) DOUBLE 의 이진 정확값으로 비교** (survey S1-2): 기각. `n(0.1) = 0.1e0` 이 거짓이 되어 JDBC `setDouble(0.1)` 로 NUMERIC 열을 찾는 패턴이 깨진다.
- **(B) 현행 CAST(16자리 절단) 값으로 비교**: 기각. `12345678901234568 = 12345678901234568e0` 처럼 현행이 맞던 17자리 답을 틀리게 한다.

## Consequences

- 비교 결과가 바뀌는 사양 변경이므로 JIRA CBRD-27819 의 "Specification Changes: 없음" 은 수정 대상(사용자 승인 뒤). 바뀐 답을 가진 CTP 답 파일은 고치고, 위 표는 TC 로 고정한다.
- 인덱스 키 범위·다중 키 정리·파티션 가지치기·DML 라우팅·해시 조인 키·IN 리스트·CASE/DECODE/NULLIF 동등 등 두 값을 판정하는 모든 자리가 같은 비교값을 써야 한다(CBRD-27583 사양 14 의 범위 확장은 이 규칙으로 대체).
- 비교값을 행마다 구하는 비용이 비교 경로의 성능 과제다(CBRD-27819): DOUBLE 끼리 먼저 견주고 같을 때만 가장 짧은 십진수를 구하는 두 단계가 가능하다(nearest(n) < d ⇒ n < shortest(d), 반올림의 단조성).
