# 바깥에 인덱스 스캔이 있어도 가장 안쪽 순차 힙 스캔은 래치 유지 스캔으로 읽는다

스캔 사슬 어디에든 인덱스 스캔이 있으면 사슬 전체의 래치 유지 스캔(fixed scan)을 끄는 규칙이 있었다(`qexec_execute_mainblock_internal`, 주석 "this is legacy and should be reconsidered"). 페이지 복사 스캔은 선행 스캔에만 허용됐다. 그래서 바깥이 인덱스 스캔인 중첩 루프의 안쪽 순차 힙 스캔은 읽는 행마다 페이지를 다시 잡았다. 206페이지·2만 행 테이블을 바깥 행 8개에 대해 읽으면 trace fetch가 161,648이었다. 같은 테이블을 혼자 읽으면 206이다.

사용자 결정(2026-11-09 그릴링, CBRD-27967 PR 8438에 넣음):

- 가장 안쪽 순차 힙 스캔은 바깥에 인덱스 스캔이 있어도 래치 유지 스캔으로 읽는다. 그 스캔의 행마다 실행되는 하위 질의가 있으면 제외한다.
- 래치 유지 스캔이 아닌 나머지 힙 스캔은 페이지 복사 스캔으로 읽는다. 다음 바깥 행에서 다시 시작할 때 이전 복사본을 버린다.
- 가장 안쪽 스캔은 첫 일치에서 멈춘 경우(세미·안티 조인, 바깥 조인의 한 행)에도 바깥 단계로 제어가 넘어가기 전에 래치를 놓는다.
- 환경 게이트 없이 항상 켠다.
- SP가 스캔 도중 행을 바꾸는 문장(CBRD-27590, CBRD-27591)은 여기서 막지 않는다. CBRD-27579(PR 8182)가 SQL에서 부른 SP의 DML을 거부한다.

같은 질의의 fetch는 1,648이 된다(페이지당 한 번). 답은 develop과 같다.

## Considered Options

- **인덱스 규칙 유지, 안쪽 스캔에도 페이지 복사 스캔만 허용**: 기각. 가장 안쪽 스캔은 행을 이어서 읽고 바로 끝나므로, 페이지를 복사하는 비용 없이 래치를 쥔 채 읽어도 된다(사용자). 중간 스캔에만 복사를 쓴다.
- **첫 일치 후 래치를 다음 바깥 행의 리셋에서 놓기**: 기각. 바깥 스캔이 다음 행을 가져온 뒤에 리셋이 불리므로(SA gdb로 호출 순서 확인), 그동안 바깥 단계가 래치를 쥔 채 돈다. 이 경우에도 지금 코드의 래치 순서로는 대기 사이클이 없지만(TLC), 원칙("바깥 단계로 가기 전에 놓는다")이 순서 보장에 기대게 된다.
- **SP가 있는 문장에서는 끄기**: 기각(사용자). PR 8182가 SP의 DML을 막는다.

## Consequences

- 검증: `docs/tla/CBRD-27967-nl-inner-fixed/` `RESULT: OK`(2026-11-09). 대기 사이클 없음(C1)은 래치 해제(C2)와 코드의 래치 순서 둘 중 하나만 있어도 성립한다. 둘을 함께 뺀 mutant만 사이클을 만든다.
- 바깥 인덱스 스캔이 같은 페이지의 행을 바꾸려는 다른 트랜잭션을 기다리게 하는 시간이 안쪽 스캔 한 번 분량으로 늘어난다. 단일 테이블 래치 유지 스캔과 같은 수준이다.
- PR 8182가 머지되지 않은 동안, SP가 안쪽 스캔 중인 페이지를 DML로 바꾸면 자기 래치를 기다린다(CBRD-27591). 이 변경으로 그 경우가 바깥 인덱스 스캔을 가진 질의로도 넓어진다.
- 용어: GLOSSARY "래치 유지 스캔", "페이지 복사 스캔".
