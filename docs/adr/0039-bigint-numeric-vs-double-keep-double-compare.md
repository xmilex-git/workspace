# BIGINT/NUMERIC 과 DOUBLE/FLOAT 의 비교는 develop 처럼 근사형으로 하고, 모든 경로가 그 답에 맞춘다

ADR 0037 은 BIGINT/NUMERIC × DOUBLE 비교를 DOUBLE 의 가장 짧은 왕복 십진수로 정확히 판정하기로 했었다(안 C). 구현(map #562, #569)을 진행해 보니 이 규칙은 두 갈래가 됐다. |d| < 2^53 이면 가장 짧은 십진수, 그 이상이면 정확한 정수다. 공통 타입을 둘 수 없어서(NUMERIC 은 컴파일 때 정한 precision·scale 하나로 DOUBLE 값의 범위를 담지 못한다) 타입 쌍별 전용 비교 함수가 필요했다. 해시 조인·해시 리스트 스캔 키에는 별도의 정확 반올림 변환이 필요했다. 상수 접기와 옵티마이저도 같은 규칙을 따라야 했다. 사용자는 2026-10-30 이를 보고 PostgreSQL 18.6·Oracle 과 같은 방식(안 P)으로 바꾸었다("P로 가자"). 비교의 공통 타입은 develop 그대로 근사형이다(DOUBLE, FLOAT 상대는 FLOAT). `9007199254740993 = 9007199254740992e0` 은 develop·PG 처럼 참으로 남는다. CBRD-27797·27799·27703 이 문제 삼은 것은 같은 비교가 경로(순차 스캔, 인덱스 범위, 다중 키 정리, 여러 열 인덱스의 뒤 열, 파티션 가지치기와 DML 라우팅)마다 다른 답을 내는 것이다. 이 결정은 그 모든 경로가 순차 스캔의 근사형 비교와 같은 답을 내게 한다. 예를 들어 인덱스 키 범위는 "근사형으로 바꿨을 때 경계와 같은 키 전부"를 덮는다. PG 는 같은 문제를 섞인 비교에 인덱스·파티션 키를 쓰지 않는 것으로 피하지만, CUBRID 는 키를 쓰면서 범위를 맞춘다.

## Considered Options

- **(C) 가장 짧은 왕복 십진수로 정확 비교(ADR 0037)**: 기각(2026-10-30). 답은 더 정확하지만 규칙이 두 갈래이고 공통 타입이 없다. 그래서 비교·해시·접기마다 전용 경로가 필요했고 사양 설명이 직관적이지 않았다. 구현 산출물(설계 `research/cbrd27819-compare-dispatch`, 미커밋 diff `.git_ignored_dir/scratch/cbrd27819/569/c-design-final.diff`)은 기록으로만 남긴다.
- **(A) DOUBLE 의 이진 정확값으로 비교**: 기각(ADR 0037 과 같은 이유). `n(0.1) = 0.1e0` 이 거짓이 된다.
- **(B) CAST 값(16자리 절단)으로 비교**: 기각. develop 에서 맞던 `12345678901234568 = 12345678901234568e0`, `n(0.3) = 0.1e0 + 0.2e0`(거짓→참) 같은 답을 새로 틀리게 한다.
- **(P′) PG 그대로 — 섞인 비교에 인덱스·파티션 키를 쓰지 않음**: 기각. develop 에서 인덱스를 타던 문장이 순차 스캔으로 바뀐다.

## Consequences

- 비교 결과는 develop 의 순차 스캔 답과 같다. 바뀌는 것은 인덱스·다중 키·파티션 경로가 그 답과 어긋나던 경우뿐이다(CBRD-27797·27799·27703). 사양 변경은 "경로 간 불일치 해소" 로 기술한다.
- CBRD-27819 의 "공통 타입을 DOUBLE 에서 NUMERIC 으로" 는 채택하지 않는다. 이 이슈에 남는 것은 NUMERIC 경로의 성능이다: `_dtoa` 제거(DOUBLE→NUMERIC CAST), 정수×NUMERIC 직접 비교, 산술 개선, 결과 캐시 NUMERIC 해시. 산술·집계·함수 결과 타입은 바뀌지 않는다.
- ADR 0037 의 2^53 규칙, FLOAT 2^24 규칙, NaN·JSON 행, ADR 0038(새 비교 경로의 env 게이트 예외)은 효력이 없다.
- 이 경로 정렬은 컴파일러의 결정(키 범위 확장 여부, 가지치기 방식)으로만 한다. 서버가 행 시점에 값 타입을 보고 비교 의미를 고르지 않는다(CUBRID/cubrid#8213 의 원칙). CBRD-27583 사양 14 의 "손실 없이 바꿀 수 없는 키의 범위 확장" 이 이 결정의 기반이다.

## 구현 형태 (2026-10-30, map #569 설계; PostgreSQL 18.6 대조 `.git_ignored_dir/scratch/cbrd27819/grill/pg-join2.out`)

PostgreSQL 은 손실 키 쌍(GLOSSARY)의 열을 인덱스·파티션 키로 쓰지 않고 필터로만 비교해 불일치를 피한다. 실측한 모든 모양(열 × 열 조인, 여러 열 인덱스, OR/IN, ORDER BY, PK, LIST 파티션·DELETE)에서 답은 이 결정의 목표 답과 같다. 사용자는 2026-10-30 develop 이 쓰던 인덱스를 잃지 않는 쪽을 택했다("가로 가긴 해야 돼"): 손실 키 쌍의 열도 키로 쓰되 범위로 탐색한다.

- 컴파일러가 두 타입만 보고 손실 키 쌍을 판정한다(`domain_key_converts_losslessly` 의 기존 기준). 값은 보지 않는다.
- 상수·호스트 변수와의 동등 항은 재작성 맨 앞에서 범위 항(`b BETWEEN d AND d`, 양 경계 merges)으로 정규화한다. 그러면 ORDER BY 제거·동등 항 축약·여러 열 인덱스 접두·UNIQUE 단건 탐색·HASH/LIST 가지치기가 범위 항의 기존 규칙으로 맞게 된다.
- 경계 값의 같음을 범위의 같음으로 보던 자리 셋(옵티마이저 OR 범위 병합, 실행 시점 다중 키 병합, RANGE 파티션 가지치기·DML 라우팅)은 merges 표시를 보고 판정한다. 값 계산은 없다.
- 열 × 열 조인 항은 등호 항으로 둔다(해시·병합 조인 유지). B-tree 탐색은 CBRD-27583 사양 14 의 merges 경계가 바깥 행마다 범위로 탐색한다. 여러 열 인덱스 접두를 고르는 한 곳만 merges 항을 등호로 치지 않는다.
- 기각: L/H 구간을 값으로 계산해 키 도메인 경계로 바꾸는 안(서버 또는 클라이언트 계산이 생기고, #8213 의 merges 가 이미 있는 일을 다시 한다); PostgreSQL 처럼 키로 쓰지 않는 안(단일 열 인덱스와 NL 인덱스 조인이 느려진다).
- PostgreSQL 과 알려진 차이(2026-10-30, `.git_ignored_dir/scratch/cbrd27819/571/pg/cmp.txt`): PostgreSQL 은 int4/int8/numeric 대 real(float4)을 DOUBLE 로 비교하고(`16777217 = 16777216::real` 거짓), CUBRID 는 FLOAT 로 비교한다(참). 이 결정은 develop 의 FLOAT 비교를 유지한다. 바꾸면 사양 변경이다. 그 밖의 모든 모양(27797·27799·27703 TC, 열 × 열 조인, 여러 열 인덱스, OR/IN, ORDER BY, PK, LIST 파티션·DELETE)에서 두 시스템의 답은 같다.
