# 모든 비교 확정은 타입 쌍 비교 표의 칸이다 — 키를 행 전에 아는 자리는 칸을 복사하고, 컬렉션 원소·인덱스 키는 표의 행을 보기로 쓴다

비교 확정의 계산은 이미 한 함수(`domain_resolve_comparison`, 호출처 9곳)다. 그런데 결과를 담는 곳이 여섯 갈래로 나뉘어, 조회·PX 복사·optdebug 교차 검사를 각자 따로 가졌다. 여섯 갈래는 확정 비교와 비교 연산자 함수, 컬렉션 원소 비교 표, 인덱스 키 비교 표, 타입 쌍 비교 표, B-tree 검색 키 비교기, 해시 빌드 키 계획이다. 새 비교 경로를 만들 때 어느 것을 써야 하는지 코드만으로는 알 수 없었다(#374 F-374-06).

결정:
- 비교 확정은 타입 쌍 비교 표(부팅 때 한 번, `entry[강제 여부][키1 × 키 수 + 키2]`, 비교에 쓰이는 값 타입 30종과 등록된 collation 을 모두 덮는다)의 칸이다.
- 두 쪽 키를 행 전에 아는 자리는 그 칸을 자기 확정 비교에 복사한다: 술어 항, FIELD·NULLIF·LEAST·GREATEST, LIMIT, 머지 쌍. 로드나 실행 전 도메인 확정이 복사한다. 행은 자기 확정 비교만 읽으므로 그 첫 64바이트 배치가 유지된다.
- 컬렉션 원소 비교 표와 인덱스 키 비교 표는 없앤다. 두 표는 타입 쌍 비교 표와 같은 색인(`first[타입] + ordinal[collation]`)을 부분집합에 다시 만든 것이었다. 대신 한쪽 키(항의 item, 인덱스 컬럼)로 정해지는 타입 쌍 비교 표의 한 행을 보기로 쓴다.
- B-tree 검색 키 비교기(DIRECT·MIDXKEY_PLAIN·RESOLVED, 옛 이름 PLANNED)와 해시 빌드 키 계획은 비교 확정이 아니다. 각각 빠른 길 선택과 변환기 선택이다. 이름과 주석으로만 구분한다.

효과: 보관 구조가 넷에서 둘(자리별 복사, 타입 쌍 비교 표)이 된다. PX 복사는 확정 비교뿐이다(타입 쌍 비교 표는 공유되고 바뀌지 않는다). 교차 검사도 한 곳이 된다.

## Considered Options

- **보관은 그대로 두고 조회·PX 복사·교차 검사만 한 인터페이스로(라운드 1 Q9 (나))**: 기각. 성능 변화는 없지만 구조의 수가 그대로라 처음의 문제(어느 것을 쓰나)가 남는다.
- **헤더 주석 표만(Q9 (다))**: 기각. 같은 이유다.

## Consequences

- 컬렉션 원소 비교와 B-tree 검색 키 비교의 행 경로가 "구조별 조회" 에서 "타입 쌍 비교 표 행 조회" 로 바뀐다. 둘 다 O(1)(키 번호 계산 + 색인)이지만 B-tree 경로는 뜨겁다. 그래서 명령 수로 잰다(PR 머리 대비 +1% 이내, develop 대비 +5% 이내, D-374-30). 이동이 코드 배치를 바꾸므로 시간으로 비교하지 않는다(CC-08).
- 되돌리는 길: 측정이 기준을 넘으면 인덱스 키 비교 표만 옛 보관(스캔별 표)으로 남긴다(D-374-23). 원소 쪽은 그대로 보기로 간다.
- 측정 결과(2026-09-29, 커밋 3, 커밋 2 대비): 인덱스 스캔 칸 P5-eq·P5-mro 는 명령 수가 0.7~1.7%, P6-in H=·H!= 는 2.3% 줄었고, +0.5% 를 넘은 칸은 없다. 되돌리는 길은 쓰지 않았다.
