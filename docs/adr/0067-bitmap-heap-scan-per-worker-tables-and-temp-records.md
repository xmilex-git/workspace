# bitmap heap scan은 워커별 표시 테이블과 임시 파일의 표시 레코드로 표시하고, 페이지 단위 표시는 두지 않으며, 옵티마이저가 고른다

ADR 0056은 스캔 하나가 힙의 모든 섹터에 대한 비트열을 메모리에 두고(파라미터 `index_scan_oid_bitmap_size`, 기본 16MB) 워커들이 atomic OR로 함께 표시하며, 상한을 넘으면 페이지 단위로 표시하도록 정했다. 켜고 끄는 것도 파라미터(`bitmap_heap_scan`)였다. 이 문서는 그 세 가지를 모두 바꾼다.

사용자 결정(2026-11-18~19 그릴링, MAP의 E1~E33).

## 결정

1. **메모리 상한은 워커의 표시 테이블 크기다.** 인덱스 단계의 워커는 인덱스 스캔의 키 버퍼와 같은 크기(20페이지)의 표시 테이블을 자기 것으로 갖는다. 표시가 생긴 페이지에만 페이지 엔트리(슬롯 비트 640개)가 생긴다. 힙 전체에 대한 비트열은 두지 않는다.
2. **넘치면 임시 파일에 쓴다. 페이지 단위 표시는 없다.** 힙은 스캔을 시작할 때 힙 파티션으로 나뉘고, 그 개수는 한 파티션의 페이지가 표시 테이블 하나에 들어가게 정해진다. 워커의 테이블이 처음 가득 차면 첫 파티션의 엔트리만 남고, 나머지와 그 뒤의 표시는 16바이트 표시 레코드로 그 파티션의 임시 파일 체인에 쓰인다. 힙 단계의 워커는 파티션을 맡아 모든 워커의 엔트리와 레코드를 하나로 합친 뒤 페이지를 파일 순서로 읽는다. 파티션이 256개로 모자란 큰 힙은 힙 워커가 파티션을 한 번 더 나눈다.
3. **슬롯 번호가 640 이상인 OID는 넘침 목록으로 간다.** 워커마다 list file 하나에 모으고, 힙 단계에서 한 워커가 합쳐 중복 없이 조회한다.
4. **옵티마이저가 고른다.** 계획이 정해지고 구동 인덱스 스캔의 병렬 여부가 정해진 뒤, 문장이 한 번 실행하고 끝까지 읽는 인덱스 스캔(구동 스캔, hash join의 두 입력 아래 스캔)마다 힙을 키 순서로 조회하는 비용과 bitmap heap scan의 비용을 비교해 싼 쪽을 고른다. 파라미터는 없다. nested loop join의 안쪽 스캔, 행 수 제한으로 중간에 멈출 수 있는 문장, 행에 잠금을 거는 스캔은 고르지 않는다. 키 순서를 쓰는 계획(ORDER BY, GROUP BY 생략), 키 limit, 커버링 스캔, index skip scan, loose scan, multi range optimization은 고르지 않는다.

## 왜

- **상한을 넘는 테이블에서 페이지 단위 표시는 느렸다.** TPC-H SF10 lineitem(11.7GB)을 320KB 상한의 페이지 단위 표시로 읽으면 hot에서 기존 인덱스 스캔보다 2.4~20배 느렸다(perf-node0, run `20261118-161919-248`). 모든 행을 다시 읽고 조건을 다시 확인하기 때문이다. 표시 레코드로 내보내면 10% 범위 hot이 1.61~1.63초로, 공유 비트열(1.54초)과 0.1초 안이다(run `20261118-212647-248`).
- **파티션 개수를 실행 중에 늘리지 않는다.** hash join처럼 넘칠 때마다 두 배로 늘리면, 적은 개수일 때 쓴 레코드의 40~80%를 다시 나눠 써야 했다(구조 프로토타입 실측). 힙의 섹터 수는 스캔을 시작할 때 알므로 개수를 처음에 정한다.
- **필터·함수·prefix 인덱스도 대상이 된다.** 페이지 단위 표시가 없으니 힙 행에서 인덱스 조건을 다시 확인할 일이 없다.
- **행 수 추정은 계획만 정한다.** 크기와 배치는 섹터 수와 실제로 쓴 표시에서 나오므로, 추정이 틀려도 결과와 메모리 상한은 그대로다.

## 따라오는 것

- 워커는 표시 테이블을 단계마다 하나씩, 둘 갖는다(인덱스 단계의 테이블은 힙 단계에서 다른 워커가 읽는다).
- 옵티마이저의 선택은 계획의 비용을 바꾸지 않는다. 조인 순서는 인덱스 스캔의 비용으로 정해지고, bitmap heap scan은 그 뒤에 스캔의 실행 방식으로만 고른다. (2026-11-25 ADR 0068이 대체: bitmap heap scan은 계획 후보이고 그 비용이 조인 순서에 들어간다.)
- 직렬 스캔도 대상이다(2026-11-19 사용자 결정, MAP E34). 표시 코드는 병렬 스캔 소스가 아니라 `scan_manager.c`에 둔다(`scan_bitmap_marks`, 서버와 SA 모두). 직렬 스캔은 스캔 하나가 워커 하나로서 같은 표시 테이블, 임시 파일, 파티션을 쓰고, 한 스레드가 index step을 끝낸 뒤 heap step에서 행을 하나씩 반환한다. nested loop join 안쪽 스캔의 bitmap은 만들지 않는다: 바깥 행마다 표시를 새로 만들어야 하고, PostgreSQL 18.6 실측에서도 그 형태는 키당 100행쯤일 때만 골라졌으며 페이지가 버퍼에 있으면 인덱스 스캔보다 31~38% 느렸다. nested loop join 안쪽의 힙 조회는 배치 조인이 맡고, 같은 변경에 들어 있다(ADR 0057의 2026-11-19 절).
