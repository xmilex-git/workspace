# 배치 조인은 쌓아 둔 바깥 행을 기존 행 경로로 다시 흘려 조인한다

배치 조인(`nl_join_batch`)의 목적은 중첩 루프 안쪽 조회의 힙 페이지를 장치가 한꺼번에 읽게 하는 것이다. 구현은 바깥 행을 쌓으면서 행마다 안쪽 인덱스만 먼저 읽어 OID를 모으고, 배치를 닫을 때 그 OID의 힙 페이지를 OS에 알린 뒤(ADR 0055의 힌트), 쌓은 행을 온 순서대로 지금의 행 단위 조인 경로(`qexec_execute_scan_row`)에 다시 넣는다. 행 경로는 바깥 값이 되돌려진 상태에서, 인덱스 탐색 대신 이미 모은 OID를 받아 시작한다.

사용자 결정(2026-11-11): 이 방식은 두고, 범위는 넓힌다. TPC-H Q9(병렬 스캔 워커 안의 첫 조인 단계)와 Q20(바깥 행마다 도는 상관 부질의의 인덱스 조회)도 빨라져야 한다(MAP D39). 스냅샷이 중첩 문장으로 다시 만들어지는 문장도 그대로 묶고, 앞서 읽은 행의 오류는 받아들인다.

## Considered Options

- **모은 OID를 힙 페이지별로 묶어 한 번에 처리(D19의 원래 문장)**: 페이지당 fix가 한 번으로 줄지만, 조인 행을 바깥 순서로 내려면 조회한 행을 다시 정렬해 둘 자리가 필요하고, memoize 저장, left outer의 NULL 행, 안쪽 data filter, 더 깊은 조인 단계로 넘기는 일을 행 경로 밖에서 다시 구현해야 한다. I/O 동시성은 힌트로 이미 얻으므로(ADR 0055) 남는 이득은 fix 횟수뿐이다. 하지 않았다.
- **행 경로를 그대로 쓰고 OID만 먼저 읽기(채택)**: 조인의 의미(memoize, outer join, 필터, 다음 단계)를 한 줄도 다시 쓰지 않는다. 결과와 순서가 행 단위 조인과 같다는 것(C8)이 "행 경로에 같은 값과 같은 OID를 준다"로 줄어든다.

## Consequences

- 순서는 언제나 바깥 순서다. 자유 순서 모드(D22)는 없다.
- semi, anti, following 조인은 묶지 않는다(D21보다 좁다). 첫 일치에서 멈추는 조인에 키의 OID를 전부 먼저 읽는 것은 따로 따져야 한다. (2026-11-19에 바뀜: 아래 절 3)
- OID가 버퍼 하나보다 많은 행은 배치에 걸치지 않고(D35) 행 경로가 직접 읽는다. 그 경로는 자기 OID 버퍼마다 힌트한다(ADR 0055의 읽기 힌트).
- 바깥 스캔과 안쪽 인덱스를 행 단위 조인보다 최대 배치 하나만큼 앞서 읽는다. 일찍 멈추는 질의(LIMIT)에서 그 앞선 행이 내는 오류는 행 단위 조인이라면 나지 않았을 오류다. 배치는 OID 16개에서 시작해 배로 커지므로 앞서 읽는 양은 실제로 쓴 행 수에 비례한다.
- 한 단계의 배치는 윗단계의 현재 행에 대한 바깥 행이 끝나면 닫힌다. 깊은 단계의 배치는 윗단계 한 행의 fan-out만큼만 커진다(D20의 단계 사이 연결은 없다). (2026-11-19에 바뀜: 아래 절 4)
- 인덱스 리프 읽기는 그대로 한 번에 하나다. 배치가 동시에 읽게 하는 것은 힙 페이지뿐이다.
- 바깥 행이 스캔을 지날 때 정해지고 조인 행이 나올 때 쓰이는 상태는 배치와 맞지 않는다. 지금 아는 것은 GROUP BY skip의 키 시작 표시이고, 그 경우 첫 스캔은 묶지 않는다.

## 2026-11-11 이후 (MAP D40~D43; CBRD-28033)

- **도입 여부를 검토 중이다.** 사용자는 힌트와 bitmap heap scan이 이미 많은 부분을 줄이므로 배치 조인을 더 생각해 보기로 했다. 구현 이슈는 CBRD-28033이고 다음 버전 대상이다.
- **도입하면 파라미터 없이 기본으로 동작한다.** `nl_join_batch`(기본 no)는 작업 브랜치의 스위치다.
- **병렬 스캔 워커의 첫 조인 단계도 묶는다**(구현됨, `5eb88d442`): 워커가 자기 XASL 복제본의 첫 조인 단계에 배치를 걸고, 자기 행이 끝나면 쌓인 행을 마저 조인한다. Q9 콜드 NVMe 24.3초 -> 18.2초, SATA SSD 45.7초 -> 37.7초.
- **목표 범위**(구현 안 됨): 깊은 단계의 배치가 윗단계 행이 바뀌어도 유지되는 것, 바깥 행마다 도는 상관 부질의의 인덱스 조회, semi와 anti 조인. 첫 스캔에 직접 붙은 상관 부질의와, 상관 부질의가 붙은 단계 아래의 조인 단계는 넣지 않는다.
- **깊은 단계를 넓히는 방법**은 `docs/tla/CBRD-28033/BatchChain`이 정리했다(TLC만): 윗단계 행을 넘어 유지되는 배치는 그 위의 값 목록을 모두 쌓아야 하고, 끝날 때는 위 단계부터 비우며, 재생 뒤에는 배치를 닫을 때의 윗단계 값을 되돌려 놓는다.
- **한계 실측**: 버퍼는 비어 있고 OS 페이지 캐시에는 다 있는 상태(미리 읽기가 닿을 수 있는 가장 빠른 값)에서 Q7 30.4~31.7초, Q20 9.2~9.9초다. 남은 범위를 다 넣어도 Q7은 44.1초에서 최대 30%, Q20은 17.5초에서 최대 45% 준다.
- 힌트만으로는 Q7이 거의 줄지 않는다(71~74초 -> 67~75초). 키 하나에 OID가 적은 조인을 줄이는 것은 배치 조인뿐이다.

## 2026-11-19 이후 (CBRD-28032에 구현; MAP E35~E37, C9, C10)

사용자 결정(2026-11-19): 배치 조인을 bitmap heap scan과 같은 변경(CBRD-28032, PR #8627)에 넣고, 위 절의 목표 범위를 전부 구현한다. 위 절의 "도입 여부 검토 중", "구현 이슈는 CBRD-28033", "목표 범위(구현 안 됨)"는 이 절로 대체된다. 파라미터 `nl_join_batch`는 없앴다.

1. **배치의 힙 페이지는 표시 테이블에 적지 않고 OS에 알리기만 한다.** bitmap heap scan의 표시(`scan_bitmap_marks`, ADR 0067)에 배치의 OID를 적으면 페이지를 한 번씩만 읽지만, 안쪽 행을 쌓아 두고 바깥 행에 다시 맞춰야 한다. OID 버퍼 하나 크기의 배치에는 같은 페이지가 거의 두 번 들어오지 않으므로 얻는 것이 없다. 행은 이 문서의 원래 결정대로 행 경로로 조인한다.
2. **알리는 양은 미리 읽기 창 하나다.** 배치는 OID를 목표 크기까지 모으지만, 페이지는 조회가 나아가는 대로 창 단위로 알린다(첫 창 OID 8개, 배로 커져 64개까지, 조회가 창의 절반에 닿으면 다음 창). 배치를 닫을 때 한꺼번에 알리면 CBRD-28031이 다른 세션의 커밋 지연을 재고 둔 상한을 넘는다(C10). 창 안의 페이지는 조회 순서로 알리고 정렬하지 않는다.
3. **semi와 anti 조인도 묶는다.** 바깥 행마다 OID 버퍼 한 번의 읽기만 모으고 그 페이지만 알린다. 키의 OID가 버퍼 하나보다 많으면 모은 OID는 알리는 데만 쓰고 행 경로가 인덱스를 다시 읽는다. 파티션 테이블이 안쪽인 semi/anti 단계와, semi, anti 또는 파티션 단계 뒤의 단계는 묶지 않는다(파티션 순회가 바깥 행마다 돈다).
4. **깊은 단계의 배치는 윗단계 행을 넘어 열려 있다(걸친 묶음).** 윗단계도 묶고 있을 때 아래 단계의 배치는 윗단계 행이 바뀌어도 닫지 않고, 붙잡은 행마다 그 위 모든 스캔의 값 목록을 함께 쌓는다. 배치를 닫을 때의 윗단계 값은 따로 두었다가 재생이 끝나면 되돌린다. 윗단계가 끝났는데 자기는 행을 쥐고 있지 않은 단계는 아래 단계의 배치를 마저 비운다. 윗단계 행마다 닫으면 fan-out이 작은 조인에서 배치가 OID 몇 개로 끝나 알릴 것이 없기 때문이다. `BatchChain`의 `mutant-no-prefix`(위 값 없이 재생)와 `mutant-bottom-up`(아래부터 비움)은 행을 빠뜨리고(`AllReturned` 위반), `mutant-late-close`(가득 찬 배치를 위 스캔이 지나간 뒤에 닫음)는 없는 행을 낸다(`NoExtra` 위반).
5. **상관 부질의의 인덱스 조회도 묶는다(부질의 조회 묶음).** 조인 단계에 붙은 상관 부질의가 실행되기 전에 그 단계의 행을 붙잡아 부질의가 읽을 인덱스를 먼저 읽고, 붙잡은 순서대로 부질의를 실행한다. 부질의 결과 캐시가 가진 키의 행은 OID 없이 붙잡는다(캐시의 hit/miss 수가 행 단위 실행과 같다). TPC-H Q20에서 lineitem 부질의 86,204회 실행 중 81,383회가 묶였다(`569df9ac4`).
6. **memoize와 부질의 결과 캐시는 쌓을 때 조회하고, 재생할 때 등록한다**(2026-11-20, MAP E39, C11). 키가 이미 저장돼 있으면 인덱스를 읽지 않고 쌓는다. 같은 키가 한 묶음에 또 오면 그것도 읽지 않는다: 묶음이 쌓은 행의 키 해시를 기억하고, 재생 때 첫 행이 등록한 것을 둘째 행이 받는다. 행 단위 조인보다 인덱스를 더 읽지 않는다는 것이 C11이다(`c01d1edae` 전에는 memoize 조인의 안쪽 readkeys가 146, 뒤에는 develop과 같은 100).
7. **memoize하는 단계도 상관 부질의를 위해 행을 쌓는다**(`900e20c71`). memoize 저장소에는 "이 키는 여기까지"라는 표시가 없어서, 일부만 등록된 키가 조회되면 틀린 결과가 된다. 그래서 키는 그 바깥 행의 행이 전부 한 묶음에 있을 때만, 재생 때 등록한다. 묶음은 자리가 있는 동안 바깥 행의 마지막 행 뒤에서 닫고, 쌓인 키와 같은 키의 바깥 행이 오면 그 행을 조회하기 전에 묶음을 먼저 재생한다. 이렇게 해서 memoize의 hit/miss 수가 행 단위 조인과 같다. 행이 두 묶음에 나뉜 바깥 행의 키는 등록하지 않는다(다음에 다시 계산될 뿐이다). 버린 안: memoize가 스스로 꺼질 때까지 쌓지 않기(키가 반복되는 질의는 끝까지 묶이지 않는다), 바깥 키 하나마다 묶음 닫기(fan-out이 작으면 묶음이 OID 몇 개로 끝난다).
8. **묶지 않는 것:** 첫 스캔에 직접 붙은 상관 부질의, 상관 부질의가 붙은 단계 아래의 조인 단계, FOR UPDATE, 안쪽이 커버링 스캔이거나 키 limit, multi range optimization, index skip scan인 단계.

시도하고 접은 것(MAP E38): 버퍼에 없는 페이지를 가진 바깥 행만 미루고 나머지는 바로 조인하는 형태. 결과 순서가 버퍼 상태에 따라 바뀌고, TPC-H Q7/Q9/Q20의 cold 시간과 hot 명령어 수가 지금 형태와 같거나 나빴다.

하지 않은 것: 인덱스 클러스터링 통계로 묶을지 정하기(CUBRID에 그 통계가 없고, 실행 중 back-off가 대신한다), 여러 문장이 나눠 쓰는 미리 읽기 예산(힌트 자체의 문제, CBRD-28031), 페이지가 도착하는 대로 행을 내는 모드(힌트 형태에서는 순서를 바꿔 얻을 것이 없다).

검증: `docs/tla/CBRD-28032/`의 `BatchJoin`(TLC와 Apalache IndInv)과 `BatchChain`(TLC만, IndInv 없음), 결과는 MAP의 Result. 구현은 `3b46fac34`(부질의), `0b92ed687`(semi/anti), `569df9ac4`(걸친 묶음), `c01d1edae`(묶음 안 반복 키), `900e20c71`(memoize 단계의 부질의 묶음). memoize 단계의 부질의 묶음은 모델에 없고 실행 확인만 있다.
