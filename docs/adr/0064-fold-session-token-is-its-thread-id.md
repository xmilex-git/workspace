# 폴드 세션의 토큰은 세션 스레드의 커널 스레드 id다

develop에서 드라이버가 접속 응답으로 받는 CAS pid는 호스트에서 유일하다. 드라이버는 질의 취소(QC/X1)와 상태 조회(ST)에 그 값을 실어 보내고, 브로커는 그 pid의 CAS를 찾는다. CAS 폴드(CBRD-27430, PR 7837)에는 세션마다의 프로세스가 없어서, B1a까지는 서버가 세션에 1부터 센 일련번호를 토큰으로 줬다. 한 브로커 뒤에 DB가 둘이면 두 서버의 토큰이 같은 값이 되기 쉽고, 요즘 JDBC의 취소(X1)는 클라이언트 포트를 싣지 않아 브로커가 IP만으로 후보를 고른다. 같은 클라이언트가 두 DB에 붙어 있으면 후보가 둘이 되고 브로커는 취소를 거절했다(임의의 세션을 고르지 않기 위해). develop에서는 되던 취소가 안 되는 것이다.

결정(사용자, 2026-11-18): 세션의 토큰은 그 세션을 돌리는 스레드의 커널 스레드 id(`gettid`)다. 살아 있는 두 스레드는 호스트에서 같은 id를 갖지 않으므로 두 DB의 세션 토큰이 겹치지 않고, 취소는 develop처럼 한 세션을 찾는다. 숫자의 모양도 pid와 같은 번호 공간이다.

따르는 것:

- 서버는 핸드오프를 받으면 세션 스레드를 먼저 만들어 세워 두고, 그 id로 세션을 등록해 HANDOFF_ACK를 보낸 뒤에 스레드를 풀어 세션을 시작시킨다(`adoption.cpp` `handle_handoff`, `session_thread_run`). ACK보다 세션이 먼저 도는 일은 여전히 없다(B1a의 `SHSpawn`은 이제 세워 둔 스레드를 푸는 일이다). 스레드를 못 만들면 등록 전에 거절한다.
- 토큰은 스레드가 끝난 뒤 다른 세션에 다시 쓰일 수 있다. 다른 서버의 세션이 같은 값을 받았는데 브로커가 앞 세션의 SESSION_END를 아직 읽지 않았으면 토큰 표에 같은 값이 둘 있게 된다. 표는 계속 채널(세대)로 항목을 가르고, 요청이 두 항목에 맞으면 취소를 보내지 않는다(`TokenTable` 모델의 `NoAmbiguousPick`).
- 같은 서버 안에서도 토큰은 다시 쓰인다. 브로커가 토큰 표에서 포트를 비교한 뒤 서버가 중단을 걸기 전에 그 세션이 끝나고 다른 세션이 같은 스레드 id를 받을 수 있으므로, 취소·상태 요청은 클라이언트 포트와 세션 id를 서버까지 싣고 가고(`session_ref_body`) 서버가 지금 그 토큰을 가진 세션과 다시 비교한다(`binding_is_named_by`). `TokenTable` 모델의 `no_port_check` mutant가 이 구멍이다.
- **그 번호에 `kill`을 보내면 안 된다.** develop에서는 `broker status`의 PID에 시그널을 보내 CAS 하나를 죽일 수 있었지만, 스레드 id에 보낸 시그널은 그 스레드가 속한 `cub_server` 프로세스 전체에 간다. 세션을 끝내는 방법은 `KILL TRANSACTION`과 `cubrid broker reset`이다. 매뉴얼과 QA test.md에 적는다.

## Considered Options

- **무작위 토큰(1..2^31-1)**: 채택하지 않음 — 취소 동작은 같지만 숫자가 pid처럼 보이지 않는다. 대신 `kill` 위험이 없고 핸드오프 순서를 안 바꾼다는 장점이 있었다.
- **서버별 일련번호 유지**: 기각 — DB 둘 + 같은 클라이언트 IP + 포트 없는 취소에서 취소가 거절된다.
- **후보 채널 모두에 취소를 보내고 서버가 세션 id로 거르기**: 기각 — 세션 id도 서버별 일련번호라 (토큰, 세션 id)가 함께 겹칠 수 있다.
