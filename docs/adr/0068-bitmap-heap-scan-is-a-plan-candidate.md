# bitmap heap scan은 계획 후보이고, bitmap이 들어간 계획은 따로 보관하며, 비용은 직렬 기준으로 계산한다

ADR 0067은 옵티마이저가 계획을 다 고른 뒤 그 안의 인덱스 스캔마다 bitmap heap scan 여부만 정하도록 했다(`qo_to_xasl`의 `qo_plan_decide_bitmap_heap`). 그래서 순차 스캔이 이긴 범위에서는 bitmap이 뽑히지 않았고, bitmap의 비용이 조인 순서에 들어가지 않았다. 이 문서는 그 부분을 바꾼다.

사용자 결정(2026-11-24 "bitmap을 경로 후보로 올립니다", 2026-11-25).

## 결정

- **쌍둥이 계획.** 인덱스 범위 스캔의 계획을 만들 때 bitmap heap scan이 키 순서 조회보다 싸면 힙을 bitmap으로 읽는 계획을 하나 더 만든다. 비용은 키 순서 계획의 비용에서 그 차이를 뺀 값이고 순서가 없다.
- **따로 보관.** bitmap heap scan이 들어간 계획은 `QO_INFO.best_bitmap`에 둔다. 기존 벡터는 그대로이므로 bitmap을 쓸 수 없는 자리(nested loop join과 merge join의 안쪽, 순서가 필요한 입력)는 전과 같은 계획을 고른다. 조인은 bitmap 계획을 바깥이나 hash join 입력으로 써서 한 번 더 만든다.
- **판정은 한 번.** 계획 선택 뒤의 판정은 없앴다. 문장 단위 조건은 쌍둥이 계획을 만들지 말지로 옮겼다.
- **예외 두 개를 뺐다.** LIMIT이나 `inst_num ()`으로 중간에 멈출 수 있는 문장은 hash join 아래의 스캔도 키 순서로 읽는다. merge join의 입력은 bitmap으로 읽지 않는다. 둘을 유지하려면 조인 계획마다 "아직 끝까지 읽혀야 하는 bitmap이 있는가"를 들고 다니는 벡터가 하나 더 필요했다.
- **정렬을 생략하는 자리는 키 순서를 지킨다.** (2026-11-25 추가, 사용자: "정렬생략은 bitmap 하면 안되자나") 세 곳에서 지킨다. (1) 인덱스 키 순서가 분석 함수 하나의 정렬이라도 덮으면 그 인덱스 스캔에는 쌍둥이 계획을 만들지 않는다. 조인 안의 스캔과 파티션된 테이블도 같다. (2) bitmap이 없는 계획 중 최선이 ORDER BY나 GROUP BY 정렬을 생략하거나 multi range optimization이면, 비용이 더 싼 bitmap 계획이 있어도 바꾸지 않는다. bitmap 계획의 비용은 그 위에 다시 생기는 정렬과 LIMIT으로 일찍 멈추는 효과를 담지 않기 때문이다. (3) XASL 생성은 bitmap heap scan을 정렬을 덮는 스캔으로 세지 않는다((1)이 놓친 모양이 있어도 틀린 순위 대신 정렬을 한다).
- **계층 질의의 반복 스캔은 후보가 아니다.** 부모 행마다 한 번씩 도는 스캔이라 상관 부질의와 같이 쌍둥이 계획을 만들지 않는다(`PT_SELECT_INFO_HQ_ITERATION`).
- **비용은 직렬 기준.** 시작 비용에 병렬 워커 수를 곱하지 않는다. 병렬 스캔의 워커 수는 계획 선택 뒤에 정해지고, 옵티마이저는 병렬을 비용에 넣지 않는다.
- **상수는 그대로.** MARK 0.24, LOOKUP 1.92, PAGE 1.39, RECORD 0.12, START 340, SECTOR 0.5.

## 검토한 것

- **행당 상수를 올림.** 개발 호스트(NVMe, 직렬, 콜드, 3회)에서 페이지당 243행이고 흩어진 테이블은 실제 경계가 5~7%인데 20%까지 bitmap을 골라 1.24~1.35배 느렸다. 상수를 약 14로 올리면 이 테이블은 맞지만 행이 넓고 모여 있는 테이블이 10% 범위에서 순차 스캔을 골라 약 1.7배 느려지고(추정), bitmap 대 키 순서 조회 경계도 깨진다. 통계에 키 순서와 힙 순서의 상관이 없어 한 상수로 양쪽을 맞출 수 없다. 그대로 두었다.
- **`cost_heap_fetch_per_oid`에 연동.** bitmap heap scan은 OID마다 힙 페이지를 다시 찾아가지 않으므로 그 파라미터가 매기는 동작이 없다. 기각.

## 따라오는 것

- 순차 스캔으로 돌던 중간 범위가 bitmap heap scan으로 바뀐다(800만 행 테이블의 5% 범위: 1,374ms → 500ms, 같은 실측).
- 병렬 인덱스 스캔이 bitmap으로 넘어가는 경계가 직렬과 같아진다(약 235행).
- TC 정답 3개가 바뀌었다(cubrid-testcases `9763f360d`: cbrd_26722_index, cbrd_26889 3번, cbrd_27404).
- `d79e09f012`는 위 (1)을 "인덱스가 모든 분석 함수의 정렬을 덮는 단일 테이블"로만 지켜서, 분석 함수 둘 중 하나만 덮이는 질의와 NL join 바깥 스캔 위의 분석 함수에서 순위가 틀렸고(20,004행 중 123곳), ORDER BY를 생략하던 계획을 bitmap + 정렬로 바꿨다(shell TC cbrd_25080). 같은 날 고쳤다.
- 파티션된 테이블에서 분석 함수의 정렬을 생략하면 develop도 순서가 어긋난다(같은 데이터에서 3곳). 이 변경은 그 계획을 develop과 같게 두므로 그대로 남는다. 별도 결함이다.
- 모델: 계획 선택은 `docs/tla/CBRD-28032/`의 모델 밖이다(MAP E51). 실행 검증은 MAP의 "Runtime checks"에 있다.
