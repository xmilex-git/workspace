# 전체 범위 묶음은 공유 섹터 비트맵 하나에 atomic OR로 표시하고, 상한을 넘으면 페이지 단위로 표시한다

인덱스 조건 하나로 많은 행을 찾는 non-covering 스캔은 찾은 행마다 힙 페이지를 한 장씩 읽고 기다린다. 전체 범위 묶음(PostgreSQL의 bitmap heap scan)은 키 범위의 OID를 먼저 전부 표시한 뒤 힙을 파일 순서로 한 번씩만 읽는다. 이 문서는 그 표시를 어디에 어떻게 하는지를 정한다.

사용자 결정(2026-11-10 그릴링 D25~D33, D36, D37).

- 스냅샷을 받은 뒤 힙의 섹터 목록을 한 번 받는다. 목록 밖 페이지의 OID는 버린다. 그 페이지의 행은 스냅샷이 보지 못하는 트랜잭션의 것이다(CBRD-27967이 병렬 힙 스캔에서 고친 순서와 같다).
- 인덱스 단계는 지금의 병렬 인덱스 스캔이다. 워커들은 힙을 조회하지 않고, 찾은 OID를 **공유 섹터 비트맵 하나**에 atomic OR로 표시한다. 비트맵 안에는 섹터 정보가 없다. 바깥의 섹터 목록 순서가 비트의 위치를 정한다.
- 모든 인덱스 워커가 끝난 뒤에만 힙 단계가 시작한다. 힙 단계 워커는 섹터를 하나씩 잡아 표시된 행을 읽고, 가시성과 데이터 필터를 확인한다.
- 비트맵의 메모리 상한은 새 파라미터 `index_scan_oid_bitmap_size`다(기본 16MB, 세션에서 바꿀 수 있음). 처음에는 `max_hash_list_scan_size`를 쓰기로 했으나, 해시 테이블과 용도가 달라 따로 두었다(2026-11-11). 행 단위인지 페이지 단위인지는 **스캔을 열 때 한 번** 정한다. 섹터 목록을 표시 전에 받으므로 행 단위 비트맵의 크기(섹터 수 × 64페이지 × 페이지당 폭)를 그때 안다. 스캔 도중에는 바꾸지 않는다.
- 페이지당 폭은 상한에서 역산한다: min(페이지의 슬롯 상한, 상한의 비트 수 ÷ 페이지 수). 64의 배수로 내리지 않는다(2026-11-11 측정 뒤 바꿈: 내리면 lineitem이 64비트가 되어 슬롯 64 이상의 행이 있는 페이지를 통째로 다시 읽고, 핫 실행이 0.53초에서 2.5초가 된다). 64에 못 미치면 **페이지 단위로만 표시**한다. 폭 이상의 슬롯 번호를 가진 OID는 그 페이지를 페이지 단위로 표시한다. 힙 단계는 그 페이지의 모든 행을 읽고 인덱스 조건(키 범위, 키 필터)을 힙 행에서 다시 확인한다.
- 전체 범위 묶음을 쓸지는 계획 생성 때 정한다(non-covering, 순서 불필요, LIMIT으로 일찍 끝나지 않음, 찾을 행 수 추정이 기준 이상).

조인과의 경계: 전체 범위 묶음은 스캔 하나의 키 범위에 대한 것이다. 조인 전체의 OID를 비트맵에 모으면 어느 바깥 행의 짝인지가 사라져 다시 조인해야 하고, 그것은 해시 조인이다. 중첩 루프 조인은 OID 버퍼 크기의 묶음만 다루고(배치 조인, 모델 `BatchJoin`), 바깥 행이 아주 많은 조인은 해시 조인의 영역으로 둔다.

## Considered Options

- **워커별 비트맵을 힙 단계에서 병합**(처음 결정, D32/D33): 표시할 때 동기화가 없다. 기각한 이유는 메모리다. 인덱스 순서와 힙 순서가 무관한 테이블에서는 워커마다 거의 모든 섹터를 건드려 비트맵이 워커 수만큼 생긴다(슬롯 상한 1,360비트 기준으로 lineitem 11.7GB, 워커 4개에 약 500MB).
- **상한 없이 항상 행 단위**(처음 결정, D27/D29): 재확인이 필요 없어 XASL이 단순하다. 기각한 이유는 큰 테이블에서 비트맵이 힙 크기에 비례해 커지는 것이다.
- **만드는 도중에 넘으면 바꾸기**(PostgreSQL의 `tbm_lossify`: 닿은 페이지만 엔트리를 두고, 엔트리 수가 한도를 넘으면 일부를 페이지당 1비트로 바꾼다): 선택도가 높은 조건은 큰 테이블에서도 행 단위로 남는다. 기각한 이유는 크기를 처음에 다 알기 때문이다. 여러 워커가 atomic OR로 표시하는 중에 엔트리를 바꾸려면 동기화가 필요하다(PostgreSQL은 프로세스 하나가 비트맵을 만든다).
- **행 비트를 섹터가 처음 닿을 때 할당하고, 예산이 차면 그 뒤 섹터는 페이지 단위**: 도중 변환이 없고 메모리가 닿은 섹터에 비례한다. 같은 이유로 기각했다.
- **폭을 슬롯 상한으로 고정**(PostgreSQL의 `MaxHeapTuplesPerPage`): 폭을 넘는 슬롯이 없다. PostgreSQL은 닿은 페이지만 엔트리를 두지만 여기서는 모든 페이지가 폭만큼 차지한다(lineitem 약 73만 페이지에 129MB). 기본 8MB가 745MiB 테이블까지만 덮는다.
- **폭을 64나 128로 고정, 또는 힙 헤더의 행 수 추정에서**: 테이블이 상한을 조금만 넘어도 전부 페이지 단위가 된다(lineitem은 128비트에 11.7MB).
- **폭을 넘는 OID를 별도 목록에**: 워커 사이의 잠금과 할당이 생기고 힙 단계가 구조 두 개를 본다. 재확인 술어는 어차피 XASL에 항상 있다.
- **temp 파일에 비트열로 저장**: 흩어진 비트 쓰기가 temp 페이지 I/O가 된다. 페이지 단위 표시가 같은 목적을 메모리 안에서 이룬다.
- **OID 목록을 모아 정렬**: 정렬 비용과 목록 메모리. 섹터 순서 비트맵은 정렬이 필요 없다.
- **인덱스 단계를 스레드 하나로**(D31, 철회): 병렬 인덱스 스캔은 covering 스캔과 GROUP BY skip 병합에도 쓰이므로 남긴다.

## Consequences

- 페이지 단위 표시에서는 인덱스 조건을 힙 행에서 평가해야 한다. XASL이 그 술어를 함께 가진다.
- 표시는 비트맵 워드에 대한 atomic OR 하나여야 한다. 읽고 쓰는 두 단계로 나누면 다른 워커의 비트를 잃는다(모델의 변이 `nonatomic-or`).
- 페이지 단위로 표시된 페이지에서 행 단위 비트를 함께 따라가면 같은 행을 두 번 반환한다(변이 `both-paths`).
- 인덱스 항목이 남아 있는 삭제된 행이 표시될 수 있으므로 힙 단계의 가시성 확인은 생략할 수 없다(변이 `no-heap-visibility`).
- 힙 단계는 표시된 페이지를(행 단위든 페이지 단위든) 행을 읽기 전에 "반납됐을 수 있는 페이지"로 한 번 fix하고 마지막 행까지 잡고 있는다. 행 조회는 페이지가 반드시 있다고 보고 fix한다(반납된 페이지면 디버그 빌드는 assert로 멈추고 릴리스 빌드는 오류를 지우고 건너뛴다). 그래서 표시한 뒤 vacuum이 비우고 반납한 페이지는 이 fix에서 걸러 페이지째 건너뛴다(변이 `fix-freed`, `no-freed-skip`). 스캔 하나가 스냅샷 하나만 쓰는 동안에는 리프의 가시성 확인이 그런 행을 표시하지 않으므로 이 경로에 닿지 않는다. 닿는 것은 스캔 도중 스냅샷이 바뀔 때다(READ COMMITTED에서 행마다 부르는 저장 프로시저의 SQL).
- 결과의 행 순서는 정해지지 않는다. 순서가 필요한 계획은 OID 버퍼 크기의 묶음(키 순서 유지)을 쓴다.
- MVCC를 쓰지 않는 클래스는 대상이 아니다(섹터 목록 밖 OID를 버리는 근거가 스냅샷이다).
- 판정 기준이 표시된 양이 아니라 테이블 크기다. 기본 16MB에서 16K 페이지 약 98,000장(1.5GiB)까지는 전폭(1,365비트)이고, 그보다 크면 폭이 줄어 폭 이상의 슬롯에 있는 행이 페이지 단위가 되며, 2,097,152장(32GiB)을 넘으면 조건이 몇 행만 골라도 전부 페이지 단위다. lineitem(약 73만 장, 장당 약 82행)은 8MB에서도 93비트라 모든 행이 행 단위로 표시됐다(측정: trace의 `bitmap: 93`). 읽는 페이지는 같고, 표시된 페이지의 모든 행에 가시성 확인과 인덱스 조건 재확인이 든다.
- 폭이 전폭보다 작은 테이블은 스캔마다 상한만큼 할당하고 0으로 채운다. 통계로 폭에 상한을 더 두는 것은 측정으로 필요가 보이면 한다.

- 힙 단계는 모든 페이지가 표시된 섹터만 빼고 표시된 페이지를 OS에 미리 알린다(SSD 1%: 27초 → 12초).

## 2026-11-11 결정: 누가 고르고 어떻게 보이나 (MAP D42, D43; CBRD-28032)

밖에서 쓰는 이름은 bitmap heap scan이다(JIRA, trace, 플랜 출력). 이 문서의 "전체 범위 묶음"과 같은 것이다.

- **옵티마이저가 고른다.** 실행 계획을 만들 때 정하고(D26: non-covering, 인덱스 순서를 쓰지 않음, LIMIT 등으로 일찍 끝나지 않음, 예상 행 수가 기준 이상), 실행 중에는 바꾸지 않는다. 켜고 끄는 시스템 파라미터는 없다(`bitmap_heap_scan`은 없앤다). 지금 구현은 서버가 스캔을 열 때, 서버가 병렬 인덱스 스캔으로 올린 스캔 안에서 정한다(`input_handler_index::bitmap_init_on_main`). 이것을 계획 시점으로 옮긴다.
- **워커가 없어도 실행한다.** 옵티마이저는 병렬 여부를 모른다(서버가 실행 때 정한다). 그래서 한 스레드가 두 단계를 그대로 실행하는 경로가 있어야 한다. 기존 인덱스 스캔으로 되돌아가는 길은 만들지 않는다. 이 경로는 아직 없다.
- **기준 값은 실측으로 정한다.** 한 스레드 경로를 만든 뒤 작은 행 수(0.01%, 0.1%, 1%)에서 양쪽을 잰다. 지금은 60만 행 이상만 재 봤다.
- **접근 명세를 나눈다.** 힙 명세가 인덱스 명세를 자식으로 갖는다(PostgreSQL의 Bitmap Heap Scan 아래 Bitmap Index Scan). `spec_list`의 형제로 두지 않는다. 형제는 "차례로 각각 스캔한다"(상속 클래스)는 뜻이다. 자식은 지금 하나다.
- **SQL 힌트 두 개**(강제, 금지)를 둔다. 파라미터가 없으면 작은 테이블의 TC가 이 경로를 탈 방법이 없기 때문이다. 이름은 정하지 않았다.
- **trace는 두 스캔으로 찍는다**(구현됨, fork `CBRD-28005-aio` `5eb88d442`): 인덱스 스캔 줄 아래에 `SCAN (bitmap heap: <클래스>)` 줄. 인덱스 줄의 시간과 fetch는 힙 단계를 뺀 값이고 lookup 묶음이 없다. JSON은 `"bitmap heap"` 객체다. 예전의 `bitmap: N` 토큰은 없다.
- **플랜 출력**에는 `INDEX SCAN` 줄 위에 `BITMAP HEAP SCAN (클래스)` 줄을 추가한다.
- 메모리 상한 `index_scan_oid_bitmap_size`는 그대로 둔다.
