# 선언 타입이 있는 NULL 과 EXECUTE 열 정보는 버전을 확인하지 않고, 드라이버·브로커·엔진이 같은 버전이라고 가정한다

CBRD-27679 는 JDBC `setNull (i, sqlType)` 과 CCI `cci_bind_param` 의 NULL 이 지닌 선언 타입을 엔진까지 지키고(타입 바이트 + 길이 0), 서명 플랜을 컴파일한 EXECUTE 응답에 열 정보를 더한다. 처음 사양은 "통신 형식 불변, 한쪽이 옛 버전이면 지금처럼 동작"이었으나, 게이트웨이 CAS(`cgw_set_bindparam`)는 길이를 보지 않고 타입대로 값을 읽어 타입 INT + 길이 0 을 NULL 이 아닌 엉뚱한 값으로 바인드하므로 그 전제가 틀렸다. 2026-10-20 그릴링(Q4, Q7)에서 사용자는 버전 게이트 대신 "모든 구성 요소가 새 버전"을 가정하기로 정했다: 드라이버는 브로커 버전을 보지 않고 선언 타입이 있는 NULL 을 보내며, 브로커(CAS, CGW)는 드라이버 버전을 보지 않고 열 정보 항목을 보낸다. 이 가정은 CBRD-27679, 그 엔진 서브태스크, APIS 두 이슈(JDBC, CCI)의 본문에 모두 적는다.

## Considered Options

- **새 프로토콜 버전(V14) 게이트**: 기각. 드라이버가 V14 이상 브로커에만 보내고 브로커가 V14 이상 드라이버에만 열 정보를 보내는 안. 사용자 결정으로 버전 확인을 두지 않는다.
- **브로커 기능 플래그**(CBRD-27389 의 `BROKER_SUPPORT_SESSION_CANCEL` 방식): 같은 이유로 기각.
- **CGW 만 고치고 통신 형식 불변 유지**: 이미 배포된 CGW 브로커에 새 드라이버가 붙으면 잘못된 값이 바인드되고, 열 정보 항목은 옛 드라이버가 해석하지 못하므로 "한쪽만 새 버전이면 지금처럼"을 지킬 수 없다.

## Consequences

- 이전 버전과 섞어 쓰는 조합(옛 드라이버 + 새 브로커, 새 드라이버 + 옛 브로커·CGW)은 지원하지 않는다. CTP 의 드라이버·서버 혼합 호환 테스트(`util_compat_test.sh`, `run_compat_jdbc.sh`)에서 이 조합의 실패는 예상된 결과다.
- 선례: CBRD-27389 세트(APIS-1112/1113)도 버전 확인 없이 나갔다가 APIS-1127 에서 "PROTOCOL_V13 이상 브로커에만" 확인을 뒤에 붙였다. 같은 요구가 다시 오면 이 ADR 을 뒤집는 결정으로 다룬다.
- CUBRID/cubrid develop 은 엔진과 드라이버가 한 번에 바뀌어야 한다: 엔진 서브태스크 PR 이 `cubrid-jdbc`, `cubrid-cci` submodule 포인터를 두 APIS 이슈가 반영된 커밋으로 함께 올리고, submodule 봇의 bump PR 은 닫는다(CTP sql 은 설치본의 JDBC 로 돈다).
