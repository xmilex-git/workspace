## D1. 한 워커가 고유 키 위반으로 실패하면 다른 워커가 오류 없이 실패해 assert

### 무엇이 틀렸나

`loaddb --no-logging-index`의 병렬 인덱스 빌드에서 고유 키가 중복이면 optdebug 서버가 `ASSERT_ERROR ()`로 죽었습니다. 30000행에서 가장 작은 키가 중복이면 첫 리프에서(3회 중 2회), 3,000,000행이면 가운데 키가 중복이어도 다음 리프를 받을 때 걸렸습니다(3회 중 1회). release는 -670으로 끝납니다.

### 원인

- 병렬 빌드의 워커는 페이지를 모두 `bt_load_provider_claim_page ()`에서 받습니다. 자기 몫이 비면 리더에게 리필을 요청하고 기다립니다.
- 한 워커가 실패하면 `bt_load_worker_epilogue ()`가 그 오류 코드를 `provider->first_error`에 걸고 모든 워커를 깨웁니다. 페이지를 기다리던 다른 워커는 그 코드를 그대로 돌려받는데, 그 오류는 *다른 스레드의* 오류라서 이 워커 스레드에는 오류가 설정돼 있지 않습니다.
- 호출하는 쪽은 모두 "실패면 이 스레드에 오류가 있다"를 assert합니다(첫 리프, `btree_proceed_leaf`, overflow 페이지 등 여러 곳).

### 고친 방식과 이유

```c
/* Another worker or the leader failed first and holds the build's error; this worker only stops.  Every
 * caller expects a failed claim to leave an error in this thread, so set one.  Only the first failure's
 * error reaches the leader (bt_load_worker_epilogue ()). */
pthread_mutex_unlock (&provider->mtx);
er_set (ER_ERROR_SEVERITY, ARG_FILE_LINE, ER_BTREE_LOAD_FAILED, 0);
return ER_BTREE_LOAD_FAILED;
```

- **호출자 계약을 한 곳에서 지킵니다.** 호출 위치가 여러 곳이라 각각 고치기보다, 페이지를 나눠 주는 함수 하나가 "실패면 오류 설정" 계약을 지키게 했습니다.
- **`first_error`가 아니라 `ER_BTREE_LOAD_FAILED`를 돌려줍니다.** 이 워커는 남의 실패 때문에 멈출 뿐이라 자기 오류가 따로 없습니다. 사용자에게 보일 오류(-670 등)는 처음 실패한 워커의 것이 리더로 따로 전달되므로(아래), 멈춘 워커는 "빌드가 실패했다"는 일반 코드만 갖습니다.

## D1의 오류 전달 경합: 워커가 실행 중인 리더의 오류 컨텍스트에 직접 쓰면 안 됨

### 무엇이 틀렸나

D1의 assert를 없애자, 5회 중 1회 메인 스레드가 오류 없이 실패를 돌려받아(`sbtree_load_index`의 assert) 다시 죽었습니다. develop optdebug에서는 같은 경합으로 `cuberr::er_message::swap (this=0x0)`에서 SIGSEGV가 나기도 했습니다(shell TC의 수정 전 결과).

### 원인

실패한 워커가 `btsort_put_result_index_leaf ()`에서 자기 오류를 리더의 오류 컨텍스트에 직접 swap했습니다. 그런데 그 시점에 리더는 멈춰 있지 않고 다른 워커의 페이지 리필을 할당하고 있습니다. optdebug의 `file_header_sanity_check`가 할당 중에 리더의 오류 스택을 push/pop하면, swap된 오류가 push된 층에 들어갔다가 pop과 함께 버려집니다.

### 고친 방식과 이유

- `bt_load_provider`에 `first_error_msg`(`cuberr::er_message`)를 두고, `first_error`를 처음 거는 워커가 `bt_load_worker_epilogue ()`에서 자기 오류를 거기에 보관합니다.
- 리더는 `bt_load_provider_service_loop ()`에서 *모든 워커가 끝난 것을 본 뒤* 자기 스레드에서 그 오류를 가져갑니다(`cuberr::context::get_thread_local_error ().swap (*provider->first_error_msg)`). 이 시점엔 실행 중인 워커가 없으므로 경합이 없습니다.
- `btsort_put_result_index_leaf ()`가 리더 컨텍스트에 직접 swap하던 코드(`px_error_published` 판정 포함)는 지웠습니다. 남긴 주석에 "여기서 리더 컨텍스트에 쓰면 리필 중인 리더와 경합한다"는 이유를 적었습니다.
- **parallel scan과 같은 방식입니다.** px_scan은 워커가 오류 메시지를 보관 장소로 옮기고, 리더가 워커를 기다린 뒤 자기 스레드로 가져옵니다. 처음에는 "오류를 넘기는 워커를 `first_error`를 건 워커 하나로 정하는" 좁은 수정을 생각했는데, 그래도 리더가 실행 중이라는 문제가 남습니다. 사용자가 "px scan 쪽 방식이 맞는 거야"라고 해서 보관 후 채택 방식으로 바꿨습니다.
- `er_message`는 생성자에서 로깅 플래그를 참조로 받으므로, 보관용 메시지가 로그를 남기지 않게 파일 범위 상수 `bt_load_er_message_logging = false`를 두었습니다. 할당 실패 경로와 `bt_load_provider_close`에서 지웁니다.

## D2. DESC PK를 참조하는 FK: 병렬 빌드에서 마지막 리프가 NULL

### 원인

- FK와 참조 PK의 정렬 방향이 다르면 `btree_load_check_fk ()`는 FK 인덱스의 마지막 리프(`load_args->leaf.vpid`)부터 거꾸로 검사합니다.
- 로깅 빌드는 `btree_build_nleafs ()` *전에* 검사하므로 이때 `leaf.vpid`가 마지막 리프입니다.
- 병렬 빌드는 `bt_load_px_join_finalize ()`가 non-leaf까지 다 만든 *뒤에* 검사합니다. `btree_build_nleafs ()`는 `leaf.vpid`를 리프 체인 끝까지 따라가 NULL로 남기므로, NULL 페이지부터 검사를 시작했습니다. 정방향 검사는 `vpid_first_leaf`를 쓰므로 정상이었습니다.

### 고친 방식과 이유

- join이 마지막 shard의 마지막 리프를 리더의 `report_last_leaf_vpid`에 남기고, `btree_load_check_fk ()`는 병렬 빌드(`px_outcome == BT_PX_TREE_DONE`)일 때 그것을 씁니다.
- 조사 때 두 안을 봤습니다. (a) join이 마지막 리프를 기록하기, (b) 병렬 빌드의 FK 검사를 join 안, `btree_build_nleafs ()` 전으로 옮겨 로깅 빌드와 순서를 맞추기. (a)는 이미 shard마다 채우는 `report_last_leaf_vpid` 필드(리더에서는 안 쓰던)를 다시 쓰는 한 줄이고, 검사 순서와 join 구조를 바꾸지 않습니다. 그래서 (a)를 택했습니다.
- 구조체 주석에 "join이 빌드의 마지막 리프를 리더의 `report_last_leaf_vpid`에 남긴다"를 더해 필드의 새 용도를 적었습니다.

## D3. (범위 추가, develop 기존 결함) 역방향 FK 검사가 앞 리프의 시작 슬롯을 틀리게 잡음

### 원인

```c
*slot_id = is_desc ? *key_cnt : 1;            /* (old) key_cnt는 아직 방금 떠난 페이지의 키 수 */
local_header = btree_get_node_header (thread_p, page);
*key_cnt = btree_node_number_of_keys (thread_p, page);
```

`btree_advance_to_next_slot_and_fix_page ()`가 역방향으로 앞 리프로 넘어갈 때, 시작 슬롯을 *새 페이지의* 키 수가 아니라 *방금 떠난 페이지의* 키 수로 잡았습니다. 2017년부터 있던 코드입니다.

- 앞 페이지 키가 더 많으면 그 페이지의 위쪽 키를 검사하지 않습니다. 그 범위에 고아 값이 있어도 FK가 만들어집니다(release 포함). 예: PK `(id desc)` 30000행, 고아 59819 → develop에서 FK가 만들어지고 고아 행 1개가 남음. ASC PK 쌍둥이는 -922로 거부.
- 앞 페이지 키가 더 적으면 없는 슬롯을 읽습니다. optdebug는 `btree_is_slot_visible ()`의 `assert_release`로 abort, release는 유효한 데이터인데도 "Internal error: pageptr = ... is not fixed."로 FK 생성이 실패합니다.

### 고친 방식과 이유

새 페이지의 키 수를 읽은 *뒤에* 시작 슬롯을 정하도록 줄 순서만 바꿨습니다. 주석에 "앞 페이지 키 수는 클 수도 작을 수도 있다"를 적었습니다.

**왜 이 PR에 넣었나:** `--no-logging-index`와 무관한 일반 FK 생성의 결함이지만, 병렬 빌드는 shard마다 마지막 리프가 덜 찬 채로 끝나고 다음 shard의 첫 리프는 대개 꽉 차 있어서, 역방향으로 shard 경계를 넘을 때마다 이 조건이 생깁니다. 그래서 D2만 고치면 바로 D3에 걸리고, D2는 D3 없이 고칠 수 없습니다. 사용자 결정으로 별도 이슈 없이 이 PR에 넣고 JIRA에 범위 추가 comment를 남겼습니다.

**백포트:** 같은 코드가 release/10.2부터 release/11.4까지 있어 백포트가 필요할 수 있습니다(PR Remarks).
