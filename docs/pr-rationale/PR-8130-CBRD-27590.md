## 1. 어떤 SQL이 틀렸나

```sql
create table t_upd (id int primary key, v int);
insert into t_upd select rownum, rownum from db_class limit 10;
create table t_one (k int);
insert into t_one values (1);
create or replace function f_del (p int) return int as begin delete from t_upd where id = p + 1; return p; end;
commit;
select /*+ ordered use_nl */ a.id, a.v, f_del (a.id) from t_upd a, t_one o;
select id from t_upd order by id;
```

- CBRD-27041 이전(기대): 반환 1, 3, 5, 7, 9 / 남은 행 1, 3, 5, 7, 9.
- develop: 지워진 2–10도 모두 반환되고, 그 행마다 함수가 다음 행을 지워 1만 남음.
- 함수가 다음 행을 UPDATE하면 바뀌기 전 값이 반환됩니다. 여러 페이지 테이블에서는 페이지 경계에 걸린 행만 바뀐 값을 보아서 결과가 행의 배치에 따라 달라집니다(600행에서 develop 10행, 수정 전 599행).
- `db_serial`을 선행 테이블로 읽으며 select 목록에서 `NEXT_VALUE`를 불러도 같습니다.

## 2. 원인

- CBRD-27041은 NL 조인 선행 테이블 같은 level 0 힙 스캔이 페이지에 들어갈 때 페이지 복사본을 만들고, 그 페이지의 나머지 행을 복사본에서 읽게 했습니다(페이지 복사 스캔, cached scan). 행마다 fix·복사·unfix하던 비용을 없애려는 것입니다.
- CUBRID MVCC에는 command id가 없어서 트랜잭션의 자기 변경은 즉시 보입니다. 그런데 복사본은 페이지에 들어간 시점의 모습이라, 같은 문장이 그 뒤에 아직 읽지 않은 행을 바꾸면(SP의 DML, 시리얼 `NEXT_VALUE`) 그 변경을 보지 못합니다.

## 3. 기대 의미를 먼저 정함: "읽는 시점 의미"

고치기 전에 "같은 문장 안의 변경을 스캔이 어떻게 봐야 하는가"를 사용자와 정했습니다(grilling).

- **읽는 시점 의미**: 스캔이 그 행에 닿았을 때의 모습을 읽는다. 수정 전 COPY 읽기의 답이고, 안쪽 힙 스캔과 힙을 읽는 인덱스 스캔이 지금도 내는 답입니다.
- PostgreSQL식 "문장 시작 시점 의미(command id)"는 안쪽 스캔과 인덱스 스캔의 develop 답까지 바꾸므로 기각했습니다.

## 4. 고친 방식: 무효화가 아니라 제외

문장 안에서 행이 바뀔 수 있는 두 경우에는 페이지 복사 스캔을 아예 쓰지 않고, CBRD-27041 이전의 행별 COPY 읽기로 돌아갑니다.

### 4.1 문장에 `PARALLEL_ENABLE`이 아닌 SP가 있으면 (`3e299d7ae`, `e7d27b61a`)

- **표시하는 곳:** XASL을 풀 때 `stx_build_sp_type`이 `PARALLEL_ENABLE`이 아닌 SP를 만나면 `xasl_unpack_info::has_sql_capable_sp`를 켜고, `stx_map_stream_to_xasl`이 그것을 루트 XASL의 `calls_sql_capable_sp`에 남깁니다. 서버가 이미 모든 SP를 풀면서 지나가는 자리라서 별도 순회가 필요 없습니다.
- **전달하는 곳:** `qexec_execute_query ()`가 이 값을 `XASL_STATE`에 담습니다. `XASL_STATE`는 모든 블록과 병렬 스캔 워커가 이미 받는 구조라서 새 인자를 늘리지 않았습니다. `qexec_deep_copy_xasl_state`도 복사합니다.
- **쓰는 곳:** `specp->cached_scan = (level == 0 && spec_level == 0 && !xasl_state->calls_sql_capable_sp);` 그리고 병렬 스캔 워커가 안쪽 스캔에 cached scan을 고르는 자리(`px_scan_task.cpp`의 `inner_cached_scan`)도 같은 표시를 봅니다. 워커 쪽을 빠뜨리면 다른 UNION arm에 SP가 있는 문장에서 워커가 여전히 페이지를 복사했습니다(`e7d27b61a`).
- **왜 문장 단위인가(블록 단위가 아니라):** 상관 하위 질의 안의 SP도, 처음 값을 쓸 때 실행되는 비상관 하위 질의(`XASL_LINK_TO_REGU_VARIABLE`) 안의 SP도 바깥 스캔 *도중에* 실행되어 그 행을 바꿉니다. 블록 단위로 좁히려면 스캔보다 먼저 끝나는 하위 질의(실체화되는 파생 테이블, CTE)만 정확히 가려내야 하는데 놓치는 경로가 생기기 쉽습니다. 사용자 결정으로 문장 단위로 하고, 실제 문제 사례가 나오면 다시 열기로 했습니다. 문장 단위 판정의 선례로 TDE 클래스 표시(`XASL_INCLUDES_TDE_CLASS`)가 있습니다.
- **왜 `PARALLEL_ENABLE` SP는 빼는가:** `PARALLEL_ENABLE` SP는 직렬 실행에서도 서버측 SQL이 런타임에 거부되므로(`pl_execution_stack_context.hpp`) 데이터를 바꿀 수 없습니다. 이 SP만 쓰는 문장은 cached scan을 그대로 씁니다.
- 레거시 메서드는 원본 질의 결과를 다 만든 뒤 `TARGET_METHOD` 스캔으로 실행되므로 스캔 도중 변경 경로가 아닙니다.

### 4.2 MVCC 비적용 클래스를 스캔하면 (`heap_file.c`)

```c
/* Rows of an MVCC-disabled class (_db_serial, ...) change in place, by this transaction or another, while the
 * scan reads the page; read them from the live page, never from a copy (CBRD-27590). */
if (copy_to_local_cache && is_queryscan && !scan_cache->mvcc_disabled_class)
```

`db_serial` 같은 클래스는 행이 제자리에서 바뀌고, 다른 트랜잭션이 바꿀 수도 있습니다. SP 표시와 상관없이 복사 버퍼 자체를 만들지 않는 것이 맞아서, 스캔 캐시를 시작하는 한 곳에서 막았습니다.

### 4.3 커버링 인덱스 읽기도 같은 판정으로 끔 (`358767e4f`)

- 같은 문장의 커버링 인덱스 스캔도 함수가 지운 행을 돌려줬습니다. 키를 미리 모아 두고 그 키로 행을 만들기 때문입니다. 이것은 CBRD-27041 이전부터 있던 동작이지만 같은 "읽는 시점 의미"를 어깁니다. 사용자가 "같이 고쳐"라고 해서 이 PR에 넣었습니다.
- `scan_open_index_scan ()`에서 `calls_sql_capable_sp`이면 `coverage_enabled = false`로 합니다. `FOR UPDATE`(`mvcc_select_lock_needed`)가 커버링을 끄는 바로 그 자리라서 같은 효과(행마다 힙을 읽음)를 냅니다.
- loose index scan은 커버링 읽기 위에서만 동작하므로(`BTS_IS_INDEX_ILS`) 함께 꺼집니다. 범위의 모든 키를 읽고, 문장의 DISTINCT나 집계는 그대로 적용되므로 답은 같습니다.

### 4.4 병렬 인덱스 워커와 trace가 실제 결정을 따르게 (`3fca48f69`, 리뷰 반영)

- 병렬 인덱스 스캔 워커의 리프 순회(`leaf_slot_walker::wire`)가 계획의 `indx_info->coverage` 대신 워커가 연 스캔의 `SCAN_IS_INDEX_COVERED`를 따릅니다. 커버링을 끈 결정과 어긋날 수 없게 하려는 것입니다.
- trace의 `loose`는 커버링이 유지될 때만 표시합니다(`coverage_enabled && ils_prefix_len > 0`).

## 6. 비용과 동작 변화 (PR Remarks)

- SP가 있는 문장은 읽기만 하는 SP여도 행별 COPY 읽기로 돌아갑니다. SP 호출 10만 번이 대부분인 NL 선행 스캔에서 release 1.005배(잡음 범위)였습니다.
- 커버링을 끄는 비용은 SP가 드물게 실행되는 큰 직렬 커버링 스캔에서 드러납니다. SP를 한 번 부르고 100만 키를 읽는 질의가 1.68배(PK 순서), 2.94배(흩어진 보조 인덱스) 느려졌습니다. 병렬 인덱스 스캔과 SP를 행마다 부르는 질의는 1.006배였습니다. SQL을 쓰지 않는 함수는 `PARALLEL_ENABLE`로 선언하면 커버링을 그대로 씁니다.
- 리뷰 대응 중 추가로 잰 값: 다른 UNION arm에 SP가 있으면 100만 키 커버링 병렬 인덱스 스캔이 0.46초 → 4.4초가 됩니다. 문장 단위 판정의 비용입니다.
- 커버링은 스캔을 열 때 끄므로 Query Plan에는 `covered: true`가 남고 Trace Statistics의 인덱스 스캔에 `(lookup time, rows)`가 나옵니다. 그래서 `cbrd_25748` Case 9, `cbrd_26522` Case 4의 trace 정답을 TC PR에서 함께 고쳤습니다(결과와 Query Plan은 그대로).

## 7. 범위 밖

- **SP가 지운 행 때문에 `LIMIT` 결과가 모자라는 문제, SP가 키를 바꾼 행이 WHERE 범위 밖인데도 나오는 문제**(리뷰 지적): develop의 힙 읽기 인덱스 스캔이 이미 같은 답을 냅니다(develop `a9940d67a` optdebug 실측). 이 PR은 커버링 읽기를 그 경로로 돌려 그 답에 맞출 뿐입니다. LIMIT 쪽 원인은 btree가 key limit에 닿으면 스캔 위치를 지우고 끝내는 데 있어서 고치려면 key limit 처리를 바꿔야 합니다. 사용자 결정으로 범위 밖으로 두었습니다.
- **SP가 인덱스 key filter에 있으면 btree 리프 래치에서 자기 대기하는 문제:** CBRD-27591(#8133)에서 다룹니다.
- **집계가 첫 행의 인자를 두 번 평가하는 문제:** 기존 workspace#417.
