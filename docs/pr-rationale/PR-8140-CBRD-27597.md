## 1. 어떤 SQL이 틀렸나

`t`가 100000행일 때 아래 두 질의가 오류 없이 행이 빠진 결과를 돌려줬습니다. 힌트 없이 기본 설정에서 나고, release와 debug 결과가 같습니다.

```sql
-- 1. 바깥 질의가 재귀 CTE를 읽는다: 200000이어야 하는데 125910
with recursive r (pad, lvl) as (select pad, 1 from t union all select pad, lvl + 1 from r where lvl < 2)
select count(*) from r;

-- 2. materialize된 CTE c2가 같은 WITH 절의 c1을 읽는다: 100000이어야 하는데 25952
with c1 as (select /*+ materialize */ pad from t),
     c2 as (select /*+ materialize */ count(*) cnt from c1)
select cnt from c2;
```

두 경우 모두 CTE 본문의 heap 스캔과 그 결과를 읽는 temp 스캔이 함께 병렬일 때만 납니다. 둘 중 하나를 직렬로 만들면(`rownum` 조건, CTE 본문에 `NO_PARALLEL_SCAN`) 정답이 나옵니다.

## 2. 원인

이 버그에는 세 가지가 함께 작용합니다.

1. **병렬 heap 스캔은 결과를 파일 하나로 합치지 않습니다.** 결과를 `mergeable list` 방식으로 모을 때는 워커마다 만든 list 파일을 결과 list id의 `dependent_list_id` 체인에 매달아 둡니다. 행 복사를 하지 않으려는 설계입니다.
2. **병렬 list 스캔은 그 체인을 따라가야 전체 페이지를 압니다.** `qfile_collect_list_sector_info`는 *자기가 읽는 list id*의 `dependent_list_id` 체인만 따라가며 읽을 섹터를 모읍니다.
3. **CTE 결과는 list id 두 개가 함께 가리킵니다.** CTE XASL의 `list_id`와 `non_recursive_part->list_id`입니다. 같은 WITH 절의 다른 CTE는 `non_recursive_part` 쪽을 읽고(`pt_to_cte_table_spec_list` 참고), 바깥 질의는 CTE XASL 쪽을 읽습니다.

`qexec_execute_cte`는 마지막에 결과를 이 두 list id 사이에 `qfile_copy_list_id (..., QFILE_MOVE_DEPENDENT)`로 복사했습니다. `MOVE`는 체인 소유권을 대상 쪽으로 넘기고 원본의 `dependent_list_id`를 `NULL`로 만듭니다. 그래서 체인이 한쪽에만 남았습니다.

- 비재귀 CTE는 `non_recursive_part` → CTE XASL로 복사하므로 `non_recursive_part`가 체인을 잃습니다. 그래서 그것을 읽는 다른 CTE(질의 2)가 첫 워커 파일만 읽었습니다.
- 재귀 CTE는 마지막에 CTE XASL → `non_recursive_part`로 복사하므로 CTE XASL이 체인을 잃습니다. 그래서 바깥 질의(질의 1)가 일부만 읽었습니다.

직렬 스캔은 tuple을 페이지 링크로 따라 읽으므로 이 체인이 필요 없습니다. 그래서 직렬로 바꾸면 정답이 나왔습니다.

## 3. 고친 방식과 이유

### 3.1 `qfile_copy_list_id`에 `QFILE_COPY_DEPENDENT` 모드 추가 (`list_file.h`, `list_file.c`)

```c
case QFILE_COPY_DEPENDENT:
  /* both list ids read the same files; each owns its dependent list ids, so either one can be cleared */
  dest_list_id_p->dependent_list_id =
    qfile_clone_list_id (src_list_id_p->dependent_list_id, false, QFILE_COPY_DEPENDENT);
```

- **왜 새 모드인가.** 두 list id가 *둘 다 살아서 읽히는* 경우는 기존 모드(`SKIP`, `MOVE`, `PROHIBIT`)로 표현할 수 없습니다. `SKIP`은 체인을 버리고 `MOVE`는 한쪽만 남깁니다. 두 쪽 모두 체인을 가져야 하므로 복사하는 모드가 필요했습니다.
- **왜 포인터를 공유하지 않고 복제하는가.** `qfile_clear_list_id`는 `dependent_list_id`를 재귀로 `qfile_clear_list_id` + `free` 합니다. 두 list id가 같은 `QFILE_LIST_ID` 구조체를 가리키면 둘째 정리에서 double free가 됩니다. 그래서 체인의 *list id 구조체*는 각자 갖고(`qfile_clone_list_id`, 재귀로 같은 모드를 넘겨 체인 전체를 복제), *list 파일*은 공유합니다. 이러면 두 list id를 어느 순서로 정리해도 안전합니다.
- **파일 해제는 바뀌지 않습니다.** list 파일은 지금처럼 CTE XASL의 list를 정리할 때 해제됩니다. `non_recursive_part`는 `qexec_clear_xasl`에서 `qfile_clear_list_id`만 받습니다(`query_executor.c:2598`). 그래서 파일이 두 번 해제되거나 먼저 해제되는 경로는 생기지 않습니다.
- **실패 경로.** 어느 단계(type list 복사, sort list 할당, 이 복제)에서 실패하든 복사가 할당한 것만 풀고 빈 list id를 남긴 뒤 `ER_FAILED`를 돌려줍니다(`exit_on_error`, 3.3 참고).
- `qfile_clone_list_id`와 `qfile_copy_list_id`는 원래 있던 함수이고 dependent mode를 이미 인자로 받습니다. 그래서 새 함수 없이 `switch`에 case 하나만 더했습니다.

### 3.2 `qexec_execute_cte`의 마지막 복사 두 곳만 바꿈 (`query_executor.c`)

- 재귀 CTE의 마지막 복사(CTE XASL → `non_recursive_part`)와 비재귀 CTE의 복사(`non_recursive_part` → CTE XASL)를 `QFILE_COPY_DEPENDENT`로 바꿨습니다.
- **재귀 루프 안의 복사(`MOVE_DEPENDENT`)는 그대로 둡니다.** 루프 안에서는 원본 list id를 곧바로 정리하거나 합치므로 소유권을 넘기는 것이 맞습니다. 두 list id가 *동시에 살아서 읽히는* 시점은 마지막 복사 뒤뿐입니다.
- 주석에 "두 list id 모두 읽히고, 병렬 list 스캔은 읽는 list id로만 dependent list의 페이지를 찾는다"를 적어, 왜 이 두 곳만 `COPY`인지 다음 사람이 알 수 있게 했습니다.

### 3.3 복사 실패 처리 (`ca1d56a82`, `f485d965f`)

Greptile 지적(6절)을 gdb로 확인하다 보니, 이 PR이 만든 복제 실패 경로가 develop에 이미 있던 실패 처리 결함으로 들어갔습니다. 새 경로가 그 결함에 닿고, 지적도 그 결함을 고치지 않으면 해결되지 않으므로 이 PR에서 함께 고쳤습니다(사용자 결정).

- **`qfile_copy_list_id`는 실패하면 빈 list id를 남깁니다.** 원래 첫 줄의 `memcpy`가 원본의 `sort_list`, `tpl_descr`, `dependent_list_id` 포인터를 대상에 그대로 복사합니다. type list 복사나 sort list 할당이 실패하면 이 포인터들이 남은 채로 돌아가 호출자가 정리할 때 원본과 두 번 해제했습니다. 그래서 `memcpy` 바로 뒤에 `sort_list`와 `tpl_descr`를 비우고, 실패 경로를 `exit_on_error` 하나로 모아 복사가 할당한 sort list와 `type_list.domp`만 푼 뒤 `QFILE_CLEAR_LIST_ID`를 합니다. 실패한 대상은 아직 `m_qlist_count`에 등록하지 않았고, 빈 list id(`type_cnt` 0)는 호출자의 정리에서 카운트를 빼지도 해제하지도 않습니다.
- **`qexec_execute_cte`의 실패 분기 세 곳은 list id를 free하지 않습니다.** 그 세 곳은 `QFILE_FREE_AND_INIT_LIST_ID`로 `non_recursive_part->list_id`나 `xasl->list_id`를 free했습니다. 이 list id는 XASL을 풀 때 `stx_restore_list_id`가 XASL 버퍼 안에 잡은 것이라 malloc한 포인터가 아닙니다. 그래서 `free(): invalid pointer`로 서버가 중단되었고, 중단되지 않더라도 plan cache의 XASL에 NULL이 남아 같은 SQL을 다시 실행하면 실패했습니다. 실패한 복사가 이미 빈 list id를 남기므로 이 free를 지우고 이유를 한 줄 주석으로 남겼습니다.
- **오류 경로에서 `t_list_id`를 해제합니다.** 재귀 CTE는 반복 결과를 `t_list_id`에 합칩니다. 두 번째 반복부터 `t_list_id`를 `xasl->list_id`로 복사하다 실패하면 `t_list_id`가 해제되지 않아 `m_qlist_count` assert가 났습니다. `exit_on_error`에서 `t_list_id`가 있으면 `QFILE_FREE_AND_INIT_LIST_ID`로 해제합니다. `qexec_end_mainblock_iterations`, `qexec_start_connect_by_lists`가 같은 모양으로 임시 list를 정리합니다.

## 4. 택하지 않은 방법

- **CTE 결과에 병렬 list 스캔을 끄기.** 정답은 나오지만 CBRD-26722가 넣은 기능을 CTE에서 버리게 됩니다. 원인은 체인 소유권 하나이므로 그것만 고쳤습니다.
- **병렬 heap 스캔이 워커 파일을 하나로 합치기.** 모든 병렬 스캔에 행 복사 비용이 생깁니다. CTE의 두 list id 문제 때문에 공통 경로를 바꿀 이유가 없습니다.
- **`qfile_collect_list_sector_info`가 체인 대신 다른 방법으로 파일을 찾게 하기.** list id가 자기 파일 목록을 모른다는 것이 문제의 본질입니다. 수집 함수를 바꾸면 list id의 불변식(체인 = 파일 목록)이 흐려집니다.

## 6. 리뷰 지적과 답

- **Greptile P1 (`list_file.c:560`): 복제 실패 시 `m_qlist_count`가 어긋난다.** 맞는 지적이었고 `baf63f840`에서 고쳤습니다. 복제가 실패하면 대상 list id를 빈 list id로 만들어 돌려주므로, 호출자의 정리가 등록된 적 없는 list를 카운트에서 빼지 않습니다. 답: r4248850822.
- **첫 답에서 범위 밖이라 했던 호출자 결함을 이 PR에서 고침.** 첫 답에서는 `qexec_execute_cte` 실패 분기의 free를 develop 기존 결함으로 보고 범위 밖이라고 했습니다. 사용자가 "따로 등록이 아니라 이 이슈에서 같이 고쳐야 한다"고 정해 `ca1d56a82`, `f485d965f`에서 고쳤고(3.3), 같은 스레드에 정정 답을 달았습니다: r4249571233.
- **검증(gdb fault injection, optdebug, client/server, `f485d965f`).** 복사 실패를 한 번씩 주입한 뒤, 같은 서버에서 재귀 CTE(200000행)와 CTE→CTE(100000행)를 다시 실행했습니다.

| 주입한 실패 | 복사 위치 (`qexec_execute_cte`) | 결과 |
|---|---|---|
| dependent list 복제 NULL | 재귀 CTE의 마지막 복사 | `Query execution failure #18758.`, 서버 유지 |
| dependent list 복제 NULL | 비재귀 CTE의 복사 | `#18776`, 서버 유지 |
| type list 할당 NULL | 재귀 첫 반복의 복사 | `#18694` |
