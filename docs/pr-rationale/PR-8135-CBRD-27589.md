- JIRA: http://jira.cubrid.org/browse/CBRD-27589
- TC: CUBRID/cubrid-testcases#3695 (`cbrd_27589`, ESCAPE 'é' Case 9 포함)

- 상태: soheejung-cs, beyondykk9 승인.

## 1. 어떤 SQL이 틀렸나

`s`, `p`가 `VARCHAR(16) COLLATE binary`일 때:

```sql
select 'a%b_' like 'a_%b_' escape '_';   -- 기대 1
select 'a%b_x' like 'a_%b_' escape '_';  -- 기대 0
```

패턴 `a_%b_`에서 첫 `_`는 `%`를 이스케이프하고, 마지막 `_`는 뒤에 문자가 없으므로 일반 문자 `_`로 비교됩니다(끝 ESCAPE). release는 답이 맞습니다. debug는 `language_support.c`의 `assert (size1 == 0 || size2 == 0)` 또는 `assert (size1 > 0)`로 abort합니다(SA면 csql, CS면 cub_server).

같은 리터럴 구간 앞쪽에 이스케이프한 문자가 있고 패턴이 ESCAPE로 끝나는 모양이면 납니다. ESCAPE 'é'처럼 첫 바이트가 0x80 이상인 경우도 같은 경로를 탑니다(binary 콜레이션은 다중 바이트 ESCAPE의 첫 바이트만 씀). CBRD-27181 이전 빌드(11.5.0.2407)에서도 나므로 오래된 결함입니다.

## 2. 원인

```c
if (is_match && escape != NULL && c2 == *escape)
  {
    str2++;                                         /* (1) 먼저 옮김 */
    if (!(has_last_escape && str2 + 1 >= str2_end))
      {
        c2 = *str2;
      }
  }
...
for (; ...; str1++, str2++)                         /* (2) 루프가 또 옮김 */
```

`'a%b_' LIKE 'a_%b_' ESCAPE '_'`를 따라가면:
1. `a` = `a`.
2. 짝 있는 ESCAPE `_`: (1)로 str2=2, c2=`%`가 텍스트의 `%`와 같다.
3. `b` = `b`.
4. 끝 ESCAPE: (1)로 str2=5(=end)가 되고, 끝이므로 c2는 `_`로 남는다. 그다음 (2)로 str2=6 = end+1.

루프가 끝나면 `size2 = str2_end - str2 = -1`입니다. 텍스트가 남으면 첫 assert, 정확히 소비했으면 else 분기의 assert에서 abort합니다. release의 else 분기는 `is_match`면 바로 0을 돌려주고 일치 길이도 맞아서, 넘어간 포인터는 다시 읽히지 않습니다. 그래서 release 답은 맞았습니다.

## 3. 고친 방식과 이유

```c
if (is_match && escape != NULL && c2 == *escape)
  {
    /* a trailing escape is a normal character: step over the escape only when a character follows it,
     * otherwise the loop increment would move str2 past str2_end */
    if (!(has_last_escape && str2 + 1 >= str2_end))
      {
        str2++;
        c2 = *str2;
      }
  }
```

- **`str2++`를 조건 안으로 옮겼습니다.** 끝 ESCAPE가 아닐 때만 ESCAPE를 건너뜁니다. 끝 ESCAPE이면 그 자리의 ESCAPE 문자 자체를 일반 문자로 비교하고, 루프 증가 한 번으로 정확히 `str2_end`에서 멈춥니다.
- **형제 matcher와 같은 모양입니다.** `lang_strmatch_ko`, `lang_strmatch_utf8`(그리고 `_utf8_w_contr`, `_utf8_uca_w_level`)은 이미 "끝 ESCAPE가 아닐 때만 옮긴다"는 순서입니다. `lang_strmatch_byte`는 `c2 = *str2++` 방식이라 다른 모양이지만 끝을 넘지 않습니다. 결함은 `lang_strmatch_binary` 하나에만 있었습니다. 새 로직을 만들지 않고 이웃 함수의 검증된 순서를 따랐습니다.
- **조건식은 그대로 두고 위치만 옮겼습니다.** 옮긴 뒤에는 `str2 + 1 >= str2_end`가 ESCAPE 위치를 기준으로 계산되므로 "ESCAPE가 마지막 바이트인가"를 뜻합니다. 원래 코드는 한 칸 옮긴 뒤 계산해서 사실상 "ESCAPE가 끝에서 두 번째 이후인가"를 봤습니다. 그래도 답은 같습니다. `qstr_eval_like`는 패턴 구간의 마지막 바이트가 이스케이프되지 않은 ESCAPE일 때만 `has_last_escape`를 켜므로, `has_last_escape`가 참이면 끝에서 두 번째 바이트가 이스케이프 시작일 수 없습니다. 조사 보고서에서 후보 A(형제 함수와 같은 판정)로 정리했고 사용자가 이 안을 골랐습니다.
- 주석은 "왜 조건 안에서 옮기는가"(루프 증가와 합쳐 끝을 넘는다)만 적었습니다.

## 4. release 결과가 바뀌지 않는다는 근거

- probe 28개(조사 때 26개 + 이스케이프한 문자로 끝나는 패턴 등 2개 추가)를 release, debug SA, debug CS로 돌렸습니다. release는 수정 전에도 모두 맞는 답이었고, 수정 후 release 답이 수정 전과 SA·CS 모두 같습니다.
- 모델 비교: 패턴과 텍스트 조합 4452만 건을 수정 전·후 함수로 비교해 답이 하나도 바뀌지 않았습니다.
- 같은 질의를 다른 콜레이션(iso88591_bin, iso88591_en_ci, utf8_bin, utf8_en_ci, euckr_bin)으로 돌려 형제 matcher가 정상임을 확인했습니다.

## 5. 범위 밖

- **ESCAPE '_' 또는 '%'에서 `%` 그룹이 100개 이상이면 ERROR가 나는 것, 다중 바이트 ESCAPE의 첫 바이트만 쓰는 것**은 별개 동작이라 workspace#423으로 남겼습니다.
- **11.4 백포트:** 사용자에게 물었고 develop만 고치기로 했습니다(11.4 debug는 ESCAPE '!'로도 abort함).
- **TC에 ESCAPE 'é' 케이스:** 처음엔 넣지 않는 쪽을 추천했으나 사용자가 "넣어"라고 해서 Case 9로 넣었습니다.
