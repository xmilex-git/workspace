## 1. 어떤 SQL이 틀렸나

```sql
create table t (id int primary key, v int);   -- 10행, 모두 한 페이지
create or replace function f_del (p int) return int as begin delete from t where id = p + 1; return p; end;
select a.id, f_del (a.id) from t a;
```

- 기대: 1, 3, 5, 7, 9가 반환되고 t에 그 다섯 행이 남음.
- develop: `page_latch_timeout_in_msecs`(기본 300초) 동안 멈춘 뒤 release는 -836 → 트랜잭션 롤백, debug는 `page_buffer.c` assert로 서버 중단.
- 같은 테이블을 읽기만 하는 함수라도, 다른 세션이 같은 페이지를 갱신하러 오면 두 세션이 모두 롤백됩니다.
- 11.4(CBRD-25184)부터 있던 결함입니다.

인덱스 스캔에도 같은 모양이 있습니다(범위 추가, 4.3절).

```sql
select /*+ ordered use_nl */ a.id, a.v from t_upd a force index (i_upd_id), t_one o
 where a.id > 0 and f_del (a.id) > 0;
```

## 2. 원인

- 테이블 하나를 순차 스캔하는 블록은 fixed(PEEK) 힙 스캔이 됩니다. 이 스캔은 행을 돌려준 뒤에도 페이지 READ 래치를 쥔 채 select 목록과 WHERE를 평가합니다.
- 거기서 부른 저장 함수의 SQL은 CAS 콜백을 거쳐 **같은 트랜잭션의 새 요청으로 다른 워커 스레드**에서 실행됩니다. 그 SQL이 스캔 중인 페이지의 행을 지우거나 고치면 그 래치를 기다리고, 스캔 스레드는 함수 결과를 기다리므로 래치 대기 시간이 끝날 때까지 서로 기다립니다.
- 엔진에 다시 들어오는 연산자가 있으면 fixed scan을 끄는 정책은 이미 있습니다(CBRD-27062). 그 조건에 SP가 빠져 있었습니다.
- 인덱스 쪽: 인덱스 컬럼만 읽는 WHERE 항은 key filter가 되고, btree 스캔은 key filter를 리프 페이지 래치를 쥔 채 평가합니다. 그 항의 SP가 같은 리프의 키를 바꾸면 같은 방식으로 기다립니다. fixed scan 끄기로는 이 경로가 막히지 않습니다.

## 3. 결과가 무엇이어야 하는가

fixed scan을 끄면 그 문장은 행마다 COPY로 읽습니다. 그런데 CBRD-27590 수정이 없으면 이번엔 페이지 복사 스캔(cached scan)으로 가서 함수가 지운 행을 그대로 반환합니다(1–10 반환, t = {1}). 그래서 이 수정은 CBRD-27590의 "읽는 시점 의미"(ADR 0026) 위에서만 맞는 답을 냅니다. 이것이 #8130 위에 쌓은 이유입니다.

## 4. 고친 방식과 이유

### 4.1 SP를 부르는 문장은 모든 블록에서 fixed scan을 끔 (`query_executor.c`)

- `qexec_execute_mainblock_internal ()`의 fixed scan 결정에서 `xasl_state->calls_sql_capable_sp`이면 `fixed_scan_xasl = NULL`로 둡니다. release에 들어가는 실행 경로 변경은 이 한 줄입니다.
- **CBRD-27590의 문장 표시를 다시 씁니다.** #8130이 이미 "PARALLEL_ENABLE이 아닌 SP를 부르는 문장"을 XASL을 풀 때 표시해서 `XASL_STATE`로 모든 블록에 넘깁니다. 같은 판정이 두 곳에 생기지 않습니다.
- **문장 단위인 이유:** hash/merge join 입력처럼 옵티마이저가 만든 하위 블록에 있는 SP도 덮어야 합니다. 이유를 코드 주석에 적었습니다.
- **px 워커의 안쪽 fixed scan은 고치지 않았습니다.** 워커는 자기 list 파일에 쓰고 메인 스레드를 기다리지 않아 교착이 생기지 않습니다(호스트 probe로 확인).

**택하지 않은 안:** 컴파일 때 블록 플래그를 만들고 `plan_generation`의 7곳을 고치는 독립안(`proposed-alt-A-compile-time.diff`). #8130과 독립적이지만, #8130보다 먼저 들어가면 위 3절처럼 1–10을 반환하고 t = {1}이 남는 오답이 됩니다. 사용자에게 "CBRD-27590 표시 재사용, 27590 뒤 머지 vs 독립안"을 물었고 재사용(추천)으로 정했습니다.

### 4.2 debug 전용 자기 대기 감지 (`network_callback_sr.cpp`, `page_buffer.c`, `thread_entry.*`)

같은 결함이 다른 경로로 다시 생기면 300초를 기다리지 않고 바로 드러나게 하려는 장치입니다. 조사 보고서는 "넣지 않음"을 추천했지만 사용자가 "debug 전용으로" 넣으라고 정했습니다.

- 콜백 요청을 보내기 직전(`xs_callback_begin_wait ()`)에 스레드의 `m_callback_wait_seq`를 홀수로 만들고, 클라이언트 응답을 받으면(`xs_callback_receive ()`) 짝수로 되돌립니다. 보내기에 실패하면 `xs_callback_end_wait ()`에서 짝수로 되돌립니다.
  - 응답을 받은 뒤 실행하는 콜백 함수(`func ()`)는 페이지를 고정할 수 있어서 홀수 구간에서 뺍니다.
- `pgbuf_timed_sleep ()`에 들어갈 때 `pgbuf_find_callback_waiting_holder ()`가 "같은 트랜잭션에서 콜백 응답을 기다리는(홀수) 스레드가 이 페이지를 쥐고 있는가"를 봅니다. 그러면 서버 로그에 `page latch self-wait: ...`를 남기고 assert합니다.
- 오탐을 막는 조건: 연결에 걸린 콜백이 없으면 먼저 빠집니다. 대기 시간 0인 요청은 건너뜁니다. 기다리는 스레드 자신의 px 워커는 정상 대기라서 제외합니다(반대로 콜백 체인 쪽 스레드의 px 워커는 진짜 교착이므로 제외하지 않습니다).
- **스레드 단위 순번인 이유:** 연결 단위 카운터로는 "콜백 대기 중인 바로 그 스레드"를 가려낼 수 없습니다.
- holder 목록은 순번을 앞뒤로 읽어(seqlock 모양), 대기가 끝나는 순간과 겹친 읽기를 버립니다. 6절의 Greptile 지적 참고.
- 모든 것이 `#if !defined(NDEBUG)` 안이라 release 구조체 레이아웃과 실행 경로는 바뀌지 않습니다.
- **효과 확인:** `query_executor.c` 줄을 뺀 빌드에서 이슈 질의를 포함한 10개 모양(다음 행 DELETE, INSERT, WHERE, 집계, INSERT ... SELECT, NL 안쪽, hash/merge join 입력, 동시 writer)이 모두 바로 assert했고, 원래 멈추지 않던 14개 모양은 assert하지 않았습니다. `3fd9e32bb`를 뺀 빌드에서도 key filter 모양 8개가 모두 바로 assert했습니다.

### 4.3 SP를 부르는 항은 key filter에 넣지 않음 (`3fd9e32bb`, 범위 추가)

CBRD-27590 TC를 쓰다 같은 부류의 인덱스 스캔 자기 대기를 찾았고, 사용자가 "범위에 추가해"라고 해서 이 PR에 넣었습니다.

- **표시:** `qo_add_term ()`이 PARALLEL_ENABLE이 아닌 SP를 부르는 항에 `QO_TERM_CALLS_SQL_CAPABLE_SP`를 세웁니다. 판정은 parallel hash join이 이미 쓰는 `qo_check_method_call_parallel_eligibility ()`를 다시 씁니다. 항마다 컴파일 때 한 번입니다.
- **key filter에서 빼기:** `qo_index_scan_new ()`가 표시된 항을 key filter 후보에서 뺍니다. 그러면 그 항은 스캔이 리프를 놓은 뒤 평가하는 data filter가 됩니다.
- **covering과 MRO 포기:** covering 스캔은 data filter를 받을 수 없고, multi-range optimization은 data filter 전에 상위 행을 고릅니다. 그래서 `qo_iscan_has_sql_capable_sp_filter ()`가 참이면 두 최적화를 쓰지 않습니다.
- **포기 범위는 좁게:** 처음에는 "노드에 걸린 표시 항 전부"로 막았더니, key range에만 SP가 있는 질의(`case_where_02` 앞부분, `cbrd_24473`)도 covering을 잃었습니다. 단일 컬럼 key range 항의 SP는 스캔이 내려가기 *전에* 범위마다 한 번 평가되므로 래치 문제가 없습니다. 그래서 그런 항은 제외하도록 바로잡았습니다.
- **조인 항과 다중 컬럼 key range:** `gen_outer ()`는 표시된 조인 항을 안쪽 인덱스 스캔의 key filter로 옮기지 않고, `make_pred_from_plan ()`은 표시된 다중 컬럼 key range 항(`(a, b) in (...)`)을 key filter 대신 data filter로 복사합니다.
- **부질의 안은 보지 않습니다.** 비상관 부질의는 스캔 전에 실행되고, 상관 부질의가 있는 항은 원래 key filter가 되지 않습니다. 처음에 부질의 안까지 봤더니 `case_index_scan_01`이 이 과대 판정으로 covering을 잃어서 바로잡았습니다.
- **CS_MODE만 적용합니다.** SA 모드는 SP의 SQL을 스캔 스레드가 직접 실행하므로 기다림이 없습니다. SA까지 바꾸면 develop에서 되던 질의가 develop의 기존 SA 결함 경로(삭제된 OID를 data filter로 읽어 debug assert, release "Accessing deleted object")로 들어가서, SA 계획은 develop 그대로 둡니다.

## 5. 동작 변화와 비용

- 이슈 질의: 1, 3, 5, 7, 9 반환, t = {1, 3, 5, 7, 9}. 다음 행 UPDATE면 2–10행이 v+100으로 보이고 그대로 남습니다.
- PARALLEL_ENABLE이 아닌 SP가 key filter에 있던 기존 TC 두 개(`_08_javasp/case_where_02`, `cbrd_26415` Case 3, 7)는 결과는 같고 계획만 바뀌어 TC PR에서 답을 갱신했습니다.
- 인덱스 컬럼만 읽고 PARALLEL_ENABLE이 아닌 SP를 부르는 항이 있는 질의는 key filter와 covering 대신 heap을 읽습니다. 이 성능은 따로 재지 않았습니다. 조사 때 잰 값은 SP 호출 행당 약 36 µs, COPY 행당 약 0.18 µs입니다.

## 6. 리뷰 지적과 답

| 지적 | 답 |
|---|---|
| Codex P2: 콜백 대기 표시가 요청을 보낸 *뒤*에 켜져서, 그 사이 들어온 SQL을 감지기가 놓친다 | 맞음. `2d1935323`에서 보내기 전에 홀수로 바꿈. 좁아진 구간 자체는 타이밍 경쟁이라 재현하지 못했음 |
| Codex P1: SA_MODE에서도 표시해야 한다 | 의도된 동작. SA는 같은 스레드가 SP의 SQL을 실행해 기다림이 없고, develop SA에서 같은 질의가 heap 스캔과 같은 답을 냄(실측). SA까지 바꾸면 develop의 기존 SA 결함 경로로 들어가 되던 질의가 실패함 |
| Greptile P1: `pgbuf_find_callback_waiting_holder ()`가 다른 스레드의 holder 목록을 동기화 없이 읽음 | 형식상 data race인 것은 인정. 다만 holder 목록은 스레드 전용이라 잠금이 없고, 이 검사를 위해 잠금을 더하면 debug 빌드의 모든 page fix/unfix에 비용과 타이밍 변화가 생김. 홀수인 동안 holder는 응답만 기다려 목록을 바꾸지 않고, `PGBUF_HOLDER`는 해제되지 않고 free list로 돌아가므로 끊긴 링크도 유효한 메모리이며, 걷는 횟수는 처음 읽은 `num_hold_cnt`로 제한됨. `!NDEBUG` 전용 진단이고 거짓 assert로 이어지지 않아 유지 |

Greptile은 "C++ 메모리 모델에서 유효한 seqlock이 아니다"라며 지적을 유지했습니다. 심각하지 않은 debug 전용 항목이라 사용자 요청으로 스레드는 resolve했고, 이 점은 사용자에게 따로 알렸습니다.
