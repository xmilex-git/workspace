# PR #8132: [CBRD-27588] 병렬 스캔에서 비상관 스칼라 부질의가 NEXT_VALUE를 부르면 ROWNUM이 있는 집계 질의가 틀린 행을 반환하는 문제

- PR: https://github.com/CUBRID/cubrid/pull/8132 (head `943c4c1a8`, base develop `a9940d67a`)
- JIRA: http://jira.cubrid.org/browse/CBRD-27588
- TC: CUBRID/cubrid-testcases#3692 (`cbrd_27588`, 7 cases). private-ex#4369는 빈 PR입니다.
- 바뀐 파일: `src/query/parallel/px_scan/px_scan.cpp` 하나 (+6 −2)

## 1. 어떤 SQL이 틀렸나

`t_big`이 100만 행(heap 약 16,400페이지, 기본 설정에서 워커 4개)이고 `s_seq`가 시리얼일 때:

```sql
select count(*), min(c) from t_big
 where c > (select s_seq.next_value from db_root) * 100000 and rownum <= 2000000;
```

- 기대: `900000 / 100001`, 실행 뒤 시리얼은 1만큼 오름.
- release 3회: `645826/200001`, `753760/245767`, `546240/200001`. 시리얼은 매번 5만큼 오름(= 1 + 워커 4).
- `NO_PARALLEL_SCAN`을 주거나 `rownum` 조건을 빼면 정답입니다. SA 모드는 정상입니다.
- `INSERT ... SELECT`로 이 결과가 테이블에 저장됩니다.

ROWNUM만의 문제가 아닙니다. row by row gather로 실행되는 병렬 heap 스캔이면 모두 해당합니다. 집계·GROUP BY와 함께 쓴 ROWNUM, `rownum >= 1` 같은 하한 조건, PARALLEL_ENABLE 없는 PL/CSQL 함수를 select 목록에 둔 질의(ROWNUM 없음)에서도 같았습니다.

## 2. 원인

1. CBRD-26931은 비상관 스칼라 부질의를 메인 스레드에서 한 번 계산하고, 그 값을 병렬 스캔 워커에 넘깁니다. 메인이 값을 맵에 담고(`capture_precomp_vals`), 워커가 시작할 때 `task::initialize`가 그 값을 자기 XASL clone에 주입합니다.
2. 그런데 맵을 채우는 `capture_precomp_vals` 호출이 `manager::next()`의 `if constexpr (result_type == MERGEABLE_LIST || result_type == BUILDVALUE_OPT)` 블록 안에 있었습니다. 이 블록은 원래 NL join 정보를 위한 것이었는데, CBRD-26931이 그 안에 capture를 넣으면서 세 번째 gather인 row by row(`XASL_SNAPSHOT`)가 빠졌습니다.
3. row by row에서는 맵이 비어 있으므로 워커의 주입 루프는 값을 찾지 못하고 넘어갑니다. 워커는 data filter(`where_pred`)를 평가할 때 자기 clone의 부질의를 다시 실행하고, NEXT_VALUE가 워커마다 하나씩 올라 워커마다 다른 기준값으로 행을 걸렀습니다. 메인은 워커가 거른 행을 다시 거르지 않으므로 버려진 행은 사라집니다.

ROWNUM이 row by row를 고르는 이유: 집계 질의는 항상 `CANNOT_LIST_MERGE`이고, ROWNUM이 있으면 `CANNOT_BUILDVALUE_OPT`도 켜져서 row by row fallback으로 갑니다.

## 3. 고친 방식과 이유

```cpp
if (unlikely (!m_task_started))
  {
    /* snapshot precomputed scalar values for worker injection; unconditional so a single-table scan injects too
     * instead of re-executing per worker. Every gather mode needs it, the row-by-row XASL_SNAPSHOT included: its
     * workers evaluate the scan predicate too, and a worker that finds no value re-executes the subquery
     * (CBRD-27588: NEXT_VALUE ran once per worker). */
    m_pre_execution_info.capture_precomp_vals (m_xasl);

    if constexpr (result_type == RESULT_TYPE::MERGEABLE_LIST || result_type == RESULT_TYPE::BUILDVALUE_OPT)
      {
        if (m_xasl->scan_ptr)
          ...
```

- **호출 한 줄을 `if constexpr` 밖으로 옮겼습니다.** 워커 쪽 주입 코드(`task::initialize`)는 원래 gather 모드를 가리지 않으므로 고칠 필요가 없습니다. 빠진 것은 메인 쪽 capture 하나뿐이었습니다.
- **NL join 정보 capture(`capture_pre_execution_info`)는 블록 안에 그대로 둡니다.** 그것은 MERGEABLE_LIST와 BUILDVALUE_OPT 전용이고, row by row는 `scan_ptr`를 메인이 실행합니다.
- **실제로 동작이 바뀌는 인스턴스는 `manager<XASL_SNAPSHOT, HEAP>` 하나입니다.** 인덱스·list 스캔은 row by row를 지원하지 않습니다(심볼로 확인).
- **주석에 이유를 남겼습니다.** 원래 주석("unconditional so a single-table scan injects too")에 "row by row도 워커가 스캔 술어를 평가하므로 필요하다"를 덧붙였습니다. 다음 사람이 이 호출을 다시 블록 안으로 넣지 않게 하려는 것입니다.
- **비용:** scan open당 한 번이고 행 루프에는 분기도 할당도 늘지 않습니다. 맵은 워커 생성 전에 채워지고 워커는 읽기만 하므로 다른 두 모드와 동시성 조건이 같습니다.

## 4. 택하지 않은 방법

- **후보 B: row by row이면서 미리 계산하는 부질의가 있으면 병렬 스캔을 끄기.** 결과는 맞지만 계획이 직렬로 바뀌어 p01이 286 ms → 679 ms(약 2.4배)가 되고, 원래 결과가 맞던 결정적 부질의 질의까지 느려집니다.
- 사용자에게 "한 줄 이동으로 병렬 유지 vs row by row에서 병렬 거부"를 물었고 한 줄 이동(추천)으로 정했습니다.

## 5. 부수 효과 (좋은 쪽)

결정적이지만 비싼 부질의도 워커마다 다시 실행되고 있었습니다(결과는 맞음). 예를 들어 `v >= (select min(b.v) from t_big b where b.pad <> 'z') and rownum <= 2000000`은 optdebug에서 전체 fetch가 402,314 → 139,898, 바깥 SCAN fetch가 336,666 → 74,250으로 줄었습니다. 실행 계획과 trace 형식은 바뀌지 않습니다.

## 6. 범위 밖

- **NOT IN 같은 비상관 리스트 부질의도 워커마다 다시 실행됩니다.** 리스트 부질의에는 미리 계산 표시(`precomp_owner_regu`)가 없어서 모든 gather 모드에서 생기는 다른 경로입니다. 사용자 결정에 따라 분리했고 workspace#420으로 등록했습니다.
- CBRD-27596(#8136)은 비상관 스칼라 부질의에 미선언 SP가 있으면 바깥 스캔을 직렬로 만듭니다. 이 PR이 머지된 뒤 그 제약을 완화할 수 있습니다.
