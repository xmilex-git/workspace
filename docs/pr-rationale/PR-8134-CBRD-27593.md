# PR #8134: [CBRD-27593] [Regression][parallel index scan] SELECT ... FOR UPDATE가 읽은 행을 잠그지 않는 문제

- PR: https://github.com/CUBRID/cubrid/pull/8134 (head `c3f4a337a`, base develop `a9940d67a`)
- JIRA: http://jira.cubrid.org/browse/CBRD-27593
- TC: CUBRID/cubrid-testcases-private-ex#4371 (shell `shell/_06_issues/_26_2h/cbrd_27593`). cubrid-testcases#3694는 빈 PR입니다.
- 바뀐 파일: `src/query/parallel/px_scan/px_scan_checker.cpp` 하나 (+13)

## 1. 어떤 SQL이 틀렸나

`t(id pk, a = mod(id, 4000), b)` 100만 행, 인덱스 `i_a(a)`일 때:

```sql
-- 세션 1 (autocommit off)
select id from t where a < 100 for update;   -- 25000행, 병렬 인덱스 스캔(workers 3)
-- 세션 2
update t set b = b + 1 where id = 5;         -- 기다려야 하는데 0.02초 만에 1 row affected
```

- `cubrid lockdb`로 보면 세션 1의 X_LOCK이 0개입니다. `no_parallel_scan`을 주면 25000개를 잡고 세션 2는 timeout됩니다.
- 갱신 손실을 실제로 재현했습니다. 세션 1이 FOR UPDATE로 읽고 3초 뒤 `b = 1`로 커밋하고, 세션 2가 1.5초 뒤 `b = b + 100`을 실행하면 최종 b가 1입니다(직렬이면 101). release와 debug가 같고, assert나 core는 없습니다.
- 격리 수준(REPEATABLE READ, SERIALIZABLE)과 상관없이 납니다. `order by`, 커버링 인덱스 모양도 같습니다.

## 2. 원인

- 병렬 스캔 워커는 스캔을 행 잠금 없이 엽니다(`px_scan_task.cpp`, `scan_open_index_scan (..., false, S_SELECT, ...)`). 직렬 인덱스 스캔은 `scan_next_index_lookup_heap`에서 행마다 `locator_lock_and_get_object_with_evaluation`으로 잠그지만, 병렬 경로에는 이 단계가 없습니다.
- 그래서 FOR UPDATE는 병렬로 돌면 안 됩니다. 힙 주 스캔은 `scan_open_parallel_heap_scan`이 `mvcc_select_lock_needed`를 보고 직렬로 돌립니다. 그런데 CBRD-26722가 추가한 인덱스·리스트 경로에는 이 확인이 없습니다.
- 검사기(`px_scan_checker.cpp`)는 `scan_op_type != S_SELECT`만 막는데, FOR UPDATE는 `scan_op_type`이 `S_SELECT`이므로 통과합니다.
- CBRD-26722 명세의 공통 제약과 매뉴얼 `parallel.rst`는 모두 "FOR UPDATE면 직렬"이라고 적고 있습니다. 즉 명세에 있는 제약이 인덱스·리스트 경로에서 구현되지 않은 것입니다.

같은 원인(워커가 잠금 없이 읽음)으로 다음 경로도 잠그지 않았습니다.

| 경로 | 언제부터 |
|---|---|
| 병렬 인덱스 주 스캔 | CBRD-26722 (회귀) |
| 병렬 주 스캔 아래 NL 안쪽 spec의 `for update of s` | 주 스캔이 힙이면 CBRD-26522, 인덱스·리스트면 CBRD-26722 |
| 파티션 힙 `parallel(4)` FOR UPDATE (파티션마다 다시 열 때 힙의 잠금 확인을 건너뜀) | CBRD-25447 |
| 리스트 주 스캔(파생 테이블) `for update of t` | CBRD-26722 |
| 워커가 실행하는 상관 파생 테이블(dptr)의 FOR UPDATE | CBRD-27205 |

## 3. 고친 방식과 이유

```cpp
/* FOR UPDATE: the serial scan locks every row it reads, but workers open their scans without locks
 * (px_scan_task.cpp), so a FOR UPDATE spec keeps its scan serial (CBRD-27593). */
if (ACCESS_SPEC_IS_FLAGED (arg, ACCESS_SPEC_FLAG_FOR_UPDATE))
  {
    set_flag (result, CANNOT_PARALLEL_SCAN);
    return result;
  }
```

같은 규칙을 두 곳에 넣었습니다.

- `check<false> (ACCESS_SPEC_TYPE *)`: 병렬로 나눌 주 스캔 자신.
- `sibling_check (ACCESS_SPEC_TYPE *)`: 워커가 여는 NL 안쪽 spec과 워커가 실행하는 dptr 쪽 spec.

병렬 스캔 체인(주 스캔, NL 안쪽, dptr) 어디든 `ACCESS_SPEC_FLAG_FOR_UPDATE` spec이 있으면 그 스캔을 `CANNOT_PARALLEL_SCAN`으로 만듭니다.

### 왜 검사기에서 막는가 (후보 C)

조사에서 네 후보를 비교했습니다.

| 후보 | 내용 | 판단 |
|---|---|---|
| A | 서버의 `scan_open_parallel_index_scan`에서 `mvcc_select_lock_needed`면 반환 (3줄) | 인덱스 주 스캔만 고쳐짐. NL 안쪽, 리스트 주 스캔, 파티션 힙이 남음 |
| B | 워커가 행 잠금을 잡게 하기 | 기각. 같은 트랜잭션의 여러 스레드가 동시에 잠그면 lock manager 경합(CBRD-26180, CBRD-26305)이 있고, 해결책인 group locking(CBRD-26793)은 아직 Open. 힙 경로의 결정, 명세, 매뉴얼과도 어긋남 |
| **C** | **검사기에서 FOR UPDATE spec이 있는 병렬 체인을 직렬로 표시** | **채택** |
| D | 옵티마이저(병렬 차수 결정)에서만 막기 | 기각. `parallel(n)` 힌트와 인덱스 외 경로가 남음 |

C를 고른 이유:
- 결함으로 분류한 모든 경로를 같은 두 블록이 덮습니다. 힙을 빼려면 오히려 예외 코드가 필요합니다.
- 판정이 XASL을 만들 때 클라이언트에서 한 번 정해지고 실행 비용이 0입니다.
- `px_scan_checker.cpp`는 {sa, cs} 라이브러리에서만 컴파일되므로 서버 `libcubrid.so`의 코드 배치가 바뀌지 않습니다.
- 병렬 스캔 적격성은 원래 이 검사기가 정하는 것이므로, CBRD-26722의 설계와 맞습니다.

바뀌는 것은 FOR UPDATE 문뿐입니다. UPDATE/DELETE/MERGE는 이미 검사기가 병렬을 막고, FOR UPDATE가 없는 같은 질의(`select id from t where a < 100;`)는 그대로 병렬입니다.

### 서버 쪽 게이트(A)를 같이 두지 않은 이유

사용자에게 물었고 "검사기만"으로 정했습니다. 서버 게이트까지 두면 server 라이브러리가 바뀌어 코드 배치 측정이 필요해지고, 같은 판정이 두 곳에 생깁니다.

## 4. 범위

- **범위 추가로 고쳐지는 기존 결함:** 힙 주 스캔 아래 NL 안쪽의 `for update of s`(CBRD-26522부터)와 파티션 힙 `parallel(4)` FOR UPDATE(CBRD-25447부터). 사용자에게 "인덱스 주 스캔만 vs 체인 전체"를 물었고 체인 전체로 정했습니다. PR Remarks에 적었습니다.
- **dptr를 워커가 실행하던 상관 파생 테이블의 FOR UPDATE도 직렬이 됩니다.** 이 경로는 워커들이 같은 트랜잭션으로 행을 동시에 잠갔고, 다른 트랜잭션이 기다리다 timeout된 뒤 FOR UPDATE 트랜잭션이 rollback하면 debug 서버가 `lock_manager.c:4338` assert로 간헐적으로 중단되었습니다(수정 전 빌드에서 core 3개, 모두 `lock_internal_perform_unlock_object ← lock_unlock_all ← log_abort`).
- **다루지 않은 것:** hash join 입력과 병렬 부질의의 잡 워커가 FOR UPDATE 행 잠금을 잡는 경로. 잠금 수는 맞고 실패가 재현되지 않아 workspace#422로 분리했습니다(사용자 결정).

## 5. 비용

p01이 release에서 0.012초 → 0.054초가 됩니다. 다만 병렬 쪽 값은 잠금 25000건과 재평가를 하지 않은 시간이라 같은 일을 잰 것이 아닙니다.
