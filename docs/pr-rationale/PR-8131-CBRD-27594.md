- JIRA: http://jira.cubrid.org/browse/CBRD-27594
- TC: CUBRID/cubrid-testcases#3691 (`cbrd_27594`). private-ex#4368은 빈 PR입니다.
- 바뀐 파일: `src/parser/xasl_generation.c` 하나 (+11)
- 상태: beyondykk9 승인.

## 1. 어떤 SQL이 틀렸나

`t_heap`이 100000행이고 CTE 결과 list가 약 936페이지(병렬 기준 256페이지 초과)일 때:

```sql
with c as (select /*+ materialize */ id, g, v, pad from t_heap)
select /*+ no_parallel_scan */ count(*), sum(v) from c;
-- CTE 결과를 읽는 temp 스캔이 parallel workers 3으로 실행됨 (결과 값은 맞음)

with c as (select /*+ materialize */ id, g, v, pad from t_heap)
select /*+ parallel(2) */ count(*), sum(v) from c;
-- 2가 아니라 3. parallel(0), (1), (8)도 모두 3
```

같은 힌트를 `no_merge` 파생 테이블에 주면 잘 적용됩니다. UNION ALL의 두 arm이 같은 CTE를 서로 다른 힌트로 참조해도, self hash join의 BUILD/PROBE도, INSERT ... WITH ... SELECT도 모두 힌트가 무시됐습니다. release와 debug가 같습니다.

결과 값은 맞으므로 심각도는 낮습니다. 다만 같은 시기에 찾은 CBRD-27597(병렬 list 스캔이 CTE 결과의 일부만 읽음)을 `NO_PARALLEL_SCAN`으로 피해 갈 길을 이 결함이 막고 있었습니다.

## 2. 원인

힌트가 서버까지 가는 길은 이렇습니다.

1. 파싱: `PARALLEL(n)`이 `select.num_parallel_threads`에 들어갑니다.
2. `pt_bind_names`: 그 SELECT의 FROM spec 전부에 `PT_SPEC_FLAG_NO_PARALLEL_SCAN`, `PT_SPEC_FLAG_PARALLEL_THREAD`를 세웁니다. **CTE 참조 spec도 여기서 플래그를 받습니다.**
3. XASL 생성: spec의 플래그를 access spec의 `ACCESS_SPEC_FLAG_*`와 `num_parallel_threads`로 옮깁니다. class spec과 파생 테이블(`pt_to_subquery_table_spec_list`)은 옮기는데, **CTE(`pt_to_cte_table_spec_list`)는 그대로 `return access;`라 옮기지 않았습니다.**
4. 서버: `scan_open_parallel_list_scan`은 플래그가 없으니 `num_parallel_threads = -1`(자동)로 `compute_parallel_degree`를 불러 936/256 = 3을 정했습니다.

CBRD-26722가 list 스캔까지 병렬화하면서 플래그 복사를 class, 파생 테이블, hash/merge join 중간 결과(`init_list_scan_proc`)에만 넣고 CTE 경로를 빠뜨린 것입니다.

## 3. 고친 방식과 이유

```c
/* The scan of a CTE result belongs to the query block that references the CTE, as a derived table scan does
 * (pt_to_subquery_table_spec_list); pt_bind_names flagged this spec with that block's parallel-scan hints. */
if (PT_IS_SPEC_FLAG_SET (spec, PT_SPEC_FLAG_NO_PARALLEL_SCAN))
  {
    ACCESS_SPEC_SET_FLAG (access, ACCESS_SPEC_FLAG_NO_PARALLEL_SCAN);
  }
if (PT_IS_SPEC_FLAG_SET (spec, PT_SPEC_FLAG_PARALLEL_THREAD))
  {
    ACCESS_SPEC_SET_FLAG (access, ACCESS_SPEC_FLAG_NUM_PARALLEL_THREADS);
    access->num_parallel_threads = spec->info.spec.num_parallel_threads;
  }
```

- **파생 테이블과 똑같은 두 블록을 CTE 함수에 넣었습니다.** CTE 결과 스캔과 파생 테이블 스캔은 둘 다 "이미 만들어진 list를 그것을 참조하는 블록이 읽는 것"이라 같은 규칙을 따르는 게 자연스럽습니다. 같은 일을 하는 코드가 같은 모양이어야 다음에 한쪽을 고칠 때 다른 쪽도 찾을 수 있습니다.
- **어느 블록의 힌트를 따르는가: CTE를 참조하는 블록.** `pt_bind_names`가 이미 참조 spec에 그 블록의 힌트를 세워 두었으므로, 그것을 옮기기만 하면 됩니다. CTE를 여러 곳에서 참조하면 참조마다 access spec이 따로 생기므로 참조마다 따로 정해집니다(예: UNION ALL의 두 arm이 서로 다른 힌트).
- **플래그와 값을 함께 세웁니다.** 서버의 `px_scan.cpp`에는 `ACCESS_SPEC_FLAG_NUM_PARALLEL_THREADS`가 서 있으면 값도 있어야 한다는 assert가 있습니다.
- 변경은 클라이언트 쪽 {sa, cs} 라이브러리 한 함수뿐입니다. 서버 코드와 XASL 스트림 형식(`xasl_to_stream.c`가 flags와 병렬도를 이미 보냄)은 그대로입니다.
- 힌트가 없는 질의는 바뀌지 않습니다.

## 4. 택하지 않은 방법

- **A′: 같은 블록을 `pt_to_spec_list`의 CTE 분기에 두기.** 동작은 같지만, 같은 일을 하는 파생 테이블 코드와 위치가 대칭이 아닙니다.
- **공통 helper로 묶기.** 네 곳(class, 파생, CTE, 중간 결과)이 이미 각자 쓰고 있어서, 이 PR에서 리팩터링하면 최소 변경 원칙에 어긋납니다.
- **B: CTE 본문 블록의 힌트가 모든 참조에 적용되게 하기.** 이슈의 기본 모양(바깥 블록 힌트)이 고쳐지지 않고, 파생 테이블과 규칙이 달라지며, 참조별 제어가 불가능하고, 재귀 CTE에서 어느 힌트를 볼지 새로 정해야 합니다.

사용자에게 "참조 블록(추천, 파생 테이블과 같음) vs CTE 본문 블록 vs 둘 다"를 물었고 참조 블록으로 정했습니다.

## 5. 답이 바뀌는 질의

답이 바뀌는 것은 CBRD-27597 결함에 걸리면서 그 블록에 `NO_PARALLEL_SCAN`을 준 질의뿐이고, 틀린 답이 맞는 답으로 바뀝니다.
