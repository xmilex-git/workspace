## 1. 무엇이 틀렸나

병렬 실행(병렬 스캔, 병렬 정렬, 병렬 hash join, 병렬 부질의)이 있는 질의에서 `SHOW TRACE`와 `SHOW EXEC STATISTICS`의 숫자가 틀렸습니다. TPC-H SF10 46개 질의로 전수조사해서 찾은 항목입니다.

| # | 증상 (예) | 원인 |
|---|---|---|
| C1 | 필터가 있는 병렬 heap 스캔의 SCAN `rows`가 `readrows`와 같음 (Q6 `rows: 59986052`, 실제 1139264) | 워커 slot 반복자가 `qualified_rows++`를 데이터 필터 검사보다 먼저 함 |
| D1 | 중첩 루프 조인의 바깥 병렬 스캔이 `readrows: 0, rows: 0`, SELECT fetch에서 워커 몫이 빠짐 (q03 trace 111,192 / 전역 34,504,078) | 워커 통계 합산이 `manager::end`에만 있었는데, scan_ptr가 있으면 `apply_pre_execution_info`가 스캔을 `S_ENDED`로 미리 바꿔 `scan_end_scan`이 `manager::end`를 부르지 않음 |

| D3 | ORDERBY page/ioread에 앞선 정렬 값이 다시 찍힘 | `qexec_orderby_distinct`가 `orderby_filesort`가 이미 참일 때만 기준값을 읽는데, 이 플래그는 첫 정렬 안에서 켜짐 (병렬과 무관한 기존 결함) |

그리고 워커는 trace일 때도 page fix 등 7개 항목만 부모로 옮겼습니다(`perfmon_get_parallel_merged_offsets`). 정렬 page, lock 같은 나머지 항목은 버려졌습니다.

## 2. 고친 방식의 큰 줄기: "워커는 자기 배열에 쌓고, 끝날 때 한 번 넘긴다"

사용자 지시(2026-10-11): "thread local 집계 → 끝나고 전체 집계에 merge 패턴을 사용해. /cpp-perf-rules를 참고해서."

- **누가 통계를 볼 때만 배열을 만듭니다.** `perfmon_parallel_stats_needed ()` = trace 중이거나 그 트랜잭션의 통계를 누가 보고 있을 때(`perfmon_server_is_stats_on`). 아무도 보지 않으면 배열을 만들지 않으므로 꺼져 있을 때 비용은 0입니다.
- **워커는 자기 배열에만 씁니다.** 공유 배열에 원자적이지 않은 `+=`를 동시에 하지 않으므로 C2(경합으로 잃는 값)가 없어지고, 캐시 라인을 번갈아 뺏는 일도 없습니다(cpp-perf-rules PAR-01, COH-04, MEM-03). 원자 연산을 증가마다 넣는 방법은 핫 경로 비용이 커서 택하지 않았습니다.
- **배열 전체를 한 번에 넘깁니다.** 7개 항목 목록을 없애고 `perfmon_merge_values ()`가 배열 전체를 합칩니다. 항목 목록은 합치는 곳마다 복사되어 서로 달라진 전력이 있었고(삭제된 주석에도 그 내용이 있음), 새 통계 항목이 생길 때마다 빠질 수 있습니다.
- **소유권을 한 번 넘깁니다(COH-12).** 워커는 끝날 때 배열을 부모 쪽 저장소에 넘기고, 부모는 모든 워커가 끝난 뒤 한 번 합칩니다.

### 2.1 공통 함수 (`perf_monitor.c/h`)

- `perfmon_merge_values (dst, src)`: 통계 종류별 합치는 규칙을 한 곳에 둡니다.
  - 카운터와 COMPLEX 값은 더하고, 타이머는 count와 total을 더하고 max는 큰 값을 둡니다.
  - PEEK 값은 전역 상태에서 정하고 비율은 읽을 때 계산하므로 합치지 않습니다.
  - 예외: `PSTAT_PB_PAGE_FIX_ACQUIRE_TIME_10USEC`는 비율 항목으로 등록돼 있지만 `pgbuf_fix ()`가 그 칸에 시간을 직접 누적하고 trace가 fetch_time으로 그대로 읽습니다. 그래서 이 칸만 더합니다(6820f5ece, 리뷰 반영, 6절).
- `perfmon_add_values_to_local (thread_p, values)`: 받는 쪽이 병렬 워커면 그 워커의 배열에, 아니면 감시 중인 트랜잭션 통계에 합칩니다. 중첩(워커 안의 워커)도 이 한 함수로 처리됩니다.
- `perfmon_time_at_offset`, `perfmon_time_bulk_at_offset`: 병렬 워커면 자기 배열에 씁니다. 전에는 타이머만 트랜잭션 통계에 경합 쓰기를 했습니다.
- 삭제: `perfmon_get_parallel_merged_offsets`, 호출처가 없던 `perfmon_merge_child_stats_to_parent_stats`, 대체된 `perfmon_merge_parallel_stats_to_tran_stats`.

### 2.2 병렬 스캔 (`px_scan*`) — C1, D1, C2, E5

- **C1:** `qualified_rows++`를 데이터 필터 통과 뒤로 옮겼습니다. list 반복자와 직렬 `scan_next_heap_scan`은 원래 참일 때만 셉니다.
- **D1:** 워커는 `task::finalize`의 맨 끝에서 배열 전체를 `trace_handler::add_px_stats`로 넘기고, 리더는 `trace_handler::merge_stats`에서 한 번 합칩니다.
  - 맨 끝에 두는 이유: finalize 안의 정리 작업이 fix한 페이지도 세기 위해서입니다.
  - `scan_close_parallel_{heap,list,index}_scan`의 모든 결과 유형에서 `wait_for_workers ()` + `merge_stats ()`를 부릅니다. close는 어떤 경우에도 지나가는 경로이므로 `S_ENDED`로 end가 건너뛰어져도 합산이 됩니다. 주석에 "scan_end_scan ()이 manager::end ()를 건너뛸 수 있다"고 적어 이유를 남겼습니다.
  - end와 close가 둘 다 `merge_stats`를 부를 수 있으므로 `m_merged`로 한 번만 합칩니다. 파티션마다 스캔을 다시 열 때 `clear ()`가 이 플래그를 되돌립니다.
- **SCAN 줄의 fetch는 따로 잽니다(`m_scan_fixes`).** 워커 배열에는 그 워커가 행마다 실행한 NL 안쪽 스캔, dptr 부질의, 결과 쓰기의 fix도 들어갑니다. 직렬 스캔의 SCAN 줄은 `scan_next_scan_local`이 페이지·슬롯 읽기 구간만 세므로, 워커도 같은 구간(`next_qualified_slot_with_peek`, `get_next_vpid_with_fix`, `wait_or_help_overflow`)의 앞뒤 차이만 SCAN 줄에 씁니다. 배열 전체는 SELECT 총계로 갑니다. 이렇게 해야 병렬과 직렬의 SCAN 줄 의미가 같습니다.
  - 루프 안에서는 `const bool on_trace = thread_ref.on_trace;`로 한 번 읽어 둡니다. 루프 안의 함수 호출 때문에 컴파일러가 멤버를 매 행 다시 읽을 수 있어서입니다.
- **E5:** `manager::open`이 리더 스레드의 `m_px_stats`를 memset하고 `merge_stats`가 해제하던 코드를 지웠습니다. 같은 스레드에서 hash join이 모으던 값을 지울 수 있었습니다. `m_px_stats_initialized_by_me`도 필요 없어져 지웠습니다.
- `add_px_stats`의 calloc이 실패하면 그 워커의 통계만 버리고 질의는 계속합니다. 통계 때문에 질의를 실패시키지 않습니다.

### 2.3 병렬 부질의 (`px_query_*`) — E1, E2, C2

- 작업(job)이 끝나면 배열 전체를 `trace_context::m_px_stats`에 합치고, `run_jobs`가 executor의 스레드에 한 번 합칩니다. 전에는 fetch, ioread, fetch_time, SP 4개 항목만 따로 모았습니다(`m_stats` 벡터와 `m_sp_*`). 이것을 배열 하나로 바꿨습니다.
- `trace_context`를 trace 여부와 상관없이 넘깁니다. 세션 통계만 볼 때도 job의 통계를 모아야 하기 때문입니다(C2).
- **E1:** 루트 스레드는 executor를 만들 때부터 `run_jobs` 끝까지 자기 배열에 쌓는데, 끝에 7개 항목만 트랜잭션 통계로 옮겼습니다. 이제 배열 전체를 옮깁니다. `run_jobs` 전에 오류로 끝나면 `~query_executor`가 같은 정리를 합니다. 전에는 배열이 남아 그 스레드의 다음 문장 통계가 사라졌습니다.
- **E2:** 작업이 끝나면 `on_trace`를 `!!trace_context_p`가 아니라 원래 값으로 되돌립니다.

### 2.4 병렬 hash join (`query_hash_join.c`, `px_hash_join*`)

- 워커 조각(`px_worker_stats`)을 trace일 때만이 아니라 `perfmon_parallel_stats_needed`일 때 할당합니다(C2).
- 단계(split, build, probe)마다 `hjoin_trace_drain_worker_stats`가 조각 전체를 `perfmon_add_values_to_local`로 합칩니다. 합산은 `px_worker_stats != nullptr`이면 하고, trace 종료 처리(`hjoin_trace_end`)는 trace일 때만 합니다. 두 조건이 달라졌으므로 `if`를 나눴습니다.
- 리더 스레드에 `m_px_stats`를 따로 만들던 코드와 `hjoin_clear_manager`의 트랜잭션 통계 합산을 지웠습니다. 합칠 곳은 `perfmon_add_values_to_local`이 정합니다.
- 조각 경계가 같은 캐시 라인을 공유할 수 있는 점(MEM-03)은 고치지 않았습니다. 경계에 걸리는 값이 자주 바뀌지 않는 항목이고, 측정 근거가 없습니다.

### 2.5 병렬 정렬 (`external_sort.c`) — D2, E3

- 정렬 워커 세 곳(`sort_listfile_execute`, `sort_merge_nruns_queue_cb`, `sort_put_result_for_parallel`)은 끝날 때 `sort_px_hand_over_stats`로 배열을 자기 `SORT_PARAM::px_stats`에 넘깁니다. 병합 큐 슬롯은 병합을 여러 번 하므로 두 번째부터는 더합니다.
- `sort_listfile`은 워커를 모두 정리한 뒤 `px_sort_param[i].px_stats`를 한 번 합치고 해제합니다. 워커가 리더의 배열에 직접 쓰지 않으므로 잠금이 필요 없습니다.
- **E3:** 정렬 워커는 trace일 때만 `thread_set_sort_stats_active`를 켜서, trace 없이 도는 병렬 정렬의 정렬 page가 statdump에서도 빠졌습니다. 리더(`sort_listfile`)처럼 항상 켭니다.

### 2.6 병렬과 무관한 항목별 오류 — D3, D4, D5, E4

- **D3 (`qexec_orderby_distinct`):** trace이면 기준값(`old_sort_pages/ioreads`)을 항상 읽습니다. 주석에 "첫 실행에서 이 플래그를 켜는 것이 바로 아래 정렬"이라고 적었습니다.
- **D4 (`qexec_hash_gby_put_next`):** 같은 키를 합칠 때 `tuple_count`도 더합니다. 한 그룹이 hash 표에서 두 번 이상 밀려나면 partial 항목이 여러 개 생기기 때문입니다. 처음엔 "+1 누락"으로 추정했는데 코드로 확인하니 틀려서 이 원인으로 바로잡았습니다. 병렬 hash 집계는 워커마다 partial 항목을 남기므로 GROUPBY readrows가 거의 항상 워커 하나 몫이었습니다. `input_recs`는 MERGE 원본 중복 검사(`ER_MERGE_TOO_MANY_SOURCE_ROWS`)에도 쓰여서 이 값이 맞아야 합니다.
- **D5 (`query_dump.c`):** JSON 조건을 text와 같게 `S_PARALLEL_HEAP_SCAN || S_HEAP_SCAN`으로 했습니다. 파티션 스캔은 마지막 파티션 뒤 타입이 `S_HEAP_SCAN`으로 돌아갑니다.
- **E4 (`qexec_init_next_partition`):** 파티션을 바꿀 때 리더 스레드의 `m_px_stats`(그 스캔과 무관한, hash join의 배열일 수도 있는)를 스캔 fetch에 더하던 코드를 지웠습니다. 워커 fix는 이미 `manager::merge_stats`에서 들어갑니다.
