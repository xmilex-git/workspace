# PR #8114: [CBRD-27567] NL 조인 memoize 키에 상관 스칼라 부질의 결과값이 포함되어 inner 행이 누락되는 문제

- PR: https://github.com/CUBRID/cubrid/pull/8114 (head `116bd0ace`)
  - `114360b8a` 본 수정, `09a423c26` develop 병합, `116bd0ace` anti join 살아남은 바깥 행(범위 추가, Greptile 리뷰에서 발견)
- JIRA: http://jira.cubrid.org/browse/CBRD-27567
- TC: CUBRID/cubrid-testcases#3655 (`sql/_36_guava/cbrd_27567`, 16 cases, memoize 사용 vs `memoize_memory_limit=0` 쌍). private-ex#4326은 빈 PR입니다.
- 바뀐 파일: `src/query/memoize.cpp`, `src/query/query_executor.c` (+86)

## 1. 무엇이 틀렸나

JIRA 질의는 memoize를 쓰면 82행, 쓰지 않으면 100행이었습니다. NL 조인의 inner에 상관 스칼라 부질의가 붙어 있으면 memo를 재생할 때 inner 행이 빠지거나, select 목록 부질의가 다른 행의 결과를 냈습니다. develop TC에서 Case 1–3은 82 vs 100, Case 4는 합계 50/170 vs 500/1700과 NULL 행, Case 6은 97 vs 104였습니다.

## 2. 원인

memoize는 inner를 "inner 술어가 읽는 상수들"을 키로 기억했다가, 같은 키가 오면 inner를 다시 스캔하지 않고 저장한 행을 재생합니다. 키를 만드는 `key_maker`에 두 문제가 있었습니다.

1. **inner의 상관 부질의(dptr) 결과가 키에 들어갔습니다.** `key_maker`는 inner 술어와 inner의 dptr 부질의에서 찾은 상수를 모두 키로 삼았는데, 여기에 상관 스칼라 부질의의 결과와, 부질의 outptr을 통해 들어온 집계 accumulator가 포함됐습니다. 이 값들은 memo를 조회한 *뒤* inner 행마다 계산됩니다. 그래서 행을 저장할 때의 키에는 그 행의 부질의 결과가, 다음 조회의 키에는 마지막으로 읽은 행의 결과가 들어가서, 결과가 다른 행은 재생되지 않았습니다.
2. **재생된 행은 inner의 상관 부질의를 초기화하지 않았습니다.** 스캔은 행을 읽을 때마다 dptr 부질의를 초기화합니다. 재생은 스캔을 건너뛰므로 이 초기화도 빠졌고, 가장 안쪽 스캔에 붙는 select 목록 상관 부질의가 그 행으로 계산되지 않은 값을 돌려줬습니다.

## 3. 고친 방식과 이유

### 3.1 inner의 dptr 부질의 결과를 키에서 뺌 (`memoize.cpp`)

```cpp
/* a correlated subquery runs again for every inner row, after the memo is probed, so its result is not an
 * input of the probe. Its correlated references, collected just above, key it instead (CBRD-27567). */
const_regu_var_vector.erase (std::remove_if (..., [xasl] (regu_variable_node *regu_var)
{
  for (XASL_NODE *dptr = xasl->dptr_list; dptr != NULL; dptr = dptr->next)
    if (regu_var->xasl == dptr) return true;
  return false;
}), ...);
```

- 키는 "조회 시점에 이미 정해진 입력"이어야 합니다. 부질의 결과는 조회 뒤에 계산되므로 입력이 아닙니다.
- 부질의는 키에서 사라지는 게 아니라, 그 부질의가 바깥에서 받는 상관 참조로 키에 들어갑니다(dptr 순회에서 이미 수집함). 같은 상관 참조면 부질의 결과도 같으므로 이것으로 충분합니다.

### 3.2 부질의 안에서는 상관 참조만 키로 남김

```cpp
/* only the subquery's correlated references come from outside it. Every other constant (its own columns, an
 * aggregate's accumulator, a nested subquery's result) is computed by the subquery itself, so its value when
 * the memo is probed is left over from the previous row and must not be part of the key (CBRD-27567). */
... return !REGU_VARIABLE_IS_FLAGED (regu_var, REGU_VARIABLE_CORRELATED);
```

- 판정 기준은 `REGU_VARIABLE_CORRELATED` 플래그입니다. subquery result cache가 키를 정할 때 쓰는 기준과 같아서, 새 판정을 만들지 않았습니다.
- 상관 참조를 놓치지 않으려고 수집 위치를 넓혔습니다: 집계 인자, PERCENTILE 비율, HAVING, rownum 술어(`instnum_pred`, `ordbynum_pred`). 키에서 바깥 컬럼이 빠지면 같은 조인 키의 바깥 행이 모두 첫 행의 재생을 받아 결과가 틀립니다.

### 3.3 `key_maker`가 다 보지 못하는 모양은 memoize하지 않음 (`possible_check`)

GROUP BY 키, 분석 함수, HAVING 안의 부질의(`eptr_list`), CONNECT BY가 있는 부질의는 `key_maker`가 그 안의 상관 참조를 모두 찾지 못합니다. 이런 모양에 키 수집을 더 늘리기보다 memoize를 쓰지 않는 쪽이 안전합니다. 키가 모자라면 오답이고, memoize를 안 쓰면 원래 실행일 뿐이기 때문입니다.

### 3.4 재생한 행마다 inner의 dptr 부질의를 초기화 (`qexec_execute_nljoin_with_memoize`)

- 재생은 스캔을 건너뛰므로, 스캔이 행마다 하던 `qexec_execute_dptr_list (..., true)`를 재생 행마다 똑같이 합니다. 첫 재생 행과 이어지는 재생 행 두 곳에 넣었습니다.
- 효과: 행을 소비하는 쪽이 읽는 부질의(가장 안쪽 스캔에 붙는 select 목록 부질의)는 그 행으로 다시 실행되고, inner 술어만 읽는 부질의는 다시 실행되지 않습니다(재생된 행은 이미 그 술어를 통과함).
- **키 끝(ENDED)에서는 초기화하지 않습니다.** 일반·SEMI inner의 키 끝은 행을 내보내지 않으므로 비용만 듭니다(Greptile 지적 반영).

### 3.5 (범위 추가) NL anti join에서 살아남은 바깥 행도 초기화 (`qexec_execute_sa_anti_survive`)

Greptile의 "ENDED에서 초기화하지 말라"는 지적을 검토하다 찾았습니다.

- ANTI inner의 ENDED(memo에 캐시된 "매치 없음")는 살아남은 바깥 행을 *내보내므로* 초기화가 필요합니다. 그래서 위치만 옮겨서는 안 됐습니다.
- 이 경로는 스캔의 S_END와 함께 `qexec_execute_sa_anti_survive ()`를 거칩니다. 그런데 이 함수가 원래 inner의 상관 부질의를 초기화하지 않아서 develop에도 결함이 있었습니다(CBRD-26872, memoize와 무관). anti inner가 중간 스캔 아래의 가장 안쪽 스캔이면, 같은 root 행 아래에서 연달아 살아남은 바깥 행이 앞선 행의 select 목록 부질의 결과를 읽었고, subquery cache가 켜져 있으면 그 결과가 새 키로 캐시되었습니다. develop에서 TC Case 11은 memoize 사용·미사용, cache 사용 모두 8행 중 4행이 틀립니다.
- 그래서 초기화를 이 함수 안으로 넣어 스캔 경로와 memo 경로를 한 곳에서 고쳤습니다. 사용자에게 "이 PR에서 함께(B)"를 물었고 B로 정했습니다.
- **부수 효과(리뷰에서 확인):** `qexec_execute_dptr_list ()`는 LINK 플래그가 없는 dptr(바깥 행에 상관된 derived table)는 초기화에 그치지 않고 실행합니다. develop은 살아남은 바깥 행에서 이것을 실행하지 않아, 명시적 ANTI JOIN inner 바로 뒤의 상관 derived table이 비어 질의가 0행을 냈습니다. 이 PR에서는 맞는 행이 나옵니다. soheejung-cs 리뷰 제안대로 PR 본문에 적고 TC Case 15로 고정했습니다. memoize 경로에는 이런 dptr이 없습니다(`possible_check`가 거부).

## 4. 고치는 과정에서 버린 것

- v2는 "바깥 노드" 부질의와 IN 목록까지 키에 넣었습니다. `show trace`의 들여쓰기를 잘못 읽어 MEMOIZE와 SUBQUERY의 소속을 오해한 것이었고, 상관 수준 1 부질의는 의사 상수가 아니라 inner의 dptr에 붙는다는 것을 확인한 뒤 도달할 수 없는 코드로 보고 지웠습니다(v3 = 현재 커밋).

## 5. 범위 밖

- 상관 GROUP BY 스칼라 부질의가 NL inner 술어에 있으면 optdebug assert(`qfile_update_domains_on_type_list`)가 나는 develop 결함: workspace#383 = CBRD-27572. 그래서 TC에 GROUP BY 케이스가 없고, `possible_check`가 그 모양을 memoize하지 않습니다.
- SEMI/ANTI inner 컬럼을 FROM 절 derived table 안에서 참조해도 `pt_check_semi_anti_join ()`이 거부하지 않는 검사 누락: workspace#430으로 기록했고 Hamkua 님이 #8144에서 고치기로 했습니다.

Case 12–14(CASE rownum, CASE orderby_num, CONNECT BY)는 Greptile 리뷰를 반영해 추가했습니다. Case 15, 16은 soheejung-cs 리뷰를 반영해 추가했습니다(Case 16은 바깥 컬럼이 부질의의 인덱스 key range에만 있는 모양).
