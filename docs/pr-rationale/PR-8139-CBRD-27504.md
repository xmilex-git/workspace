# PR #8139: [CBRD-27504] 날짜/시간 값의 TO_CHAR 포맷 인자에 BIGINT를 바인드하면 서버가 죽는 문제

- JIRA: http://jira.cubrid.org/browse/CBRD-27504
- TC: CUBRID/cubrid-testcases#3700 (`sql/_13_issues/_26_2h/cbrd_27504`, 8 cases). private-ex#4377은 변경이 없는 빈 PR입니다.
- 바뀐 파일: `src/query/string_opfunc.c` 하나 (+8)
- 상태: beyondykk9, jihyekim-0 승인. gha-ci run 38193922705 모두 통과.

## 1. 어떤 SQL이 틀렸나

```sql
create table tg (g int, dtt datetime);
insert into tg values (1, datetime'2024-01-02 10:00:01.500');
prepare s from 'select to_char(dtt, ?) from tg where g = 1';
execute s using 'YYYY-MM-DD';             -- '2024-01-02'
execute s using 9007199254740993;         -- release: cub_server SIGSEGV, debug: assert
```

JDBC `setLong`으로 바인드해도 같습니다. 바인드 값 하나로 서버 프로세스가 죽으므로 그 서버의 모든 세션이 끊깁니다.

## 2. 원인

- `PT_TO_CHAR`는 `pt_is_op_hv_late_bind`에 들어 있습니다. 그래서 TO_CHAR 인자에 쓴 호스트 변수는 컴파일 때 형변환되지 않고, 바인드한 값이 그대로 실행기까지 갑니다. 세션 변수(`@f`)도 같습니다. 반면 리터럴이나 컬럼을 포맷으로 쓰면 컴파일 때 문자열로 변환되고, 맞지 않으면 -783이 납니다.
- 숫자를 변환하는 `number_to_char`는 포맷이 문자열인지(`is_char_string`) 먼저 확인합니다.
- 날짜/시간을 변환하는 `date_to_char`는 이 확인이 없었습니다. BIGINT 값의 바이트를 문자열 헤더와 버퍼 포인터로 읽었고, 그 결과 debug는 `db_check_or_create_null_term_string`의 `QSTR_IS_ANY_CHAR` assert로, release는 SIGSEGV로 죽었습니다.

## 3. 고친 방식과 이유

```c
/* a host variable is bound here without a cast (late binding), so the format can be any type */
if (!is_char_string (format_str))
  {
    error_status = ER_QSTR_INVALID_DATA_TYPE;
    er_set (ER_ERROR_SEVERITY, ARG_FILE_LINE, error_status, 0);
    goto exit;
  }
```

- **위치.** 포맷이 NULL인지 보는 검사 바로 뒤, 포맷을 처음 문자열로 읽는 `db_get_string_length (format_str)` 앞입니다. 문자열로 읽기 전에 막아야 하므로 여기가 가장 이른 지점입니다. NULL 포맷은 지금처럼 NULL 결과를 돌려줍니다.
- **오류 코드.** `ER_QSTR_INVALID_DATA_TYPE`(-621)는 `number_to_char`가 같은 상황에서 이미 돌려주는 코드입니다. TO_CHAR 하나가 첫 인자 타입에 따라 다른 오류를 내지 않도록 맞췄습니다.
- **방향.** JIRA에서 park se hun 님이 "포맷 인자 타입 검사만 보강하면 될 것"이라고 정리한 방향과 같습니다.
- **주석.** "late binding이라 포맷이 어떤 타입이든 올 수 있다"는 이유를 한 줄로 남겼습니다. 그렇지 않으면 다음 사람이 "포맷은 컴파일 때 문자열로 정해지는데 왜 검사하나"라며 지울 수 있습니다.

## 4. 택하지 않은 방법

- **컴파일 때 포맷 호스트 변수를 VARCHAR로 형변환하기**(`PT_TO_CHAR`의 late binding 처리를 바꾸기). `pt_is_op_hv_late_bind`는 TO_CHAR를 포함해 40개 가까운 연산자가 함께 쓰는 규칙이고, 컴파일 쪽 여러 곳(`pt_coerce_expression_argument`, `pt_infer_common_type`, `pt_to_regu_variable` 등)이 이 규칙을 봅니다. TO_CHAR의 포맷 인자만 따로 빼면 TO_CHAR 바인드 처리 전체가 바뀌고 범위가 커집니다. 서버가 죽는 문제는 값을 문자열로 읽는 실행 함수 한 곳의 입력 검증으로 충분히 막힙니다.
- **포맷 값을 실행기에서 문자열로 형변환해서 계속 진행하기.** `number_to_char`와 동작이 갈라지고, BIGINT를 포맷 문자열로 해석하는 것은 의미가 없습니다.

## 5. 동작 변화 (알고 있어야 할 것)

포맷에 문자열이 아닌 값을 바인드하면 이제 모두 -621입니다. 그전에는 값에 따라 결과가 달랐습니다.

| 바인드한 포맷 | 수정 전 | 수정 후 |
|---|---|---|
| BIGINT 9007199254740993, 4294967297 | debug assert / release SIGSEGV | -621 |
| BIGINT 1, INT 1, DOUBLE 1.5, NUMERIC 1.50, DATE | -782 (Empty string not allowed here) | -621 |
| BIT VARYING `X'59595959'` | debug assert / release `'2024'` (비트 바이트를 "YYYY" 포맷으로 사용) | -621 |
| 문자열, NULL | 그대로 | 그대로 |

-782나 `'2024'`는 우연히 메모리를 그렇게 읽은 결과라서 지켜야 할 동작이 아닙니다. 컬럼이나 리터럴을 포맷으로 쓰는 경우는 컴파일 때 형변환되므로 바뀌지 않습니다(리뷰어가 ENUM, CLOB, BIT, SET 컬럼으로 확인).

## 6. 검증

- probe 22개를 SA, CS, JDBC에서 pre와 fix, optdebug와 release 네 설치본으로 돌렸습니다. pre는 BIGINT에서 optdebug assert, release crash. fix는 모든 경로가 -621이고 세션이 살아 있습니다. PL/CSQL은 -889가 -621을 감싸서 나옵니다.
- 같은 모양의 다른 함수 확인: `STR_TO_DATE`는 모든 빌드에서 -204를 돌려주므로 같은 결함이 없습니다. 리뷰어도 `pt_is_op_hv_late_bind()` 연산자 전체를 서버 함수까지 추적해서, 형식 검사 없이 문자열로 읽던 곳은 `date_to_char` 한 곳뿐임을 확인했습니다.
- TC `cbrd_27504`: pre는 assert로 NOK, fix는 4/4 OK. CTP의 `$bigint` 바인드는 문자열로 넘어가므로 TC는 `execute s using 9007199254740993`으로 BIGINT를 바인드합니다. 리뷰 제안에 따라 scalar subquery `(select ? from db_root)`로 바인드하는 경우를 Case 7에 넣었습니다(TC `8cdea8af3`).
- 게이트: release와 optdebug 빌드 성공. optdebug sql 17510/17510, medium 975/975, core 0.
