# PR #8136: [CBRD-27596] 병렬 heap 스캔 아래 상관 부질의가 SQL을 실행하는 미선언 저장 함수를 부르면 질의가 끝나지 않는 문제

- PR: https://github.com/CUBRID/cubrid/pull/8136 (head `4a5256c99` = `1d477f24f` 본 수정 + `4a5256c99` 리뷰 반영)
- JIRA: http://jira.cubrid.org/browse/CBRD-27596
- TC: CUBRID/cubrid-testcases#3696 (`cbrd_27596`, Case 1–12). private-ex#4373은 빈 PR입니다.
- 바뀐 파일: `src/query/parallel/px_scan/px_scan_checker.cpp`, `src/sp/pl_execution_stack_context.hpp` (+166 −4)

## 1. 어떤 SQL이 틀렸나

`t_big`이 1,000,000행이고 `f_sq`가 PARALLEL_ENABLE로 선언하지 않은, 정적 SQL을 실행하는 PL/CSQL 함수일 때:

```sql
-- S01: 상관 스칼라 부질의의 select 목록에 미선언 함수
select count(*) from t_big where a <= 10 and b > (select f_sq (z.b) from t_small z where z.a = mod (t_big.a, 3) + 1);
```

- release: 질의가 끝나지 않습니다. Ctrl-C도 듣지 않고, 잠금을 쥔 채 남아서 다른 세션의 DDL이 막힙니다. `cubrid killtran`이나 서버 중지로만 풀립니다.
- debug: 첫 호출에서 `pl_execution_stack_context.hpp`의 `m_is_parallel_enabled_sp || !m_is_px_worker` assert로 abort합니다.
- SQL이 없는 미선언 함수도 결과는 맞지만 O(N²)로 느려지다가 연결이 끊깁니다(N=20000에서 직렬 1.09초, 병렬 17.5초).

함수 위치를 바꿔 가며 재현한 모양이 20개입니다. 부질의의 select 목록, 집계 인자, GROUP BY / HAVING / ORDER BY / PARTITION BY, 인덱스 key range, NL 조인의 두 번째 테이블, 중첩 부질의, 바깥 NL 안쪽 테이블의 key range 등입니다.

## 2. 원인

- **실행 쪽:** px 워커는 부모의 `conn_entry`를 물려받지만 요청 번호(`rid`)는 0입니다. 클라이언트(CAS)는 자기 요청 번호의 패킷에만 답하므로, 워커가 보낸 SP 콜백에는 아무도 답하지 않습니다. 그래서 미선언 SP는 워커에서 실행되면 안 되고, 이것은 계획 단계의 병렬 스캔 적격성 검사(`px_scan_checker.cpp`)가 막아야 합니다.
- **계획 쪽:** 검사기는 regu에 연결된 부질의를 `sibling_check ()`로 봅니다. 그런데 이 함수는 원래 "그 부질의의 스캔을 나눌 수 있는가"를 판단하려고 만든 것이라, 부질의 첫 테이블의 술어처럼 그 판단에 필요한 자리만 봅니다. 그래서 위에 적은 자리에 있는 미선언 SP를 보지 못했고, 바깥 스캔이 병렬로 실행되어 그 부질의(와 SP)를 워커가 평가했습니다.

## 3. 고친 방식과 이유

### 3.1 별도 walker를 만들지 않고 기존 검사를 넓힘

처음 조사 보고서는 "부질의 트리 어디든 미선언 SP가 있는가"를 보는 별도 walker(`sp_walk`)를 추천했습니다. 사용자가 "별도 walker 없이 기존 `sibling_check` / `check`를 확장하라"고 정해서 그렇게 했습니다. 판정 규칙과 순회가 한 곳에 있어야, 나중에 자리 하나를 추가할 때 두 곳을 같이 고쳐야 하는 일이 생기지 않습니다.

### 3.2 새 플래그 `CANNOT_RUN_IN_WORKER`

```cpp
/* the checked part calls an SP not declared PARALLEL_ENABLE or a method: a px worker cannot
 * run it, since its callbacks to the client are never answered (CBRD-27596) */
const possible_flags CANNOT_RUN_IN_WORKER = 0x1 << 3;
```

- 미선언 `TYPE_SP`와 `TARGET_METHOD` spec이 이 플래그를 세웁니다. 메서드 스캔도 SP처럼 클라이언트에 콜백하므로 같은 대상입니다.
- **새로 보는 자리에서는 이 플래그만 위로 올립니다.** `result |= temp & CANNOT_RUN_IN_WORKER;` 모양입니다. 새로 보는 자리(select 목록, 집계 등)가 원래 `CANNOT_PARALLEL_SCAN`을 만드는 다른 이유(예: 어떤 연산자)를 갖고 있어도, 그것까지 올리면 SP와 상관없는 부질의의 계획이 바뀝니다. SP가 없는 부질의는 계획이 그대로여야 하므로 이 플래그 하나만 가져옵니다. 실제로 함수 없는 25개 모양과 선언 함수(`f_pp`) 25개 모양의 계획이 수정 전과 한 줄도 다르지 않았습니다.

### 3.3 판정은 "SP를 그 자리에 직접 쓴 경우"와 같게

```cpp
/* the thread that evaluates this regu runs the whole subquery, so an SP or method in it
 * counts as one written here (TYPE_SP below) */
if (is_flag_set (temp, CANNOT_RUN_IN_WORKER))
  {
    set_flag (result, CANNOT_RUN_IN_WORKER);
    set_flag (result, is_outptr_list ? CANNOT_LIST_MERGE : CANNOT_PARALLEL_SCAN);
  }
```

- 부질의를 평가하는 스레드는 그 부질의 전체를 실행합니다. 그러니 부질의 안 어딘가의 미선언 SP는 "그 부질의가 걸린 자리에 SP를 직접 쓴 것"과 같습니다.
- 기존 규칙은 출력 목록의 SP면 `CANNOT_LIST_MERGE`(병렬 스캔은 유지하고 row by row로 리더가 평가), 그 밖이면 `CANNOT_PARALLEL_SCAN`(직렬)입니다. 같은 규칙을 그대로 씁니다. 그래서 바깥 select 목록·집계 인자 자리의 부질의(S03, S18, S19)는 병렬을 유지하고, 나머지는 직렬이 됩니다.
- 사용자에게 "출력 목록·집계 인자 자리는 row by row로 병렬 유지 vs 무조건 직렬"을 물었고, 병렬 유지(추천)로 정했습니다.

### 3.4 `sibling_check (XASL_NODE *)`가 보는 자리 확대

`outptr_list`, `during_join_pred`, `instnum_pred` / `ordbynum_pred` / limit, BUILDLIST의 그룹·분석 목록(`g_*`, `a_*`, 분석 함수 피연산자), BUILDVALUE의 `agg_list` / `having_pred` / `outarith_list`, `merge_spec`, `scan_ptr`(조인의 두 번째 이후 테이블), aptr 하위 트리, CTE의 두 부분입니다. 기존 dptr, `after_join_pred`, `if_pred` 경로도 이 플래그를 넘기게 했습니다.

### 3.5 `sibling_check (ACCESS_SPEC_TYPE *)`: key range와 스캔 입력

- `where_key`, `where_range`, 인덱스 key range와 key limit, hash list scan의 probe 목록을 봅니다. 이 값들은 그 스캔을 실행하는 스레드가 평가하고, NL 안쪽이면 바깥 행마다 평가합니다. 그래서 부질의가 없는 바깥 NL 안쪽 key range(S25)도 여기서 걸립니다.
- `TABLE ()`의 집합(`set_ptr`)과 `JSON_TABLE ()`의 입력 문서(`m_json_reguvar`), 두 대상의 WHERE도 봅니다(리뷰 반영 `4a5256c99`, 5절).
- 여기서 찾으면 스캔 자체를 직렬(`CANNOT_PARALLEL_SCAN`)로 만듭니다. key range는 출력 목록이 아니므로 row by row로 피할 수 없습니다.

### 3.6 `check (AGGREGATE_TYPE *)`: 집계 하나를 한 함수로

PERCENTILE_CONT/DISC의 비율(`info.percentile.percentile_reguvar`)은 피연산자가 아니지만 행마다 함께 평가됩니다. 그래서 집계 하나의 피연산자와 비율을 함께 보는 함수를 만들고, 집계 목록을 도는 모든 곳(부질의, dptr 하위 트리, 병렬 스캔 자체의 BUILDVALUE_OPT 판정)이 이것을 쓰게 했습니다. 한 곳만 고치면 같은 누락이 다른 곳에 남기 때문입니다. 병렬 스캔 위 집계의 비율에 SP가 있으면 스캔은 병렬로 두고 집계는 메인 스레드가 합니다(`gather: row by row`).

### 3.7 `sibling_check` 결과 캐시

```cpp
/* sibling_check results, one map per is_outptr_list. A nested subquery is reached through its regu
 * and through its parent's aptr / dptr link, so without the cache deep nesting costs 2^depth. */
thread_local std::unordered_map<XASL_NODE *, possible_flags> xasl_sibling_check_cache[2];
```

- 첫 전체 CTP 게이트에서 `_28_features_930/issue_13226/01_alias_name_group_by_having_001.sql`(30단 중첩 부질의)이 hang watchdog에 걸렸습니다. 새 aptr 재귀와 regu 경로가 같은 부질의를 두 번씩 방문해서 2^깊이가 된 것입니다(깊이 18에서 0.75초).
- `check (XASL_NODE *)`가 이미 쓰는 방식(방문 전에 sentinel 0을 넣어 순환도 막는 캐시)을 그대로 따랐습니다. 수정 후 깊이 30이 0.04초로 수정 전과 같아졌습니다.
- 결과가 `is_outptr_list`에 따라 다르므로 맵을 두 개 둡니다. `scan_check_parallel_scan_possible`의 시작과 끝에서 다른 캐시와 함께 비웁니다.

### 3.8 실행 쪽 방어: px 워커의 서버측 SQL 거부

```cpp
assert (m_is_parallel_enabled_sp || !m_is_px_worker);
return m_is_parallel_enabled_sp || m_is_px_worker;
```

- 계획 단계 검사가 앞으로 어떤 자리를 또 놓치더라도, release에서 무한 대기(잠금을 쥔 채) 대신 즉시 오류(-889)가 나게 합니다. SQL이 없는 함수는 영향 없이 정답을 냅니다.
- debug assert는 그대로 둡니다. 검사기가 놓친 경우를 개발 중에 바로 알아야 하기 때문입니다.
- 사용자에게 "release 방어 한 줄을 넣을지"를 물었고 넣기로 정했습니다.

## 4. 범위 밖과 알려진 제약

- **비상관 스칼라 부질의(precomp)에 있는 미선언 SP도 바깥 스캔을 직렬로 만듭니다(S20).** row by row 모드에서 precomp 값이 워커에 전달되지 않는 CBRD-27588(#8132)이 고쳐진 뒤 완화할 수 있습니다. 사용자 결정: "예외 없음, 27588 머지 후 완화".
- **메서드는 계획 단계 검사로만 막힙니다.** `method_invoke_group`이 `xs_callback_send_*`를 직접 불러 `is_server_side_sql_forbidden ()`을 거치지 않습니다.
- trace를 켠 상태에서 부질의에 hash join이나 UNION이 있으면 SP와 상관없이 release 서버가 죽는 문제는 조사 중 찾아서 CBRD-27598(#8138)로 따로 고쳤습니다.
- CBRD-27593(#8134)도 `px_scan_checker.cpp`를 고칩니다. 먼저 머지된 쪽에 맞춰 다른 쪽을 rebase해야 합니다.
