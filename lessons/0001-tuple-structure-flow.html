문제 정의와 해결 방향 · 2–3분

기존 qfile은 각 값에 flag 4B와 길이 4B를 붙이고 본문을 8B 단위로 정렬했다. INT 본문은 4B지만 컬럼 하나에 헤더 8B + 정렬된 본문 8B = 16B가 필요했다. 행 수와 컬럼 수가 늘면 이 반복 비용도 늘어난다.

이미 type_list가 가진 도메인에서 고정 길이와 정렬 규칙을 계산한다. NULL은 조건부 비트맵으로 모으고, 가변 값만 길이를 저장한다. 목표는 임시 리스트 크기 감소이며, 모든 질의의 실행시간 개선을 보장하는 것은 아니다.

첨부 HTML에 기록된 초기 대안은 고정폭 전용 포맷과 전환 파라미터였다. 현재 PR은 단일 포맷으로 교체한다. 두 종류의 reader/writer를 유지하는 부담을 피한다는 설계 방향이다. 정렬을 항상 8B로 하는 대안 대신 4B를 사용하고, 정렬이 필요한 가변 타입은 저장할 때 정렬해 반복 복사를 피한다.

큰 그림과 데이터 구조 · 2–3분

실행기가 값을 만들고 → 리스트에 저장하고 → scan·정렬·집계·cursor가 읽는 큰 흐름은 유지된다. 바뀌는 지점은 가운데의 튜플 조립과 해석이다. 아래 구조체 전체를 행마다 디스크에 저장하는 것은 아니다.

    ↓ qfile_type_list_finalize
공통 레이아웃 tl
    + 컬럼 입력 src[]
    ↓ qfile_tuple_size
전체 길이 + has_null + src[i].len
    ↓ 호출자가 버퍼/페이지 공간 확보
    ↓ qfile_tuple_fill
튜플 바이트
    ↓ slot_bind(tl), slot_set_tuple(tpl)
슬롯 + 컬럼 번호
    ↓ qfile_slot_locate
본문 포인터 + 본문 길이 + NULL 여부
    ↓ qfile_slot_read_value (+ domain, copy)
DB_VALUE / is_null

size와 fill은 2패스다. size에서 본문 길이를 구해 저장하므로 fill이 다시 계산하지 않는다. 미확정 VARIABLE 도메인은 첫 non-NULL 값으로 확정하고 레이아웃을 재계산할 수 있다. 역방향 리스트의 prev_len은 fill이 아니라 페이지 writer가 채운다.

locate는 가변 길이 헤더를 제외한 본문을 반환한다. read_value는 그 본문을 인코딩에 맞게 해석한다. NULL이면 is_null=true를 돌려주고 출력 DB_VALUE는 그대로 둔다. 호출자가 NULL을 처리해야 한다. copy=false일 때 참조형 값은 튜플 바이트 수명에 의존한다.

고정 접두부이면서 앞에 NULL이 없으면 주소는 tpl + data_off + col[i].off다. 첫 가변 컬럼 또는 첫 NULL 이후는 길이를 따라 걷는다. nvalid/off로 진행 위치를 기억하며, 새 튜플을 설정하면 캐시를 초기화한다. 임의 순서 접근 전체가 O(1)인 것은 아니다.

size/fill · read_value 계약 · 위치 탐색

새 로직: 실제 저장 형식 · 2–3분

같은 행: (INT 7, VARCHAR 'abc'), 정방향

OLD 40B
[행 길이 4][prev_len 4]
[flag 4][길이 4][INT 4][패딩 4]
[flag 4][길이 4][문자열 표현 4][패딩 4]

NEW 12B
offset  0         4         8   9       12
        [길이 4B][INT 7 4B][03][a b c 3B]

NEW (NULL, 'abc') 12B
offset  0         4    5       8   9       12
        [길이+N ][02 ][패딩 3][03][a b c 3B]
비트맵 02: bit0=0 → INT NULL, bit1=1 → 문자열 있음

NULL은 본문 0B지만 비트맵과 패딩이 추가될 수 있어, NULL로 바꾼다고 행이 반드시 더 작아지지는 않는다. 40→12는 이 예시의 70% 축소이며 파일 전체의 감소율과 같지 않다.

영역현재 규칙
행 길이4B. bit31은 has-null, 나머지는 전체 길이. 전체 길이는 4B 배수.
prev_lenQFILE_FLAG_BACKWARD 리스트만 추가 4B.
비트맵NULL이 있을 때만 ceil(컬럼 수/8)B. 1=값 있음, 0=NULL. 값 영역 시작은 ALIGN4.
고정폭타입 크기 그대로. 정렬 요구는 최대 4B. BIGINT는 여전히 8B.
VAR / DIRECT문자열·BIT·NUMERIC 등. 비정렬, index_* 인코딩. 본문 0–127B는 1B 헤더, 128B 이상은 4B.
VAR / SCRATCHSET·JSON·ELO·OBJECT 등. 4B 정렬 + 항상 4B 헤더 + data_* 본문. 이름과 달리 현재는 제자리 디코딩.
패딩정렬 공간일 뿐 내용은 미정의. 문자열 NUL 종료로 사용 불가.

타입별 배치와 길이 헤더 원문

영향 범위와 리스크 · 1분

리스트 생산·소비 경로인 정렬, 집계, 조인, 실행기, 서버/SA/클라이언트 cursor가 영향을 받는다. P_sort_key도 키 컬럼의 미니 튜플을 사용한다. DIRECT 비교는 index_cmpdisk, FIXED/SCRATCH 비교는 data_cmpdisk로 저장 인코딩에 맞춘다.

or_pack_listid에는 hdr_size가 추가된다. 첨부 HTML은 클라이언트·서버 혼합 버전 미지원과 동시 업그레이드 전제를 기록한다. 힙 레코드의 영속 저장 형식 변경과는 구분해야 한다.

페이지 수 감소는 병렬도와 해시조인의 실행 경로 선택까지 바꿀 수 있다. HTML의 TPC-H 결과 동치 및 A/B 수치는 해당 측정 조건의 보고이며 이번 수업에서 재실행하지 않았다. HTML은 NULL 도메인 UNION의 알려진 결과 차이도 기록한다. ‘모든 SQL 결과와 성능이 동일’이라고 발표하지 않는다.
