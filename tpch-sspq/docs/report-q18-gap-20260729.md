# Q18 격차 규명 — 1.21x는 "격차가 작다"가 아니라 **두 플랜 오류의 상쇄**다

조사일 2026-07-29. 대상은 TPCH-SSPQ 절대격차 Pareto **5위 Q18**(G2 stream 기준
CUBRID 38.659 s / PG 31.842 s = **1.21x**, positive_pareto 4.92 %, 절대격차 +6.817 s).
완주 19개 중 배수가 거의 꼴찌인데 절대격차가 5위인 이유는 **양쪽 다 느린 쿼리**이기 때문이다.

**하위 레짐(ADR 0016)**: 이 보고서의 모든 표는 **`single-query-repeat`**이다. G2 값(stream)과 같은
표에 합치지 않는다. **단위 파리티(ADR 0014)**: CUBRID `parallelism=6`(conf) ↔ PG
`max_parallel_workers_per_gather=5` **세션 SET**(+leader) = 양쪽 6 실행 단위.

---

## 0. 결론 요약 (5줄)

1. **1.21x는 상쇄값이다.** 같은 플랜 형상에서 재면 **1.92x**다. CUBRID는 집계에서 1.96x 지고,
   PG는 상위 조인에서 10.59 s(wall의 34.6 %)를 **자기 통계 오류로** 버린다. 두 손실이 서로를 지운다.
2. **양쪽 다 실행 단위를 잃는다 — 이 프로젝트 최초.** wall의 6단위 구간은 CUBRID 29.8 % / PG 34.2 %뿐이고,
   나머지는 사실상 1단위다(CUBRID 69.8 %, PG 65.8 %). **격차 7.56 s의 86 %가 직렬 구간에서 난다.**
3. **`instructions` 비가 처음으로 1 미만이다** — **0.858x**(CUBRID가 **더 적게** 실행한다).
   `cycles` 1.159x, wall 1.247x. **IPC가 역전됐다**(CUBRID 1.811 vs PG 2.447 = **0.740x**).
   "instructions 비는 시간 격차의 상한"이라는 규칙이 Q18에서 깨진다 — 여기서는 **하한**이다.
4. **CUBRID 직렬 구간(26.67 s)의 정체는 GROUP BY 정렬이고, 병렬화가 코드로 금지돼 있다** —
   `external_sort.c:5232` `if (px == NULL || px->hash_eligible) return 1;`. 그 구간 cycles의
   **23.2 %가 버퍼 고정·래치**(경합이 없는 단일 스레드인데도)이고 12.0 %가 임시파일·스필이다.
5. **PG 직렬 구간의 정체는 `n_distinct` 37.8배 과소추정이다** — `pg_stats.n_distinct(l_orderkey)`
   397,034 vs 실제 15,000,000. 그래서 lineitem을 **두 번째로 전체 순차 스캔**하고 orders 해시를
   128배치로 스필한다. CUBRID의 NDV 추정은 14,929,885(오차 0.47 %)로 **정확하다**.

**HAVING 서브쿼리를 양쪽이 어떻게 처리하는가 — 이번 쿼리의 고유 질문**

| | CUBRID | PostgreSQL |
|---|---|---|
| 서브쿼리 취급 | **비상관 서브쿼리(uncorrelated)** → 파생 테이블 `av1861`로 **한 번 실체화** | **semi-join 전개 안 함** → 별도 집계 결과를 해시 테이블로 만들어 조인 |
| 스캔 sarg 못박기(Q21형) | **아님** — `TABLE SCAN → GROUPBY → distinct`의 독립 노드 3개 | 아님 — `Parallel Seq Scan → Partial HashAggregate → Sort → Gather Merge → Finalize GroupAggregate` |
| 집계 방식 | 워커 6개 partial hash agg + **직렬 외부 정렬 병합** | 워커 6개 partial hash agg(스필) + **워커별 외부 정렬** + Gather Merge + 직렬 streaming finalize |
| 서브쿼리 결과 카디널리티 추정 | **14,929,885** (실제 624, 23,926x 과대) | **132,345** (실제 624, 212x 과대) |
| ↳ 그 추정의 출처 | l_orderkey NDV 14,929,885 (실제 15,000,000, **오차 0.47 %**) + HAVING 선택도 미적용 | `pg_stats.n_distinct` = **397,034** (실제 15,000,000, **37.8x 과소**) × 부등식 기본 선택도 1/3 |
| 상위 3-way 조인 | **idx-join 체인** — `sscan av1861(624행)` → `iscan orders.pk` → `iscan customer.pk` → `iscan lineitem.pk` | **해시조인 2단** — `Seq Scan lineitem(60M, 직렬)` ⋈ `Hash(624키)`, 그 결과 ⋈ `Hash(orders 15M, 128배치 스필)`, 그 위 `Merge Join` + `Index Scan customer_pkey(1.5M)` |
| 상위 조인 실측 비용 | **0.048 s** (trace: SELECT 42,970 − SUBQUERY 42,922) | **10.59 s** (§2.3 부분 분리 실측) |

**핵심**: 양쪽 모두 HAVING 서브쿼리를 **별도 집계 노드**로 처리한다(Q21처럼 스캔 sarg로 못박지 않는다).
갈리는 곳은 **집계 결과를 상위 조인에 붙이는 방법**이다 — CUBRID는 624행을 드라이버로 삼는
인덱스 NL을 골랐고, PG는 132,345행으로 오추정해 lineitem을 **두 번째로 전체 스캔**했다.

`GROUPBY`에 **`(parallel workers: N)` 주석이 없다** — 이 노드는 직렬이다. 스필량은 양쪽이 맞먹는다:
CUBRID 423,552 × 16 KiB = **6.8 GB**, PG temp written 1,123,217 × 8 KiB = **9.0 GB**.

**분포 표기(ADR 0018 §4 정정 반영)**: CUBRID Q18 = **`1×6 + 직렬 2`**
(`sscan lineitem` 6워커 / GROUPBY 직렬 · ORDERBY 직렬). 상위 조인 노드 4개는 624~4,368행이라
시간 가중 0.1 %이므로 판정에서 제외한다.

### 2.4 같은 엔진 A/B — 플랜 축

**(a) PG에 CUBRID 형상 강제 — 형상 일치 성공**

`SET enable_hashjoin=off; SET enable_mergejoin=off; SET enable_eager_aggregate=off;`
(세션 GUC만. 클러스터 기본값 무변경.) `enable_eager_aggregate`는 이 pin(20devel)의 신규 기능이며
`enable_hashjoin=off` 단독으로는 lineitem을 **두 번 집계하는** 다른 형상이 나와 반드시 같이 꺼야 했다.

노드 대조 (raw `q18/raw/s2/pg-cubshape.plan`):

| CUBRID 정본 | PG CUBRID형상 강제 | 실제 행수 |
|---|---|---|
| `temp(order by)` | `Limit → Sort` | 100 |
| `temp(group by)` | `GroupAggregate ← Incremental Sort` | 624 ← 4,368 |
| `idx-join` inner `iscan lineitem.pk` | `Nested Loop` inner `Index Scan lineitem_pkey` | 4,368 |
| `idx-join` inner `iscan customer.pk` | `Nested Loop` inner `Index Scan customer_pkey` | 623 |
| `idx-join` inner `iscan orders.pk` | `Nested Loop` inner `Index Scan orders_pkey` | 624 |
| `sscan av1861` (= `temp(distinct)←temp(group by)←sscan lineitem`) | `Finalize GroupAggregate ← Gather Merge ← Sort ← Partial HashAggregate ← Parallel Seq Scan` | 624 ← 15,001,810 ← 59,986,052 |

**6개 노드가 1:1 대응하고 실제 행수가 전부 일치한다.** 형상 일치 채증 완료.

| | wall | CPU | 이용률 |
|---|---|---|---|
| PG 정본 | 30.624 s | 86.173 s | 2.814 (46.9 %) |
| **PG CUBRID형상** | **20.343 s** (별 브래킷 19.902 s, n=3, sd 0.390) | **77.283 s** | **3.799 (63.3 %)** |
| → PG 자기 플랜의 대가 | **1.505x** | 1.115x | — |

**(b) CUBRID에 PG 형상 강제 — 조인 방법은 일치, 조인 순서는 불일치**

`/*+ USE_HASH */` → `hash-join` 3단 + `sscan orders` / `sscan customer` / `sscan lineitem`
(PG 정본과 같은 "전체 스캔 + 해시조인" 계열). 단 **조인 순서가 다르다** —
CUBRID는 `orders ⋈ av1861 → ⋈ customer → ⋈ lineitem`, PG는 `lineitem ⋈ av → ⋈ orders → ⋈ customer`.
Q8에서 `join_collapse_limit=1`이 outer/inner를 뒤집은 것과 같은 종류의 한계이며, **이 값은
형상 일치가 아니라 "조인 방법 계열 일치"로만 인용한다.**

| | wall | 질의실행분 CPU | 이용률 |
|---|---|---|---|
| CUBRID 정본 | 38.181 s | 94.133 s | 2.465 (41.1 %) |
| CUBRID PG형상(USE_HASH) | **47.090 s** (n=2; 별 세트 46.774 s, n=3, sd 0.264) | 140.870 s | 2.991 (49.9 %) |
| → CUBRID 자기 플랜의 이득 | **1.233x** | 1.497x | — |

**두 방향이 같은 것을 말한다: 두 옵티마이저 다 자기 선택이 자기에게 옳다.** 다만 PG의 선택이
**1.505x**만큼 나쁘고 CUBRID의 선택은 1.233x만큼 좋다 — 그 비대칭이 배수를 1.21x로 눌러준다.

### 4.1 CUBRID 직렬 구간의 원인 — 코드 상수다

```
xasl_generation.c:16556-16563   sum() GROUP BY이고 NO_HASH_AGGREGATE 힌트가 없으면
                                buildlist->g_hash_eligible = true
        ↓

external_sort.c:5232              if (px == NULL || px->hash_eligible)  return 1;   ← 직렬 확정
                                  ...
external_sort.c:5237-5239         parallel_num = compute_parallel_degree (SORT, input_list->page_cnt, hint)
```

**즉 GROUP BY의 외부 정렬은 "해시 집계가 가능한 쿼리"에서 항상 직렬이다.**
`input_list->page_cnt` = 423,552 페이지로 문턱 2048을 **207배** 넘지만 그 계산에 도달하지 못한다.
`parallelism=6`도 `/*+ PARALLEL(6) */`도 이 조항을 넘지 못한다 — Q8의
`parallel_scan_page_threshold`(px_parallel.cpp:118-122)와 같은 종류의 **선반환 게이트**다.

**기제 확증 A/B — `/*+ NO_HASH_AGGREGATE */`로 조항을 끄면 정렬이 실제로 병렬로 켜진다**

| 변형 | wall | SCAN | GROUPBY | GROUPBY 병렬 |
|---|---|---|---|---|
| 정본 (hash_eligible=true) | 42.97 s (trace on) | 12,112 ms (6워커) | **30,801 ms** | **없음(직렬)** |
| 집계 단독 정본 | 43.10 s (trace on) | 12,125 ms (6워커) | 30,968 ms | 없음(직렬) |
| 집계 단독 `NO_HASH_AGGREGATE` | **53.07 s** (trace on) | **5,740 ms** (6워커) | **47,218 ms** | **`(parallel workers: 6, time: 2480..3083, page: 149118..196330)`** |

조항은 확증됐으나 **끄면 더 느려진다** — 워커가 partial hash agg를 하지 않으므로 정렬 입력이
15 M 부분집계 엔트리 → **60 M 원행**으로 4배가 되고, 병렬 구간은 2.5~3.1 s뿐이며 나머지 ~44 s는
여전히 직렬이다. 그 직렬 잔여의 근거도 코드에 있다:

| 소스 | 내용 |
|---|---|
| `external_sort.c:5829` | GROUP_BY 병렬 종료 시 **Phase 2 = `sort_merge_worker_runs_to_one`** — 워커 런을 하나로 접는 **직렬 fan-in** |
| `external_sort.c:5841-5848` | 그 뒤 `sort_run_final_single` — **직렬 최종 런** |
| `external_sort.c:5720-5723` | 같은 이유의 선례 주석: "put_fn must not run in parallel because ordbynum_val state is shared" |

**따라서 진짜 항목은 "GROUP BY 정렬의 병렬화 허용"이 아니라 "GROUP BY 병합·최종화의 병렬화"다.**
그룹 키 범위로 파티셔닝해 워커가 서로 겹치지 않는 키 구간을 각자 병합·최종화하면 되지만,
`qexec_gby_put_next`가 그룹 상태(`gbstate`)를 공유하므로 설계 변경이 필요하다.

**보조 상수 — 해시 집계 메모리 상한**

| 소스 | 값 |
|---|---|
| `base/system_parameter.c:3472-3483` | `max_agg_hash_size` 기본 **2 MB**, **최대 128 MB**, `PRM_FOR_SERVER \| PRM_TEST_CHANGE` |

15 M 그룹 × (키 + NUMERIC 합계 + hentry) ≈ 600 MB 이상이므로 **128 MB 상한으로는 구조적으로 불가능**하다.
그래서 `hash: partial`이 되고 나머지가 정렬로 흘러간다. `PRM_TEST_CHANGE`라 런타임 변경이
거부된다(`ERROR: Cannot change system parameter "max_agg_hash_size=128M"` 실측).
PG 대조: `work_mem` 4 MB × `hash_mem_multiplier` 2 = 8 MB로 **CUBRID보다도 작지만**,
스필을 16 파티션으로 갈라 **워커별로 병렬 처리**한다.

**`sort_buffer_size` 민감도 (세션 `SET SYSTEM PARAMETERS`, 집계 단독)**

| `sort_buffer_size` | wall | GROUPBY time | sort page |
|---|---|---|---|
| 2 M (기본) | 42.182 s | 30,302 ms | 423,495 |
| 16 M | 41.460 s | 29,073 ms | 279,016 |
| 64 M | **40.415 s (−4.2 %)** | 28,380 ms | **213,521 (−49.6 %)** |

**32배를 줘도 4.2 %뿐이다** — 스필량은 반으로 줄지만 병목은 스필이 아니라 **직렬 병합 자체**다.
버퍼 크기는 이 쿼리의 레버가 아니다.

### 4.2 CUBRID 워커의 TLS 비용 — 새 항목

```
px_scan_result_handler.hpp:80    thread_local static tls tl;                  (result_handler 멤버)
px_scan_result_handler.cpp:49    thread_local typename result_handler<result_type>::tls result_handler<result_type>::tl;
px_scan_result_handler.cpp:787-925  result_handler<MERGEABLE_LIST>::write ()  ← 튜플마다 tl.* 15회 이상
```

`tls`는 `std::vector<DB_VALUE>`를 품어 **비자명 생성자**를 가지므로, 공유 라이브러리
(`libcubrid.so`)의 `thread_local` 접근은 매번 `__tls_get_addr` + TLS-init 가드를 탄다.
프로파일에 실제로 `TLS init function for parallel_scan::result_handler<(RESULT_TYPE)1>::tl@plt`가
심볼로 잡힌다. `write()` 안의 `tl.` 참조는 787(`prefetch`), 789, 793, 794, 796, 798, 800, 808,
812, 816, 827, 829, 831-832, 839-840, 846, 850-853, 867, 886, 917, 924 — **60 M 튜플 × 15+회**다.

측정값: 워커 instructions **22.62 G(7.6 %)** / cycles **9.02 G(5.2 %)**,
전체 대비 instructions 4.9 % / cycles 3.6 %.
**같은 파일 939-940행에 이미 해법 패턴이 있다** — `parallel_scan::list_id_header *tl_list_id_header = tl.list_id_header_p;`
처럼 함수 진입 시 지역 참조로 한 번만 받으면 된다.

## 5. 남은 것 / 한계

* **CUBRID PG형상 강제(§2.4b)는 조인 순서가 불일치한다.** `/*+ USE_HASH */`는 조인 방법만 고정하고
  순서는 옵티마이저가 정한다. `LEADING` 힌트로 순서까지 맞추려면 파생 테이블 `av1861`을 명시
  이름으로 재작성해야 하므로 질의 재작성 범위가 커진다 — 미수행. 그래서 §2.5의 정본 3축 분해는
  **형상 일치가 확인된 방향(PG측 A/B)**으로 세웠다.
* **PG stream 레짐의 hit/read 분할은 근사다.** G2 스트림 22쿼리 상태가 아니라 q1 1개로 축출한
  상태이며, G2 라운드의 q18 플랜은 `EXPLAIN`(ANALYZE 아님)이라 원본 분할값이 없다.
  다만 총 버퍼 접근량이 2,552,611로 완전 동일하고 시간 변화가 +0.68 %라 판정(무감)은 견고하다.
* **후보 A의 상한은 선형 스케일 가정이다.** 직렬 병합은 비교·버퍼 접근 혼합이라 6단위에서
  선형이 아닐 수 있다. 3단위 시나리오를 보수값으로 같이 적었다.
* **`agg` 세트의 C3 런(43.011 s)은 배경 부하 스파이크 구간이다**(loadavg 22.71, procs_running 47).
  평균에서 제외하고 C1·C2만 썼다. 원값은 `q18/raw/s2/wall.tsv`에 남긴다.
* **미측정**: Q5·Q11 이용률(ADR 0018 §2가 남긴 것). Q18이 "양쪽 단위 붕괴"를 처음 확인했으므로
  그 두 쿼리도 **PG 이용률까지** 재야 한다.
