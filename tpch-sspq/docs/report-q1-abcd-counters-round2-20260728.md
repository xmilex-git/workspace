# Q1 DOP6 A~D 카운터 — 확정판 (새 표 형식 기준선 겸용)

2026-07-28. 원인·병목 후보 지목 없음(ADR 0005). worker 합산 CPU를 wall time에서
감산하거나 직접 비교하지 않았다. 표는 ADR 0009 + ADR 0011 형식(SUT CPU / broker+CAS /
파싱·플랜 열 분리, 합산 단일 숫자 없음). ADR 0013에 따라 이 라운드가 **새 표 형식의
기준선 레코드**를 겸한다.

## 결론 (5줄)

1. **CPU 작업량 비 3.035x vs wall 비 3.555x** — 두 축이 다르다(CUBRID SUT CPU
   188.673 s / PG 62.163 s).
2. **instructions 비 3.02x, IPC는 사실상 동일**(SUT 부착 2.457 vs 2.523). 명령 수
   자체가 3배다.
3. **(A) 게이트 통과** — 클라이언트측 CPU가 SUT CPU의 **0.045 %(CUBRID) /
   0.113 %(PG)** 로 1 % 미만이므로 지시대로 (B)를 `perf stat -a -C 0-15`로 측정했다.
4. **오염률은 카운터별로 전혀 다르다** — instructions 2.6 %/4.1 %, cycles 7.3 %/10.5 %,
   branch-misses 11.7 %/11.2 %, 그러나 **LLC-load-misses 44.8 %/93.9 %**.
5. **바이트 1.214x는 전부 컬럼 저장 표현**(CHAR +21.91 B/행, DECIMAL +12.53,
   VARCHAR +7.89, DATE +1.50, INTEGER ±0); 행 구조 오버헤드는 CUBRID가 10.96 B 작다.

## 측정 조건

Q1, DOP 6. WARM 레짐(세트 전 warmup 1회 미집계 + 엔진 전환 직후 재수행). 양쪽 서버
node0 `0-15` 핀, **클라이언트도 `0-15`(ADR 0012 공유 정책)**, 수집기 `20-23`(SUT 밖).
300 s timeout, 초과 0건. 집계 런 physical read(`/proc/diskstats` sda) 전부 **0.0 MiB**,
무효 런 0건.

A·C·D는 직전 라운드에서 지시된 방법 그대로 측정된 값을 쓴다(재실행으로 서버에 부하를
더하지 않기 위해). B는 (A) 게이트 결과에 따라 **이 라운드에서 새로 측정**했다.

## A. 쿼리 구간 총 CPU 초 vs wall 초

구간은 **클라이언트 세션 안에서** 브래킷했다(CUBRID `;SHELL_Cmd`/`;SHELL`, PG `\!`) —
클라이언트 기동이 아닌 질의 구간이다. `/proc/<pid>/stat` utime+stime 델타 방식.

정확성 근거: `cub_server`는 단일 프로세스이고 해당 필드가 **전 스레드 합산**이라 워커
스레드가 구간 안에서 생성·소멸해도 누락되지 않는다(스레드 분해 잔차 평균 **0.007 s**).
PG 리더는 세션 유지로 프로세스가 살아 있고, 병렬 워커는 postmaster가 reap하므로
`cutime/cstime` 델타가 정확하다.

| 지표 | CUBRID | PostgreSQL | CUBRID/PG |
|---|---|---|---|
| **wall (질의 구간)** | 31.846 s (within-set sd 0.622) | 8.957 s (sd 0.004) | **3.555x** |
| **SUT CPU 합계** | **188.673 s** (sd 1.371) | **62.163 s** (sd 0.025) | **3.035x** |
| ├ user | 184.560 s | 61.963 s | 2.978x |
| └ sys | 4.113 s | 0.200 s | 20.6x |
| **SUT CPU / wall** (평균 병렬 활용도) | **5.926** | **6.940** | — |
| ├ **leader** | **0.470 s** (`transaction` 스레드) | **8.870 s** (sd 0.000) | — |
| └ **worker 합** | **188.0 s** (`parallel-query` × 6) | **53.293 s** (sd 0.025) | — |
| 참여 실행 단위 수 | 6 (워커만) | 7 (리더 + 워커 6) | — |
| 단위당 CPU | 31.4 s | 8.88 s | 3.54x |

| | CUBRID | PostgreSQL |
|---|---|---|

## B. perf stat — 방법은 (A) 게이트가 정했다

### 게이트 계산

| 엔진 | 클라이언트측 CPU | SUT CPU | 비율 | 판정 |
|---|---|---|---|---|
| CUBRID | 0.084 s | 188.673 s | **0.045 %** | < 1 % → `-a -C` 실행 |
| PostgreSQL | 0.070 s | 62.163 s | **0.113 %** | < 1 % → `-a -C` 실행 |

### 선행 검증: `perf -a -C`가 정확한가 (직전 라운드의 내 오류 정정)

직전 라운드에서 "시스템 와이드는 신뢰 불가"라고 적었는데 **그 판단은 틀렸다.**
통제 워크로드로 확인했다.

| 검증 | 결과 |
|---|---|
| 코어 14 고정 busy 루프, per-process vs `-a -C 14` | instructions **14,030,607,865 vs 14,013,490,579** = **0.12 % 일치** |
| 같은 10 s 창, `-a -C 0-15` cycles → CPU-초 환산 vs `/proc/stat` 실측 | **22.94 vs 21.63 CPU-s** = 6 % 내 일치 |
| 코어 0-15 실제 사용률(`/proc/stat`, 10 s) | 평균 **11.6 %** (cpu2만 100 %, 나머지 3.5~9.1 %) |
| 앞서 본 "idle 9 s에 469 G instructions" | perf 결함이 아니라 **그 순간 배경 부하가 실제로 무거웠던 것**. 배경 부하 실측 범위 **1.9 ~ 52 G instructions/s** 로 변동이 크다 |

### B 표 — 지시대로 `perf stat -a -C 0-15` 값 (2회 평균)

동시에 SUT 부착 세션(`-p cub_server` / `-p postmaster`)을 붙여 오염률을 **측정**했다.
PG의 postmaster 부착은 리더 backend와 병렬 워커가 모두 부착 후 fork되는 자식이라
perf 기본 `inherit=1`로 포착되며, task-clock 62.54 s가 A의 /proc 62.163 s와 0.6 % 일치해
부착 집합이 SUT 경계와 같음이 확인된다.

| 카운터 | CUBRID (`-a -C 0-15`) | PostgreSQL (`-a -C 0-15`) | CUBRID/PG |
|---|---|---|---|
| cycles | 561,517,591,382 | 188,284,371,854 | 2.982x |
| **instructions** | **1,313,341,333,435** | **443,699,628,476** | **2.960x** |
| **IPC** | **2.339** | **2.357** | 0.992x |
| LLC-load-misses | 144,487,790 | 100,038,800 | 1.445x |
| branch-misses | 989,568,204 | 338,860,759 | 2.920x |
| task-clock | 509,769 ms | 143,127 ms | (구조상 wall × 16) |
| 질의 wall | 31.860 s | 8.945 s | 3.562x |

**각주 — 오염률 (SUT 밖 활동이 위 값에서 차지하는 비율, 동시 측정으로 실측)**

| 카운터 | CUBRID 오염률 | PostgreSQL 오염률 | 동시 SUT 부착값 (CUBRID / PG) |
|---|---|---|---|
| instructions | **2.6 %** | **4.1 %** | 1,278,870,326,058 / 425,447,800,136 |
| cycles | 7.3 % | 10.5 % | 520,437,684,530 / 168,606,419,528 |
| branch-misses | 11.7 % | 11.2 % | 874,105,110 / 300,978,114 |
| **LLC-load-misses** | **44.8 %** | **93.9 %** | 79,791,766 / **6,071,644** |

**해석상 경계 (사실만)**: instructions·cycles·branch-misses는 오염률 2.6~11.7 %로
시스템 와이드 값이 SUT 값의 대용으로 쓸 만하다. **LLC-load-misses는 그렇지 않다** —
PG 쪽 오염률 93.9 %는 시스템 와이드 값의 대부분이 SUT 밖 활동이라는 뜻이다. 캐시
이벤트는 SUT 부착값(CUBRID 79.79 M / PG 6.07 M)을 쓴다. 이로써 직전 라운드에서
"미해결"로 남긴 PG 캐시 이벤트 15배 불일치도 설명된다 — 넓은 부착·시스템 와이드가
배경을 함께 센 것이고, 좁은 부착값은 5회에 걸쳐 5.07 / 5.25 / 5.63 / 6.33 / 5.82 M로
안정적이다.

**추가 각주**: 이 라운드의 SUT 부착 세션은 5개 이벤트가 4개 프로그래머블 카운터를 넘어
perf가 이벤트 스케일링(≈25 %)을 표시했다. 스케일 보정된 값은 직전 라운드의
비-멀티플렉싱 6이벤트 측정과 0.5 % 내에서 일치한다(instructions 1,278.9 G vs
1,285.4 G, PG 425.4 G vs 425.5 G).

### D-3 행당 바이트 항목별 — 양쪽 실측

`CUBRID_DATABASES` 경로에 스크래치 DB를 만들어 컬럼군별 변형 테이블 5개(각 500,000행)의
힙 페이지 수를 재고 기준 테이블 대비 한계 비용을 구했다(측정 후 삭제,
