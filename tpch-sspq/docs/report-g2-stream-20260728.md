2026-07-28. 단위 파리티 트랙만(CUBRID `parallelism=6` ↔ PG
`max_parallel_workers_per_gather=5`+leader = 양쪽 6 실행 단위). 자연 구성 트랙은 재지
않았다. 프로파일러 미부착 — wall time과 플랜만.

> **PG 각주 (ADR 0015 의무)**: PostgreSQL 수치는 `dynamic_shared_memory_type=mmap`
> 구성이다(기본값 `posix` 이탈). 전환 비용 실측: PG가 **1.40 % 빨라졌고**, 같은
> 세션쌍에서 무변경 CUBRID 대조군이 −0.72 % 드리프트했으므로 mmap 귀속분은 최대
> 약 0.7 %p, 배수 영향은 3.049x → 3.070x. **표에 posix/mmap을 구분 표기했다.**

## 결론 (5줄)

1. **Q1은 대표가 아니다.** 격차의 **43.5 %가 Q21 단독**(12.72x)이고 Q1은 15.3 %(2.87x)로
   2위다. 배수 분포의 중앙값은 2.15x이고 Q1은 19개 중 3위 — 전형이 아니라 상위권이다.
2. **CUBRID가 이기는 쿼리가 있다 — Q2(0.10x, 0.302 s vs 3.023 s).** 숨기지 않고 signed
   기여율 −2.00 %로 그대로 낸다.
3. **PG-only Parallel subset은 존재하지 않는다.** 완주 19개 전부 CUBRID가 병렬을 탄다.
   유일한 비대칭은 **반대 방향** — **Q13은 CUBRID 6단위 / PG 완전 직렬**(1.03x).
4. ~~**CUBRID의 실행 단위는 쿼리마다 붕괴한다.**~~ 단일 테이블 쿼리는 노드 1개 × 6워커지만,
   다중 조인 쿼리는 노드 대부분이 **2워커**다 — Q21은 `4x2 1x3 1x6`, Q5·Q8·Q11도 동일 양상.
   ~~목표 6단위가 실제로 유지되는 것은 단일 스캔 쿼리뿐이다.~~

   > **정정 (2026-07-29, ADR 0018)** — 워커 분포는 **플랜 채증으로 유효하고 성능 해석으로는
   > 무효**다. Q21을 CPU까지 재 보니 CUBRID `parallel-query` 스레드 6개가 각 57.7~63.4 s를
   > 태우고(SUT CPU 370.387 s) **`CPU/wall` = 5.818 = 6단위의 96.97 %**이며, 2/3워커 노드의
   > 자기 시간 합은 **675 ms = 0.83 %**다. wall 배수 14.319x가 SUT CPU 배수 14.291x와
   > **0.2 % 차**로 일치하므로 실행 단위 축은 격차를 만들지 않는다. `N×2`는
   > `parallel_type::SUBQUERY`의 **코드 상수 1**(`src/query/parallel/px_parallel.cpp:85-109`,
   > 주석 `TODO: degree fixed at 1`)이고 데이터 크기·`parallelism`·힌트와 무관하다 —
   > "쿼리마다 붕괴"는 데이터 의존을 함의하므로 부정확하다. **Q5·Q8·Q11은 이용률을 재지
   > 않았으므로 붕괴 라벨을 붙이지 않는다.** 상세: `docs/report-q21-gap-20260729.md` §2.3.
5. **timeout 3개**: Q17·Q20은 **양쪽 다** 300 s 초과, Q22는 **CUBRID만**(PG 0.971 s,

### 강제된 이탈 — "한 세션 스트림"이 CUBRID에서 성립하지 않는다

지시는 단일 세션 순차 스트림이었다. **CUBRID에서는 불가능하다는 것이 측정으로 확정됐다.**

* CUBRID에 쿼리 단위 timeout 기제가 **없다** — `query_timeout` 파라미터 부재,
  `lock_timeout`은 락 대기 전용, broker `QUERY_TIMEOUT`은 정본 경로(`csql -C` 직결)에
  broker가 없어 무효 (CONTEXT.md에 비대칭으로 등재).
* 따라서 단일 세션 CUBRID 스트림은 **무경계**다. **Q22를 `timeout 1500`으로 단독
  프로브했으나 1500 s에도 완주하지 못했다**(PG 0.971 s). 스트림에 그런 쿼리가 3개 있으면
  5개 CUBRID 스트림의 상한이 없다.
* 그래서 300 s 규칙을 실제로 집행하기 위해 **쿼리별 클라이언트 호출 + 외부
  `timeout 300`** 을 쓴다. 대칭을 위해 PG도 같은 형태로 돌리되, PG는 추가로
  세션 GUC `statement_timeout='300s'`로 **엔진 측 취소**까지 받는다.
* **포기한 것은 단일 커넥션 속성 하나**이고, 스트림 순서와 warm 상태는 유지된다.
  클라이언트 기동 비용은 10~20 ms 대 질의 1~300 s다.

### 게이트 답 — PG-only Parallel subset은 **비어 있다**

* **PG는 병렬, CUBRID는 직렬**인 쿼리: **없다.** 완주 19개 전부 CUBRID가 병렬을 탄다.
* **CUBRID는 병렬, PG는 직렬**인 쿼리: **Q13 하나.** PG `Workers Planned: 0`,
  플랜은 `Sort → HashAggregate → Hash Right Join → Seq Scan` 전부 직렬.
  그런데 격차는 1.03x로 사실상 동률 — CUBRID가 6단위를 써서 PG의 1단위와 겨우 비겼다.
* **계획 ≠ 실제**: PG Q22만 `Planned 5 / Launched 4`. 나머지는 일치.
* ~~**CUBRID의 목표 6단위는 단일 스캔 쿼리에서만 유지된다.**~~ 노드 1개짜리 쿼리
  (Q1,Q3,Q4,Q6,Q12,Q14,Q18,Q19)는 `1×6`이지만, 다중 조인 쿼리는 노드 대부분이 2워커다
  (Q5 `4×2`, Q8 `4×2`, Q11 `4×2`, Q21 `4×2`). **PG는 모든 병렬 노드가 동일하게
  leader+5로 돈다.** → **정정 (ADR 0018)**: 노드 개수 서술은 유효하나 Q21 실측 이용률은
  6단위의 **96.97 %**다. 판정 라벨은 `CPU/wall ÷ 목표 단위 수`로 붙이고 80 % 미만일 때만
  `단위 붕괴`를 쓴다.

| 플랜 형상 | 단일 테이블 스캔 + hash groupby | — | **22개 중 가장 단순한 형상** |
| CUBRID 실행 단위 | `1×6` (붕괴 없음) | 다중 조인 쿼리는 `4×2` 등 | **붕괴가 없는 소수 케이스** |

**근거에 기반한 결론**: Q1은 **배수 밴드로는 대표성이 있으나(2~3x 밴드에 19개 중 10개가
들어가고 Q1은 그 상단), 격차 지배 요인으로는 대표가 아니다.**

* Pareto 1위 **Q21은 형상이 완전히 다르다** — PG는 `Nested Loop Anti Join` +
  `lineitem_pkey` **인덱스 스캔 2개**로 상관 서브쿼리를 처리하는데, CUBRID는
  `HASH JOIN ×2 + NESTED LOOPS`에 **노드 대부분이 2워커**다. Q1의 "단일 스캔 6워커"와
  같은 범주가 아니다. → **후속 규명 완료**: 그 차이의 실체는 워커 수가 아니라
  **조인 순서**였다(`docs/report-q21-gap-20260729.md`: 14.319x = 플랜 4.436x × 행당 3.228x,
  실행 단위 기여 0.2 %).
* 따라서 **5·6단계에서 Q1으로 규명한 결론(식 평가/값 도메인 변환/집계 누산의 행당
  인터프리테이션 비용)은 Q1형 = 단일 스캔 집계 쿼리에 대해 확립된 것**이고,
  Pareto 1위 Q21로 자동 일반화되지 않는다. Q21은 **실행 단위 붕괴와 조인 전략 차이**라는
  별개 축을 갖는다 — 이는 이번 측정의 플랜 채증에서 나온 사실이며, 원인 규명은
  아직 하지 않았다.
