# Q15 격차 규명 — 필터 지배형 + 양쪽 실행 단위 붕괴

2026-07-29. 단위 파리티 트랙(CUBRID `parallelism=6` ↔ PG `max_parallel_workers_per_gather=5`+leader = 양쪽 6 실행 단위).
하위 레짐 **single-query-repeat** (ADR 0016) — G2 stream 값과 같은 표에 합치지 않는다.

> **배수 인용 단서 (의무)**: Q15 PG 수치는 **`InitPlan` gather가 워커 3개만 띄운 상태**를 포함한다
> (클러스터 상한 `max_parallel_workers=8`, 기본값 유지). 사용자 방침에 따라 상한을 올린 보조 통제 런은
> 하지 않았고, 이 손실은 **실행 단위 축 1.2620x로 분해해 별도 기록**했다(Q8에서 실행 단위 0.9314x를
> 분리한 것과 같은 방식).

> **PG 각주 (ADR 0015 의무)**: `dynamic_shared_memory_type=mmap` 구성이다.

## 결론 5줄

1. **격차가 곱으로 정확히 갈렸다: `2.1650x = 플랜 1.0000x × 실행 단위 1.2620x × 행당 실행 비용 1.7155x`**,
   검산 오차 **0.00 %**. 플랜 축이 **네이티브로 1**인 첫 쿼리다 — 강제할 형상 차가 없다.
2. **Q15는 기존 다섯 분류에 들어가지 않는다 — 새 범주 `필터 지배형`이다.** cycles 격차의 **47.7 %가 술어
   평가**(22.02x)이고, Q1형의 3버킷은 죽는다(식 평가 **1.00x 동률**, 수치 **0.62x로 CUBRID가 적다**).
   **스캔·레코드 디코드는 0.97x 완전 동률**이다.
3. **양쪽이 동시에 `단위 붕괴`다 — Q18에 이어 두 번째.** CUBRID 이용률 **59.3 %**(wall의 **50.1 %가
   leader 단독 GROUP BY**), PG **74.8 %**(손실 전량이 `InitPlan` 3워커). 실행 단위 축이 격차 5.773 s의
   **38.6 %(2.227 s)**를 쥔다.
4. **CUBRID 직렬화의 뿌리는 Q18과 같은 한 줄이다** — `external_sort.c:5232`의 `hash_eligible` 선반환.
   같은 line이 **두 쿼리에서 지배축**이 됐다. 뷰가 2회 평가되므로 직렬 구간도 2회 온다.
5. **뷰 2회 평가는 양쪽 공통 구조 문제다** — 단일 평가(CTE 실체화)로 CUBRID −49.2 % / PG −54.2 %,
   **배수는 2.165x → 2.400x로 악화**한다. 개선 후보 5개 제시, 기존 후보 8개 중 **5개를 채증으로 배제**,
   **구현 없음.**

## 0단계 — 뷰 정의 문제 (측정 단위 확정)

Q15는 세 문장(`create view revenue0` / `select` / `drop view`)이 하나의 논리 쿼리다. G2 하네스 원본
(`.git_ignored_dir/g2-stream/scratch/run-g2.sh`)을 확인했다.

```
if [ "$i" = 15 ]; then
  cat "$Q/q15_create_view-cubrid.sql" "$Q/q15_select-cubrid.sql" "$Q/q15_drop_view-cubrid.sql" > "$f.sql"
```

**G2는 세 문장 전체를 한 클라이언트 호출로 쟀다 → 정의 A가 정본이고 헤드라인은 A를 쓴다.**
두 정의를 같은 런에서 문장 단위로 함께 냈다.

| 정의 | CUBRID | PG | 배수 |
|---|---|---|---|
| **A — 3문장 호출 end-to-end (G2 정본, 헤드라인)** | **10.781 s** (sd 0.049) | **4.948 s** (sd 0.044) | **2.1788x** |
| B — `select` 문장만 | 10.750 s (sd 0.049) | 4.933 s (sd 0.043) | 2.1790x |
| `create view` | 0.0013 s | 0.0030 s | — |
| `drop view` | 0.0027 s | 0.0010 s | — |
| **DDL 합** | **0.0040 s** | **0.0040 s** | **격차 기여 0.0000 s (0.00 %)** |

**두 정의는 구별되지 않는다(차 0.01 %).** 뷰 생성 비용은 격차에 **기여하지 않는다** — 양쪽 정확히 4 ms다.
이후 축 분해·프로파일은 정의 B(`select`)를 대상으로 하고, 정의 A는 DDL 4 ms를 더한 값이다.
`revenue0` 잔존은 모든 라운드에서 양쪽 **0**(계약 확인, cleanup 불필요).

같은 엔진 A/B의 대상이 없다(§2.4에서 대칭 변형 A/B를 따로 냈다).

### PG `InitPlan` 3워커 (결정적)

`EXPLAIN ANALYZE` 5회 반복 전부 `Workers Launched: [3 5]`. 원인은 §4에서 소스로 확정했다 —
외곽 `Gather Merge`가 워커 5개를 쥔 채 `InitPlan`이 트리거되어 클러스터 상한 8−5=3만 뜬다.
**G2 분류표의 `Planned 5 / Launched 5`는 두 gather 중 하나만 본 값이다.**

### 채증 함정 등재 — CUBRID trace의 `rows`

병렬 힙 스캔의 `rows`(qualified_rows)가 `readrows`와 **항상 같게** 찍힌다
(`scan_manager.c:8690`, `px_scan_trace_handler.cpp:300`; 카운터 증가 위치가
`px_scan_slot_iterator.cpp:119`/`:125`로 술어 평가 결과와 무관). Q15의 `rows: 59986052`는
**sarg 미적용이 아니다** — 통제 프로베(`select count(*) ... where l_shipdate …` = 2,265,714,
스캔 노드도 `rows: 59986052`)로 확정했다. **이 카운터로 선택도를 읽지 않는다.**

### 2.4 같은 엔진 A/B — 양쪽 단일 평가 강제 (두 번째 형상 일치 쌍)

`create view` → `WITH … AS MATERIALIZED`(PG) / `WITH …`(CUBRID).
CUBRID 실체화 확인: trace `CTE (non_recursive_part)` 아래 lineitem 스캔 **1회**, `fetch 694,110`.

|---|---|---|---|

| 이용률 | **3.542 = 59.0 %** (정본 59.3 % → **불변**) | **5.202 = 86.7 %** (정본 74.8 % → **복귀**) | 단위 축 **1.4687x** |
| 검산 | 1.6340 × 1.4687 = **2.3998** ↔ 실측 2.3998 | | **0.00 %** |

- 행당 비용 축은 두 형상에서 **1.7155x ↔ 1.6340x**로 일관.

## 3단계 — 대칭 프로파일링

### 4.5 PG `InitPlan` 3워커 — 코드 근거

```c
/* ~/dev/postgres/src/backend/postmaster/bgworker.c:1103-1113 */
if (parallel && (BackgroundWorkerData->parallel_register_count -
                 BackgroundWorkerData->parallel_terminate_count) >=
    max_parallel_workers)
```

외곽 `Gather Merge`가 워커 5개를 등록·미종료 상태로 쥔 채 `Finalize GroupAggregate`의 필터가
