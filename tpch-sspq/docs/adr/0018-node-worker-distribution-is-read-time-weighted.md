# 노드별 워커 분포는 시간 가중으로 읽는다 — 개수만 세는 라벨을 쓰지 않는다

G2는 "**CUBRID의 실행 단위는 쿼리마다 붕괴한다** — 다중 조인 쿼리는 노드 대부분이 2워커다
(Q21 `4×2 1×3 1×6`)"를 결론 4번으로 냈다. **노드 개수를 센 그 서술은 오도한다.** Q21 축
분리에서 측정으로 확정됐다.

## 측정 사실

| 채증 | 값 |
|---|---|
| `parallel-query` 스레드별 CPU (3런, 각 6개) | 62.09 / 62.00 / 61.34 / 60.93 / 60.65 / 57.73 s — **전 구간 가동** |
| SUT CPU | **370.387 s** (6 × 61.61 s 평균) |
| leader(`transaction`) 스레드 CPU | **0.92 s = SUT의 0.25 %** |
| **CPU/wall (이용률)** | **5.818 = 6단위의 96.97 %** |
| PG 대비 이용률 | PG 5.830 → 비 **1.002x** |
| wall 배수 vs SUT CPU 배수 | 14.319x vs 14.291x → **0.2 % 차** |
| **2/3워커 노드의 자기 시간 합** | **675 ms / 81,286 ms = 0.83 %** |
| degree-6 노드(`SCAN (table: dba.orders)` + 하위 서브트리)의 시간 | 80,575 ms = **99.1 %** |

즉 `4×2 1×3 1×6`은 **플랜 채증으로서 사실이지만, 일을 하는 노드는 `1×6` 하나**다.
CUBRID는 Q21에서 6 실행 단위를 96.97 % 이용률로 유지했다. **실행 단위 붕괴는 Q21 격차
14.32x에 0.2 %도 기여하지 않는다.**

## 무엇이 2로 깎는지 (소스)

`src/query/parallel/px_parallel.cpp:37 compute_parallel_degree (type, num_pages, hint_degree)`
가 모든 병렬 결정의 유일한 창구이고, 타입별 규칙이 다르다.

| 타입 | 규칙 | Q21 |
|---|---|---|
| `SCAN` | `num_pages < threshold`(기본 **2048**)면 직렬, 아니면 `floor(log2(num_pages/threshold)) + 2`, 최종 `MIN(·, parallelism)` (`:139-172`) | orders **151,689 페이지** → `74` → `6+2=8` → `MIN(8,6)` = **6** ✅ |
| `HASH_JOIN` | 같은 공식 + `MIN(degree, context_cnt)` (`query_hash_join.c:2005`, `:2114`) | 중간 리스트 파일이 작아 **2 / 3** |
| **`SUBQUERY`** | **`auto_degree = 1` 하드코드.** `num_pages`를 받지 않고(`assert (num_pages == 0)`), `hint_degree >= 2`면 **힌트를 무시하고 1을 반환** (`:85-109`) | **항상 2**(main + gather) |
| `SORT` | 같은 공식 (`external_sort.c:5143`, `:5201`, `:5238`) | 정렬 페이지 262~301 → 직렬 |

호출측이 상수를 다시 굳힌다 — `src/query/query_executor.c:16049-16071`,
`assert (n_workers_to_reserve == 1)` + 주석 `TODO: Temporarily limited to 2.`
그 경로를 만든 커밋은 `978b628c8 [CBRD-26931] Parallelize uncorrelated scalar subquery
inner scan (#7316)`(pin 포함)이다.

**그러므로 `N×2`는 데이터 크기·`parallelism` 파라미터·힌트와 무관한 코드 상수다.**
"쿼리마다 붕괴한다"는 표현은 데이터 의존 현상을 함의하므로 부정확하다.

## Decision

### 1. 분류표의 워커 분포는 **시간 가중 없이 인용하지 않는다**

G2가 미결로 남긴 "플랜 일부만 병렬인 경우의 라벨" 항목을 이렇게 닫는다.

* 노드별 워커 분포(`4×2 1×3 1×6`)는 **플랜 채증으로만** 표에 남긴다.
* **판정 라벨은 이용률로 붙인다** — `CPU/wall ÷ 목표 실행 단위 수`.
  Q21 CUBRID = 5.818/6 = **96.97 %** → 라벨 `병렬 유지`.
* 이용률이 목표 단위 수의 **80 % 미만**일 때만 라벨 `단위 붕괴`를 쓴다. 그 경우 어느 노드가
  붕괴 시간을 쥐는지 **자기 시간 비중과 함께** 적는다.
* `Workers Launched < 목표 DOP`(PG Q22의 `Planned 5 / Launched 4` 같은 경우)도 같은 규칙을
  적용한다 — 개수 불일치 자체가 아니라 이용률이 판정한다.

### 2. G2 결론 4번을 정정한다 (폐기하지 않는다)

G2 보고서와 README의 "CUBRID의 6단위는 단일 스캔 쿼리에서만 유지된다 / 다중 조인 쿼리는
노드 대부분이 2워커다"는 **플랜 형상 서술로는 유효하고, 성능 해석으로는 무효**다.
정정 문구를 두 문서에 넣되 원문을 지우지 않는다(ADR 0010의 이력 보존 규칙).

Q5·Q8·Q11도 같은 `N×2` 양상을 보였으나 **이용률을 재지 않았다.** 그 쿼리들에 대해
"단위 붕괴"라고 말하려면 CPU/wall을 먼저 재야 한다. 재기 전에는 라벨을 붙이지 않는다.

**Q9 실측 추가 (2026-07-29)** — G2가 `1×2 2×5 2×6`으로 분류한 Q9의 이용률을 재서 **라벨을
부여한다: `병렬 유지`**.

| 채증 | CUBRID Q9 | PG Q9 |
|---|---|---|
| SUT CPU (런당) | 123.18 s | 45.037 s |
| wall (같은 브래킷) | 19.533 s | 7.785 s |
| **CPU/wall** | **6.306 (6단위의 105.1 %)** | **5.785 (96.4 %)** |
| ↳ `parallel-query` 워커 | 109.34 s = 5.507단위 (SUT의 87.6 %) | 37.680 s |
| ↳ leader | `transaction` 8.34 s = 0.420단위 (6.7 %) | 7.357 s (16.3 %) |
| ↳ **내부 배경 스레드** | **`pgbuf-page-flush` 7.02 s = 0.354단위 (5.6 %)** | **N/A (SUT 경계 밖)** |
| **질의 실행분만 CPU/wall** | **5.927 = 6의 98.8 %** | 5.785 = 96.4 % |
| wall 비 2.741x vs SUT CPU 비 2.735x | | **차 0.23 %** |

**`CPU/wall`이 6을 넘는 경우의 읽는 법 (신규 조항)**: `cub_server`의 SUT CPU에는 질의 워커가
아닌 내부 배경 스레드(`pgbuf-page-flush` 등)가 섞인다. PG는 그 역할이 별개 프로세스
(bgwriter/checkpointer)라 ADR 0009 경계에서 빠진다. 따라서 **이용률 판정은 `parallel-query` +
leader 스레드만으로 계산하고, 내부 배경 스레드분은 별도 행으로 적는다.** 합산 단일 숫자는 내지
않는다(`broker+CAS`·`io worker` 열과 같은 취급).

**스레드 동시성 직접 표본화 (0.05 s × 402표본, 수집기 코어 20-23)** — before/after 스냅샷은
구간 내 생성·소멸 스레드를 놓치므로(잔차 97.6/123.8 s) 표본화가 필요하다.

| 구간 | t | `parallel-query` 존재 / 실행중 | 대응 노드 |
|---|---|---|---|
| 1 | 0.6–6.0 s | **12 / 6** | `sscan part`(5) + `sscan lineitem`(6) + `SUBQUERY` gather(2) 중첩 |
| 2 | 6.0–14.0 s | 7 / 6 | `HASHJOIN PROBE`(6) |
| 3 | 14.0–20.0 s | 5–6 / **5** | `SCAN(temp)` 인덱스 NL 체인(5) |

**`SUBQUERY` 2워커 노드의 정체가 확정됐다** — Q9에서 그 노드는 **gather 래퍼**이고 그 아래
실제 스캔이 5·6워커로 돈다. `1×2`를 "붕괴한 노드 1개"로 읽으면 오독이다. 3구간(격차 시간의
54 %)이 5워커인 것은 기록 대상이지만 이용률 98.8 %가 판정을 닫는다.

### 3. `SUBQUERY` 상수는 "무해"가 아니다 — 플랜 형상에 따라 유해해진다

정본 Q21 플랜에서는 2워커 노드가 0.83 %뿐이라 무해하지만, **좋은 플랜에서는 유해하다.**
Q21을 PG 플랜 형상으로 재작성한 변형(CUB-축소선행, 14.352 s)에서는 상관 서브쿼리가 조인
위로 올라가면서 **시간의 50.4 %가 degree 2 구간**에서 돈다(trace `SCAN (temp time: 8571 ms)`
/ 전체 17,021 ms). 따라서 이 상수는 **플랜 개선의 상한을 결정하는 항목**으로 등재한다.

## Consequences

* Q21 격차 분해에서 실행 단위 축은 **0.2~1.6 %**로 닫혔고, 남은 것은 플랜 축 4.436x와
  행당 실행 비용 축 3.228x다.
* 다중 조인 쿼리의 "붕괴" 주장은 **전부 이용률 재측정 대상**이다. G2 분류표는 플랜 채증
  테이블로 강등되고, 성능 결론의 근거로 단독 인용되지 않는다.
* `parallelism` 파라미터를 올려도 `SUBQUERY` 노드는 2에 고정된다. DOP sweep을 다시 열면
  이 사실을 sweep 축 정의에 명기한다(ADR 0014의 "축은 실행 단위 수" 조항에 부기).

## Status

Accepted (2026-07-29). ADR 0014를 **보강**한다 — 실행 단위 파리티 정의는 불변이고,
노드별 분포의 **읽는 법**이 추가된다. G2 보고서 결론 4번의 성능 해석을 정정한다.
