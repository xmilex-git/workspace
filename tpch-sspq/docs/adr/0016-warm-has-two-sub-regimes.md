# WARM에는 하위 레짐이 둘 있다 — 스트림 레짐과 단일 쿼리 반복 레짐을 같은 표에 섞지 않는다

ADR 0006은 WARM을 "측정 런 구간의 물리 read가 사라졌다는 채증"으로 정의했다. Q21 1단계
재측정에서 **그 정의를 통과하는 두 상태가 PostgreSQL wall을 12 % 다르게 만든다**는 것이
측정으로 확정됐다.

## 측정 사실

같은 Q21, 같은 단위 파리티 트랙, 같은 플랜, 물리 디스크 read 양쪽 0.

| PG `EXPLAIN ANALYZE` 최상위 카운터 | G2 (22쿼리 스트림 레짐) | Q21 단독 반복 레짐 | 델타 |
|---|---|---|---|
| `shared hit` | 10,557,216 | 11,252,570 | +695,354 |
| `shared read` | 1,275,875 | 580,522 | **−695,353 (−54.5 %)** |
| **`hit + read` (총 버퍼 접근)** | **11,833,091** | **11,833,092** | **+1** |
| `temp read / written` | 32,205 / 33,104 | 32,222 / 33,152 | +0.05 % |
| 구간 sda 물리 read | ≤94.5 MiB | 0.0–0.2 MiB | 양쪽 사실상 0 |
| `Execution Time` | 5,187.216 ms | 4,625.798 ms | **−561.4 ms** |
| wall (AB/BA 3블록 평균) | **5.038 s** | **4.446 s** | **−11.75 %** |

총 버퍼 접근량이 **1블록 차이로 동일**하므로 실행한 일의 양은 같다. 바뀐 것은 hit/read
분할뿐이고, 그 `read`는 물리 I/O가 아니라 OS page cache 히트였다. 즉 사라진 비용은
**shared buffer 미스 처리 경로**이며 단가는 **0.81 µs/미스**(`Execution Time` 기준)다.

**CUBRID는 같은 레짐 변화에 무감하다.** 같은 세션쌍에서 trace 카운터가 자릿수까지 불변:
최상위 `SELECT ioread` 4,046 → 4,048, l1 iscan `fetch` 23,511,192 → 23,511,192,
l2 서브쿼리 `fetch` 191,418,598 → 191,418,598, l3 206,379,912 → 206,379,912.
wall은 64.091 → 63.661 s(−0.67 %)로 within-set sd 안이다.

같은 기제가 3단계에서 한 번 더 관측됐다. PG 기준선이 4.446 → **4.679 s(+5.24 %)**로
움직였고, 그 사이에 있던 것은 2단계의 PG-펜스 실험(3 × ~300 s, lineitem 37.9 M × 37.9 M
`Parallel Hash Anti Join`)이었다. CUBRID 대조군은 63.661 → 63.470 s(−0.30 %)로 불변이다.

## Decision

### WARM은 하나의 레짐이 아니다 — 하위 레짐을 표에 명기한다

| 하위 레짐 | 정의 | 특징 |
|---|---|---|
| **stream** | 22쿼리(또는 다중 쿼리) 스트림을 순서대로 도는 상태 | 상대 쿼리들이 대상 쿼리의 워킹셋을 엔진 버퍼에서 밀어낸다. PG `shared_buffers` 8 GB ↔ Q21 워킹셋 90 GiB |
| **single-query-repeat** | 한 쿼리만 반복 실행하는 상태 | 그 쿼리의 워킹셋이 엔진 버퍼에 최대한 상주한다 |

* **모든 측정 표에 하위 레짐 필드를 적는다.** 비어 있으면 표에 올리지 않는다.
* **두 하위 레짐의 값을 같은 표에 합치지 않는다.** ADR 0006이 warm/cold에 적용한 규칙과
  같은 구조다.
* 배수·격차를 인용할 때 **어느 하위 레짐인지 반드시 붙인다.** Q21의 배수는
  stream 레짐 **12.72x**, single-query-repeat 레짐 **14.32x**다. 둘 다 유효하고 둘 다
  WARM이다.
* G2의 Pareto는 stream 레짐 값이므로 **stream 레짐으로 라벨을 붙인다.** 개별 쿼리를
  단독으로 파고드는 라운드는 구조적으로 single-query-repeat이 되므로, **G2 값과 개별
  라운드 값의 차이를 드리프트로 읽지 않는다** — 레짐이 다르다.

### 채증 수단은 엔진 버퍼 카운터다 (물리 read 카운터로는 구분되지 않는다)

ADR 0006의 물리 read 채증(1 % / 100 MiB)은 **그대로 유지**하되, 그것만으로는 하위 레짐이
구분되지 않는다. 하위 레짐 채증은 다음을 쓴다.

| 엔진 | 채증 |
|---|---|
| PostgreSQL | `EXPLAIN (ANALYZE, BUFFERS)`의 `shared hit` / `shared read` 분할. 총 `hit+read`가 같고 분할만 다르면 **레짐 차이**이고 일의 양 차이가 아니다 |
| CUBRID | `;trace on`의 노드별 `fetch` / `ioread`. Q21 실측처럼 자릿수까지 같으면 레짐 무감이다 |

**PG는 이 축에 민감하고 CUBRID는 무감하다**는 것이 Q21 실측이다. 그러므로 이 비대칭은
제거 대상이 아니라 **기록 대상**이며, 레짐을 통제하지 않으면 **PG 쪽만 흔들려 배수가
움직인다.**

## 추가 관측 — Q9 (2026-07-29). 결정은 불변, "민감"의 조건이 좁혀진다

Q9를 같은 방식으로 재면 **PG가 이 축에 민감하지 않다.**

| PG `EXPLAIN ANALYZE` 최상위 카운터 | Q9 stream | Q9 single-query-repeat | 델타 |
|---|---|---|---|
| `shared hit` | 20,165,807 | 20,567,873 | +402,066 |
| `shared read` | 1,007,160 | 605,102 | **−402,058 (−39.9 %)** |
| **`hit + read`** | **21,172,967** | **21,172,975** | **+8 (동일)** |
| `temp read / written` | 26,548 / 26,626 | 26,550 / 26,628 | +0.008 % |
| **wall** | **7.062 s** | **7.253 s** | **+2.70 %** |

총 버퍼 접근이 8블록 차이로 동일한 것은 Q21과 같다(구조 재현). 그런데 **미스를 40 % 줄였는데
wall이 2.70 % 늘었다** — Q21(미스 −54.5 % → wall −11.75 %)과 방향이 반대다.

**이유는 구조적이고 측정으로 확정된다**: Q9 PG의 `read` 605,102 **전량이
`Parallel Seq Scan on lineitem` 노드**에 있고(hit 520,026 / read 605,102), lineitem 힙은
1,125,128 블록 = **8.6 GB > `shared_buffers` 8 GB**다. 워킹셋이 버퍼보다 크면 어느 하위 레짐에서도
미스가 남으므로 레짐 이동이 wall을 움직이지 못한다. CUBRID는 Q21과 같이 무감하다
(trace 최상위 `fetch` 5,413,536 → 5,413,437, wall +1.02 %).

**따라서 "PG가 민감하다"는 조건부 서술로 정정한다** — 민감한 것은 **대상 쿼리의 워킹셋이
`shared_buffers`에 들어갈 때**이고, 들어가지 않으면(Q9 lineitem) 무감하다. 표기 의무와
"두 레짐을 같은 표에 섞지 않는다"는 결정은 **불변**이다. 오히려 이 관측이 그 의무를 강화한다 —
민감도가 쿼리마다 다르므로 레짐 라벨 없이는 어느 쪽인지 알 수 없다.

## 추가 관측 — Q8 (2026-07-29). "민감"의 판정 기준을 잔존율로 바꾼다

Q8 PG는 **민감하다.** 그런데 Q9와 워킹셋 조건이 같다 — 두 쿼리 모두 `read` 전량이
`Parallel Seq Scan on lineitem`(힙 1,125,128 블록 = 8.6 GB > `shared_buffers` 8 GB)에 있다.

| PG `EXPLAIN (ANALYZE, BUFFERS)` 최상위 | Q8 상태 A | Q8 상태 B | 델타 |
|---|---|---|---|
| `shared hit` | 828,069 | 939,944 | +111,875 |
| `shared read` | 637,600 | 525,725 | **−111,875 (−17.5 %)** |
| **`hit + read`** | **1,465,669** | **1,465,669** | **0 (완전 동일)** |
| ↳ lineitem 노드 hit/read | 487,528 / 637,600 | 599,403 / 525,725 | 잔존율 **43.3 % → 53.3 %** |
| `Execution Time` | 2,950.006 ms | 2,657.179 ms | **−9.9 %** |
| SUT CPU/런 | 15.348 s | 13.720 s | −10.6 % |
| **wall (문장, ×5)** | **2.620 s** | **2.343 s** | **−10.6 %** |
| 구간 sda 물리 read | 0.0 MiB | 0.0 MiB | 양쪽 0 |

미스 단가 **2.62 µs/미스**. CUBRID는 무감(trace 최상위 `fetch` 731,859 → 731,845 = −0.002 %).

**정정**: 위 §"PG가 민감하다는 조건부 서술"의 조건은 **"워킹셋이 `shared_buffers`에 들어가는가"가
아니라 "버퍼 잔존율이 상태에 따라 움직이는가"**다. Q8과 Q9는 워킹셋 조건이 같은데 Q8만
잔존율이 43.3 % ↔ 53.3 %로 움직였고(동시 상주 압력이 낮다 — `part` 해시 704 kB,
`orders` 해시 43.9 MB), Q9는 움직이지 않았다. **표기 의무와 "두 레짐을 같은 표에 섞지
않는다"는 결정은 여전히 불변**이며, 여기에 하나가 추가된다.

**신규 조항 — 같은 하위 레짐 안에서도 상태가 갈릴 수 있다.** Q8은 **둘 다
`single-query-repeat`**인 두 창에서 배수가 **3.43x ↔ 3.96x**로 갈렸다. 따라서
`stream`/`single-query-repeat` 라벨만으로는 부족하고, **PG 측 표에는 `shared hit`/`read`
분할을 같이 적는다.** 분할이 다른 두 값을 같은 평균으로 뭉개지 않는다. 이 차이를
between-session drift로 세지 않는 것도 같다(ADR 0010).

## Consequences

* Q21 배수의 헤드라인은 **레짐마다 따로** 존재한다. G2 Pareto(stream) 12.72x와 개별
  라운드(single-query-repeat) 14.32x는 **모순이 아니다.**
* ADR 0010의 "between-session drift" 개념에 **레짐 성분이 분리돼 나온다.** 세션 간 차이를
  볼 때 먼저 레짐이 같은지 확인하고, 다르면 그 차이를 미규명 드리프트로 세지 않는다.
* 앞으로 개별 쿼리를 파는 라운드는 **자기 레짐의 기준선을 같은 세션 안에서 다시 재야 한다.**
  3단계 프로파일링이 그렇게 했고(perf 없는 기준선 2회를 같은 세션에서 재측정), 그렇게 하지
  않으면 프로파일링 오버헤드 판정이 레짐 이동에 오염된다(실측: 오염된 계산 +7.96 %,
  같은 세션 기준 +2.58 %).
* PG를 stream 레짐으로 강제하려면 상대 쿼리를 실제로 돌려야 한다. `shared_buffers`를
  줄여 모방하는 것은 **다른 구성이므로 하지 않는다**(Comparison Snapshot 변경).

## Status

Accepted (2026-07-29). ADR 0006을 **보강**한다(대체하지 않는다) — 물리 read 채증과
warmup 절차는 그대로 유효하고, 여기에 하위 레짐 표기 의무가 추가된다.
