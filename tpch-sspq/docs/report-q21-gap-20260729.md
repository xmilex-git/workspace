# Q21 격차 규명 — 재현·플랜 대조·축 분리·대칭 프로파일·소스 규명

2026-07-29. 단위 파리티 트랙만(CUBRID `parallelism=6` ↔ PG 세션 GUC
`max_parallel_workers_per_gather=5` + leader = 양쪽 6 실행 단위). Q21 단독 세션.

> **PG 각주 (ADR 0015 의무)**: PostgreSQL 수치는 `dynamic_shared_memory_type=mmap`
> 구성이다(기본값 `posix` 이탈). 전환 비용 실측은 PG가 1.40 % 빨라진 것이었고, 같은
> 세션쌍의 무변경 CUBRID 대조군이 −0.72 % 드리프트했으므로 mmap 귀속분은 최대 약
> 0.7 %p다. 이 보고서의 PG 수치는 **전부 mmap**에서 측정됐다.
>
> **대외 인용 단서 3건**: PG 개발 스냅샷 핀(`5713b437`, 20devel) / CUBRID
> `update_statistics_update_histogram=yes`(기본값 이탈) / PG DSM mmap. 어느 엔진도
> "출시 기본 설정 제품의 성능"이 아니다.

## 1단계 — 재현과 플랜 대조

### 결론 (5줄)

1. **CUBRID는 재현됐다(63.661 s, G2 64.091 대비 −0.67 %). PostgreSQL은 재현되지
   않았다(4.446 s, G2 5.038 대비 −11.75 %).** 그래서 배수가 **12.72x → 14.32x**로
   커졌다.
2. **PG 델타의 원인은 측정으로 확정된다 — shared_buffers 온도다.** 총 버퍼 접근량이
   G2와 **1블록 차이로 동일**한데(11,833,091 → 11,833,092) hit/read 분할만 바뀌었다
   (read 1,275,875 → 580,522, **−54.5 %**). 물리 디스크 read는 양쪽 세션 모두 0이므로
   그 read는 전부 OS page cache 히트였고, 사라진 것은 **버퍼 미스 처리 비용**이다
   (592 ms / 695,353 미스 = 0.85 µs/미스).
3. **즉 ADR 0006의 WARM 판정(물리 read≈0)을 양쪽 세션이 다 통과하는데 PG wall이
   12 % 다르다.** 22쿼리 스트림 레짐은 Q21의 워킹셋을 8 GB shared_buffers에서 밀어내고,
   Q21 단독 반복 레짐은 밀어내지 않는다. **CUBRID는 이 레짐 차이에 무감하다**(trace
   `ioread` 4046 → 4048, sda 0.0 MiB).
4. **플랜 형상은 양쪽 다 G2와 완전히 동일하게 재현됐다.** CUBRID
   `orders sscan → l1 iscan(sargs에 EXISTS/NOT EXISTS 부착) → hash-join supplier →
   hash-join nation`, PG `lineitem l1 → supplier ⋈ nation → semi join(l2) →
   orders 해시조인 → anti join(l3)`.
5. **조인 순서 차이가 상관 서브쿼리 호출량을 결정한다** — CUBRID는 선택도 0.04의
   nation 필터를 **마지막에** 적용하므로 l1 인덱스 키 29,058,120행 위에서 두 서브쿼리를
   돌려 **436,325,872 인덱스 키**를 읽고, PG는 supplier⋈nation을 **먼저** 적용해
   1,522,366 + 707,593 = **2,229,959 인덱스 서치**로 끝낸다.

### 1.2 wall time 재측정

집계 세트는 CPU 채증까지 붙은 `s1b`(AB/BA 3블록, 전 런 sda ≤ 0.1 MiB)를 주 세트로 쓴다.

|---|---|---|---|---|---|---|---|---|---|---|---|
| **s1b (주)** | 62.894 | 64.283 | 63.807 | **63.661** | 0.706 | 4.459 | 4.460 | 4.418 | **4.446** | 0.024 | **14.32x** |
| s1 (타이밍 전용) | 64.790† | 63.325 | 62.504 | (63.540) | 1.158 | 4.442 | 4.450 | 4.411 | 4.434 | 0.021 | 14.33x |
| **풀링 (유효 런 전부)** | 5런 | | | **63.363** | 0.708 | 6런 | | | **4.440** | 0.021 | **14.27x** |
| G2 기준 | 63.525 | 64.048 | 64.700 | 64.091 | 0.589 | 5.107 | 4.987 | 5.020 | 5.038 | 0.062 | 12.72x |

† `s1` CUBRID b1은 구간 sda read **132.1 MiB**로 ADR 0006의 절대 문턱(100 MiB)을
위반했다 → **무효 처리**하고 평균에서 뺐다(괄호 값은 참고용 3런 평균). 논리 읽기량 대비로는

**실행 단위 채증** (모든 표 의무, ADR 0014)

| | CUBRID | PostgreSQL |
|---|---|---|
| 설정 | `parallelism=6` | `max_parallel_workers_per_gather=5` (세션) |

| leader 참여 | `transaction` 스레드 CPU **0.93 s / 371.9 s = 0.25 %** → 미참여 | leader CPU 4.193 s ≈ worker 평균 4.345 s → 완전 참여 |
| **실행 단위** | **6** | **6** |

### 1.4 PG 델타의 원인 — 채증

| 카운터 (PG `EXPLAIN ANALYZE` 최상위 노드) | G2 (스트림 레짐) | 이번 (Q21 단독 반복) | 델타 |
|---|---|---|---|
| `shared hit` | 10,557,216 | 11,252,570 | +695,354 |
| `shared read` | 1,275,875 | 580,522 | **−695,353 (−54.5 %)** |
| **hit + read (총 버퍼 접근)** | **11,833,091** | **11,833,092** | **+1 (동일)** |
| `temp read / written` | 32,205 / 33,104 | 32,222 / 33,152 | +0.05 % |
| 구간 sda 물리 read | 94.5 MiB 이하 | 0.0–0.2 MiB | 양쪽 사실상 0 |
| `Execution Time` | 5,187.216 ms | 4,625.798 ms | −561.4 ms |

총 접근량이 1블록 차이로 같으므로 **실행한 일의 양은 동일하다.** 바뀐 것은
hit/read 분할뿐이고, `read`가 물리 I/O가 아니라 OS page cache 히트였으므로
없어진 비용은 **shared buffer 미스 처리 경로**다: 561 ms / 695,353 = **0.81 µs/미스**
(wall 기준 592 ms → 0.85 µs/미스).

**CUBRID 대조** — 같은 레짐 변화에 무감하다.

| | G2 trace | 이번 trace |
|---|---|---|
| 최상위 `SELECT ioread` | 4,046 | 4,048 |
| l1 iscan `fetch` | 23,511,192 | 23,511,192 |
| l2 서브쿼리 `fetch` | 191,418,598 | 191,418,598 |
| l3 서브쿼리 `fetch` | 206,379,912 | 206,379,912 |

**계약에 등재해야 할 사실**: ADR 0006의 WARM 판정(물리 read ≈ 0)은 **shared_buffers /
data_buffer 온도를 통제하지 않는다.** 22쿼리 스트림 레짐과 단일 쿼리 반복 레짐은 둘 다
WARM을 통과하지만 PG Q21에서 12 %의 wall 차이를 만든다. 두 레짐의 값을 같은 표에 섞으면
안 되며, 이 보고서는 **단일 쿼리 반복 레짐**의 값이다.

### 1.6 플랜 — 노드 단위 대조

#### CUBRID 플랜 (`SET OPTIMIZATION LEVEL 514` + `;trace on` 실측)

```
temp(order by)                                    cost 125666838 card 5088
  temp(group by)                                  cost 125666815 card 5088
    hash-join (inner)  edge term[0] s_nationkey=n_nationkey   cost 125666793 card 5088
      outer: hash-join (inner)  edge term[1] s_suppkey=l1.l_suppkey  cost 125658930 card 127202
               outer: idx-join (inner)                        cost 125639330 card 127478
                        outer: sscan orders   sargs term[6] o_orderstatus='F'  cost 189189 card 7362833
                        inner: iscan l1  index pk_lineitem(l_orderkey,l_linenumber)  term[2]
                                 sargs: term[4] EXISTS AND term[5] date AND term[7] NOT EXISTS
                                 subqs: 0 1                   cost 37 card 539874
               inner: sscan supplier                          cost 1531 card 100000
      inner: sscan nation  sargs term[3] n_name='SAUDI ARABIA' cost 1 card 1
```

#### PostgreSQL 플랜

```
Limit -> Sort -> GroupAggregate -> Sort -> Gather (Workers Planned/Launched 5)
  Nested Loop Anti Join                                   (l3)
    Parallel Hash Join  l1.l_orderkey = orders.o_orderkey
      Nested Loop Semi Join                               (l2)
        Parallel Hash Join  l1.l_suppkey = supplier.s_suppkey
          Parallel Seq Scan lineitem l1  Filter l_receiptdate > l_commitdate
          Parallel Hash <- Hash Join supplier.s_nationkey = nation.n_nationkey
                             Parallel Seq Scan supplier
                             Hash <- Seq Scan nation  Filter n_name='SAUDI ARABIA'
        Index Scan lineitem_pkey l2  Index Cond l2.l_orderkey = l1.l_orderkey
      Parallel Hash <- Parallel Seq Scan orders  Filter o_orderstatus='F'
    Index Scan lineitem_pkey l3  Index Cond l3.l_orderkey = l1.l_orderkey
```

#### 조인 순서·방식·인덱스 사용 대조

| 축 | CUBRID | PostgreSQL |
|---|---|---|
| 구동 테이블 | **orders** (전체 15,000,000행 힙 스캔, `o_orderstatus='F'`는 스캔 sarg) | **lineitem l1** (전체 59,986,052행 병렬 힙 스캔) |
| lineitem l1 접근 | **인덱스 스캔** — `pk_lineitem(l_orderkey,l_linenumber)`, 키 조건 `orders.o_orderkey = l1.l_orderkey` | **병렬 순차 스캔** (인덱스 미사용) |
| `EXISTS`(l2) 처리 | **l1 스캔 노드의 sarg** (`term[4]`, subquery[0]) — 조인 노드가 아니다 | **Nested Loop Semi Join** — 1급 조인 노드 |
| `NOT EXISTS`(l3) 처리 | **l1 스캔 노드의 sarg** (`term[7]`, subquery[1]) | **Nested Loop Anti Join** — 1급 조인 노드, 최상단 |
| l2/l3 인덱스 | `pk_lineitem_l_orderkey_l_linenumber` | `lineitem_pkey` (동일 키) |
| supplier 접근 | 순차 스캔 100,000행 → **해시 BUILD 100,000행** (`method: hybrid`) | 병렬 순차 스캔 → nation과 해시조인 후 **4,010행만** BUILD |
| nation 필터(sel 0.04) 위치 | **최상단** — l1·서브쿼리 전부 끝난 뒤 | **최하단** — supplier BUILD를 4,010행으로 줄인 뒤 lineitem에 적용 |
| orders 해시 | 없음(구동측) | `Parallel Hash` 1,218,197×6행, Batches 64, temp write 21,608 |
| 정렬 | `temp(group by)` sort + `temp(order by)` sort | `Sort`(quicksort 1,537 kB) + `Sort`(top-N heapsort 36 kB) |

### 결론 (5줄)

1. **14.32x는 곱으로 정확히 갈라진다: 플랜·조인 전략 4.436x × 행당 실행 비용 3.228x =

   뒤의 항은 플랜 형상이 일치한 상태의 엔진 간 비로 측정했다.
2. **실행 단위 축의 기여는 0에 가깝다(1.002~1.016x, 즉 0.2~1.6 %).** G2가 본 `4×2 1×3 1×6`
   붕괴는 실재하지만 **일을 하는 노드는 `1×6`이다** — `parallel-query` 스레드 6개가 각각
   58.4~63.4 s를 태워 SUT CPU 370.4 s를 만들고(6단위의 **96.97 %**), 2워커 노드들의
   자기 시간 합은 **675 ms = 0.83 %**다. PG의 이용률은 98.5 %로 사실상 같다.

   `src/query/parallel/px_parallel.cpp:85-109`, `parallel_type::SUBQUERY`의 병렬도는
   **데이터·`parallelism` 파라미터와 무관하게 상수 1**(`auto_degree = 1`, 주석

   격차로 수축한다 — 즉 Q21의 **초과분 4.4x는 전부 플랜이 만든 것**이다.
5. **플랜 차이의 뿌리는 비용 비교가 아니라 탐색 공간이다.** 상관 서브쿼리는

   CUBRID에는 semi/anti join 연산자가 아예 없다.

`src/query/parallel/px_parallel.cpp:37` `compute_parallel_degree (type, num_pages, hint_degree)`

### 2.4 PG-펜스 실험 — 무효 (기록만)

CUBRID 형상을 PG에 강제하려고 서브쿼리를 `OFFSET 0` 펜스 안에 넣었다. **PG는 CUBRID
형상을 만들지 않았다** — 추정 `rows=1` 때문에 전혀 다른 병리를 골랐다:
`Parallel Hash Anti Join`(lineitem 37.9 M × lineitem 37.9 M 해시) +
`Nested Loop` / `Materialize` / `Join Filter: supplier.s_suppkey = l1.l_suppkey`
(supplier 4,000행 × 머티리얼라이즈된 서브쿼리).

| rep | wall | 결과 |
|---|---|---|
| 1 | 298.405 s | 100행 |
| 2 | 299.650 s | 100행 |
| 3 | 300.318 s | **`statement_timeout` 취소** |

**이 값은 축 분리에 쓰지 않는다** — 측정하려던 것(CUBRID 조인 순서)을 재현하지 못했다.
부수 사실로만 남긴다: 서브쿼리 pullup을 막으면 PG는 4.446 s → ~299 s(**67x**)로 무너진다.
즉 **PG의 성능은 semi/anti join pullup에 의존한다.**

### 2.5 플랜 차이의 뿌리 — 비용 비교가 아니라 탐색 공간

정본 질의에서 조인 순서를 힌트로 강제해 옵티마이저가 볼 수 있는 대안을 열거했다
(`SET OPTIMIZATION LEVEL 514`, 무실행).

| 힌트 | 결과 플랜 | l1 노드의 sargs | **추정 총 cost** |
|---|---|---|---|
| 없음 (정본) | `hash-join(hash-join(idx-join(orders sscan, l1 iscan), supplier), nation)` | `term[4] AND term[5] AND term[7]`, `subqs: 0 1` | **125,666,838** |
| `/*+ ORDERED */` FROM `nation,supplier,l1,orders` | `idx-join(hash-join(hash-join(nation,supplier), l1 sscan), orders iscan)` | **동일하게 l1에 부착** | **487,999,847** (3.88배 비쌈) |
| `/*+ LEADING(nation,supplier,l1,orders) */` | 위와 동일 | 동일 | 487,999,847 |
| `/*+ NO_USE_HASH */` | `idx-join(idx-join(idx-join(orders,l1),supplier),nation)` | 동일 | 125,770,540 |

**어떤 조인 순서에서도 `sargs: term[4] AND term[5] AND term[7]` + `subqs: 0 1`이 l1 노드를
떠나지 않는다.** supplier⋈nation을 먼저 하도록 강제하면 l1이 **전체 sscan**이 되어 서브쿼리가
59,986,052행 위에서 돌게 되므로 추정 cost가 오히려 3.88배 오른다. 즉 **옵티마이저는 자기가
볼 수 있는 대안 중 가장 싼 것을 정확히 골랐다.** 결함은 비용 비교가 아니라 **대안 집합**이다.

참조: CUB-축소선행(질의 재작성으로만 표현 가능)의 추정 cost는 내부 블록 1,266,078 + 외부
블록 459,383 = **~1.73 M**으로 정본의 125.67 M보다 **72.8배 싸다.** 그 플랜은 정본 질의의
탐색 공간에 **존재하지 않는다.**

#### 소스 — 상관 서브쿼리가 노드에 못박히는 지점

`src/optimizer/query_planner.c:9079-9107` (`qo_planner_search`, 조인 열거 **이전**):

```c
for (i = 0; i < (signed) planner->N; ++i)          /* 노드별 스캔 플랜 생성 루프 */
  {
    ...
    BITSET_CLEAR (subqueries);
    for (subq_idx = bitset_iterate (&remaining_subqueries, &si); subq_idx != -1; ...)
      {
        subq = &planner->subqueries[subq_idx];
        if (bitset_is_empty (&subq->nodes)                    /* uncorrelated */
            || (bitset_subset (&nodes, &(subq->nodes))        /* correlated  */
                && bitset_subset (&(QO_NODE_SARGS (node)), &(subq->terms))))
          {
            bitset_add (&subqueries, subq_idx);
            bitset_remove (&remaining_subqueries, subq_idx);   /* <- 되돌릴 수 없다 */
          }
      }
    bitset_assign (&(QO_NODE_SUBQUERIES (node)), &subqueries);
  }
```

상관 참조가 정확히 한 노드만 가리키면(Q21의 l2/l3는 `{l_suppkey[1], l_orderkey[1]}` = node[1]
하나) 그 노드에 배정되고 `remaining_subqueries`에서 **제거**된다. 이후 조인 플랜은
`query_planner.c:1655`(`bitset_assign (&(plan->subqueries), &(QO_NODE_SUBQUERIES (node)))`)로
그것을 그대로 물려받으므로 **조인 위로 올릴 경로가 없다.**

비용 모델 자체는 서브쿼리를 세고 있다 — `query_planner.c:776-783`이
`variable_cpu_cost += scan_rows × subq_cpu_cost`로 곱한다. 문제는 **곱해질 자리가 하나로
고정돼 있다는 것**이다.

그리고 **CUBRID에는 semi/anti join이라는 개념이 없다**:

```
$ grep -rniE "semi.?join|anti.?join" src/optimizer/ src/parser/   ->  0건
```

trace의 재작성 질의가 그것을 보여준다 — `EXISTS`는 조인으로 바뀌지 않고
`inst_num() <= 1`(첫 행에서 멈추는 존재 검사)이 붙은 상관 서브쿼리로 남는다.
